## CHAPTER 1 데이터 엔지니어링 상세

### 1.1 데이터 엔지니어링이란?

데이터 엔지니어링은 단순히 특정 기술을 다루는 것이 아니라, **데이터를 생성 → 저장 → 수집 → 변환 → 제공**하는 전체적인 과정과 이를 뒷받침하는 원칙을 다루는 분야다. 데이터 과학, 분석, 머신러닝이 성과를 내기 위해 필요한 **기초 인프라와 프로세스**를 구축하는 역할을 담당한다.

#### 1.1.1 데이터 엔지니어링 정의

- **정의**: 원시 데이터를 받아 **고품질·일관된 정보**로 가공해 분석과 머신러닝 같은 다운스트림 사용 사례를 지원하는 시스템과 프로세스를 설계·구현·운영하는 것.
- **핵심 교차 영역**: 보안, 데이터 관리, DataOps, 데이터 아키텍처, 오케스트레이션, 소프트웨어 엔지니어링.
- **데이터 엔지니어 역할**: 수명 주기 전반을 관리(소스에서 데이터 가져오기 → 가공 → 활용 가능하게 제공).

#### 1.1.2 데이터 엔지니어링 수명 주기

**5단계**:

1. **Generation (생성)** – 소스 시스템에서 데이터가 만들어짐.
2. **Storage (저장)** – 데이터가 보존되는 곳 (DB, 파일 시스템, 클라우드 등).
3. **Ingestion (수집)** – 저장된 데이터를 가져와 파이프라인에 넣음.
4. **Transformation (변환)** – 데이터를 정제·모델링·가공하여 목적에 맞게 준비.
5. **Serving (제공)** – 분석·머신러닝·비즈니스 시스템에 데이터 전달.

**언더커런트(공통 주제)**: 보안, 데이터 관리, DataOps, 데이터 아키텍처, 오케스트레이션, 소프트웨어 엔지니어링이 전 단계에 걸쳐 중요하다.

#### 1.1.3 데이터 엔지니어링의 진화

- **1980–2000년대 초반**: 데이터 웨어하우스, BI, ETL 개발자 등에서 출발.
- **2000년대 중반–2010년대**: 구글의 GFS·MapReduce 논문과 하둡(Hadoop) 등 오픈소스 빅데이터 기술의 등장 → "빅데이터 엔지니어" 시대.
- **2010년대 후반**: 스트리밍, 클라우드, 다양한 오픈소스·상용 도구 확산. 빅데이터라는 용어는 희석되고, 단순히 "데이터 엔지니어링"으로 통합.
- **2020년대**: 클라우드 기반, 모듈화, 관리형 서비스 중심으로 변화. "데이터 수명 주기 엔지니어"로서 **데이터 관리·보안·데이터 거버넌스**까지 담당하는 방향으로 발전.

#### 1.1.4 데이터 엔지니어링과 데이터 과학

- **관계**: 데이터 엔지니어링은 **업스트림**, 데이터 과학은 **다운스트림**.
- **데이터 과학의 현실**: 실제로는 70–80%의 시간을 데이터 수집·정제·처리에 사용.
- **핵심 메시지**: 데이터 엔지니어링이 잘 구축되어야 데이터 과학자들이 **분석·실험·ML 모델링**에 집중할 수 있다.
- **비유**: 데이터 과학을 위한 "토대(인프라)"를 다지는 것이 데이터 엔지니어링.

### 1.2 데이터 엔지니어링 기술과 활동

데이터 엔지니어는 단순히 파이프라인만 만드는 것이 아니라, **데이터 라이프사이클 전반**을 관리하며 보안, 데이터 관리, DataOps, 아키텍처, 소프트웨어 엔지니어링 등 다양한 영역을 아우르는 활동을 수행한다. 핵심은 **비즈니스 요구와 기술적 구현을 연결**하는 역할이다.

#### 1.2.1 데이터 성숙도와 데이터 엔지니어

**데이터 성숙도**: 조직이 데이터를 활용하는 능력의 성숙 단계를 의미.

**세 가지 단계**:

1. **시작(Starting with Data)** – 초기 단계, 데이터 활용 목표가 모호, 소규모 팀, 데이터 엔지니어는 **제너럴리스트**로서 다양한 역할(분석/엔지니어링 혼합) 수행.
2. **확장(Scaling with Data)** – 데이터 파이프라인·아키텍처가 정립되며, 역할이 **전문화**됨. DevOps/DataOps 도입, 확장성과 안정성이 핵심.
3. **리딩(Leading with Data)** – 데이터가 완전히 내재화된 조직. 자동화된 파이프라인, 셀프서비스 분석/ML 환경, **데이터 거버넌스·품질 관리** 강화.

**포인트**: 단계가 올라갈수록 엔지니어링의 초점이 **빠른 구현 → 확장성 → 거버넌스와 전략적 경쟁력**으로 이동한다.

#### 1.2.2 데이터 엔지니어의 배경과 기술

데이터 엔지니어의 배경은 다양함: **소프트웨어 엔지니어링, 데이터베이스, BI, 통계/분석** 등.

**요구되는 기술 스택**:

- **프로그래밍** (Python, SQL 등)
- **데이터베이스 지식** (OLTP, OLAP, NoSQL 등)
- **분산 시스템과 클라우드 인프라**
- **ETL/ELT, 데이터 파이프라인, 오케스트레이션 툴**
- **보안, 데이터 거버넌스, 데이터 관리 기법**

**특징**: 단일 기술 전문가가 아니라 **폭넓은 스킬셋을 통합적으로 운영**하는 역할.

#### 1.2.3 비즈니스 책임

데이터 엔지니어는 기술뿐 아니라 비즈니스적으로도 중요한 책임을 진다.

- **이해관계자와의 소통** – 데이터 요구를 기술적 설계로 변환.
- **경영진 설득** – 데이터 인프라 투자 가치 설명 및 ROI 확보.
- **데이터 활용 촉진** – 조직 내 데이터 리터러시 향상, 셀프서비스 환경 지원.
- **비즈니스 경쟁력 강화** – 데이터로 차별화된 제품·서비스 제공을 가능하게 함.

#### 1.2.4 기술 책임

핵심은 **데이터 라이프사이클 구현과 운영**.

- 소스에서 데이터 **획득·저장·이동·변환·제공**.
- 파이프라인과 데이터 아키텍처를 **확장 가능하고 안정적**으로 설계.
- **보안·품질 관리·거버넌스** 적용.
- 최신 기술 도입 시 **비용·효율·비즈니스 가치**를 고려해 판단.
- 운영 중 문제 해결(신뢰성·성능·스케일링 등).

#### 1.2.5 A에서 B로 이어지는 데이터 엔지니어링 역할의 연속성

데이터 엔지니어링 역할은 고정적이지 않고 **스펙트럼**을 이룬다.

- **A쪽**: 데이터 분석에 가까운 역할 (SQL 중심, 리포트·모델링 지원).
- **B쪽**: 소프트웨어 엔지니어링에 가까운 역할 (분산 시스템, 데이터 인프라 구축).

대부분의 데이터 엔지니어는 이 스펙트럼 어딘가에 위치하며, 조직의 규모·성숙도·필요에 따라 역할이 달라진다.

즉, 데이터 엔지니어링은 **"데이터 중심 소프트웨어 엔지니어링"에서 "분석 지원 전문 엔지니어링"까지 이어지는 연속적인 역할군**으로 이해할 수 있다.

### 1.3 조직 내 데이터 엔지니어

#### 1.3.1 내부 vs 외부 대면 데이터 엔지니어

**내부 대면 데이터 엔지니어 (Internal-facing)**

- 주요 "고객"은 **내부 팀** (데이터 과학자, 분석가, 제품팀 등).
- 역할: 데이터 파이프라인과 플랫폼을 구축해 **분석·실험·모델링**을 지원.
- 예: 내부 데이터 플랫폼팀, BI 데이터 엔지니어.

**외부 대면 데이터 엔지니어 (External-facing)**

- **외부 고객**을 직접 지원하는 경우.
- 예: SaaS 회사에서 고객 데이터를 처리하는 파이프라인, 데이터 제품을 직접 제공하는 팀.
- 기술뿐 아니라 **고객 요구를 충족하는 비즈니스 마인드** 필요.

#### 1.3.2 데이터 엔지니어와 기타 기술 역할

**소프트웨어 엔지니어**

- 코드·애플리케이션 개발이 중심.
- 데이터 엔지니어는 시스템 관점보다는 **데이터 흐름** 중심.

**데이터 과학자/분석가**

- 다운스트림 사용자. 데이터 엔지니어링이 없다면 대부분의 시간을 데이터 준비에 소모.
- 데이터 엔지니어는 이들의 **데이터 수요를 충족**시켜 "분석 속도"와 "가치 창출"을 높임.

**DevOps/플랫폼 엔지니어**

- 인프라 자동화, 배포, 운영 신뢰성에 집중.
- 데이터 엔지니어는 데이터 파이프라인을 구축·운영하는 과정에서 이들과 밀접하게 협업.

**요약**: 데이터 엔지니어는 **교차 역할**에 있으며, 소프트웨어·데이터 과학·운영 사이의 **중재자/연결자** 역할.

#### 1.3.3 데이터 엔지니어와 비즈니스 리더십

데이터 엔지니어는 단순히 기술자에 그치지 않고 **비즈니스 전략과 실행을 잇는 가교**.

**비즈니스 리더십과 협력**:

- 데이터 전략이 조직 목표와 일치하도록 설계.
- ROI와 비용 효율성을 고려한 인프라 제안.
- 데이터 거버넌스·품질 관리 체계를 경영진과 함께 수립.

**데이터 기반 문화** 확립에서 중요한 기여:

- 엔지니어링을 통해 데이터를 **신뢰 가능한 자산**으로 전환.
- 비즈니스 의사결정이 데이터 중심적으로 이루어지도록 지원.

### 1.4 결론

- 데이터 엔지니어링은 **분석·데이터 과학·머신러닝 성공을 가능하게 하는 토대**.
- 단순히 "데이터 파이프라인을 만드는 직무"가 아니라, **기술적 전문성** + **비즈니스 이해** + **협업 역량**을 요구하는 복합적인 역할.
- 데이터 엔지니어는 조직 내에서 **데이터 성숙도를 끌어올리고**, **내부/외부 이해관계자** 모두에게 가치를 창출.
- 결국, 데이터 엔지니어링은 "데이터를 전략적 자산으로 만드는 엔진" 역할을 수행한다.

## CHAPTER 2 데이터 엔지니어링 수명 주기

### 2.1 데이터 엔지니어링 수명 주기란?

데이터 엔지니어링은 단일 기술이 아니라, **데이터가 생성 → 저장 → 수집 → 변환 → 제공(서빙)** 되는 **연속적인 프로세스**.

이 수명 주기는 조직의 데이터 활용 수준에 관계없이 **핵심 프레임워크**로 작동.

각 단계는 독립적이면서도 상호 연결되어 있으며, 엔지니어는 전체 파이프라인 관점에서 관리해야 한다.

#### 2.1.1 데이터 수명 주기 vs 데이터 엔지니어링 수명 주기

**데이터 수명 주기(Data Lifecycle)**: 데이터가 태어나고(생성), 사용되고, 저장되다가 결국 폐기되는 **존재의 전체 과정**을 의미.

**데이터 엔지니어링 수명 주기(Data Engineering Lifecycle)**: 데이터가 **활용 가능한 자산**으로 전환되는 과정을 중점적으로 다룸.

- 즉, 단순히 보존·폐기까지 포함하는 것이 아니라 **"가치 창출"을 위한 흐름**에 초점.

두 개념은 겹치지만, 엔지니어링 수명 주기는 보다 **실용적이고 기술 중심적**.

#### 2.1.2 데이터 생성

- 데이터는 **애플리케이션, IoT 센서, 로그, 외부 API, 거래 시스템** 등 다양한 소스에서 생성.
- 중요한 점은 데이터가 **의도적으로 만들어지지 않은 경우**(예: 로그)도 많다는 것.
- 데이터 엔지니어는 **어떤 데이터가 생성되는지, 형식과 품질은 어떠한지** 이해해야 함.
- 생성 단계에서 품질·표준을 고려하지 않으면 이후 과정에서 큰 비용이 발생.

#### 2.1.3 데이터 저장

데이터가 머무는 장소.

**주요 스토리지 유형**:

- **OLTP 데이터베이스** (트랜잭션 처리 중심)
- **데이터 웨어하우스** (분석·리포팅 최적화)
- **데이터 레이크** (원시·비정형 데이터 저장)
- **NoSQL/분산 저장소** (특수 목적: 그래프, 키-값 등)

스토리지는 이후 수집과 변환의 기반이 되므로, **확장성·비용·성능·보안**의 균형을 고려해야 한다.

#### 2.1.4 데이터 수집

저장된 데이터를 **파이프라인으로 가져오는 과정**.

**수집 방식**:

- **Batch ingestion (일괄 수집)** – 정해진 주기로 데이터를 모아 처리.
- **Streaming ingestion (실시간 스트리밍)** – 이벤트 발생 즉시 전달.

**고려할 요소**:

- **지연 시간(latency)** vs **비용/복잡성**
- **데이터 품질** (중복·결측치 처리)

엔지니어링 관점에서 "데이터가 언제, 어떻게 시스템에 들어올지"가 핵심.

#### 2.1.5 데이터 변환

데이터를 **정제·표준화·통합·모델링**하는 과정.

**목표**: **분석·머신러닝·비즈니스 사용**에 적합한 형태로 가공.

**접근 방식**:

- **ETL (Extract → Transform → Load)** – 전통적인 방식, 변환 후 적재.
- **ELT (Extract → Load → Transform)** – 클라우드/분산 시스템 확산으로 인기, 적재 후 변환.

**주요 작업**:

- 스키마 조정
- 데이터 정합성 확보
- 비즈니스 로직 반영

**가장 큰 부가가치가 창출되는 단계**로, 많은 엔지니어링 리소스가 집중됨.

#### 2.1.6 데이터 서빙

최종적으로 데이터를 **소비자(분석가, 데이터 과학자, 애플리케이션, 비즈니스 시스템)**에게 전달하는 단계.

**방법**:

- **BI/대시보드** (예: Tableau, Power BI)
- **머신러닝 피드** (예: 추천 시스템, 모델 입력)
- **API/서비스 레이어** (데이터 제품 제공)

**고려할 사항**:

- **성능** (빠른 쿼리 응답)
- **데이터 품질** (정확하고 신뢰 가능해야 함)
- **보안·권한 관리**

데이터 엔지니어링 수명 주기의 **목적지**로서, 조직이 데이터로 **실질적인 가치를 얻는 순간**.

### 2.2 데이터 엔지니어링 수명 주기의 드러나지 않는 주요 요소

#### 2.2.1 보안

- 데이터가 여러 고객·팀·플랫폼 간에 공유되는 환경에서는 **멀티테넌시 보안**이 핵심.
- 잘못된 권한 관리나 데이터 유출은 단순한 내부 사고가 아니라 **신뢰 상실과 심각한 평판 피해**로 이어짐.
- 따라서 **테넌트 단위 보안, 데이터 레벨 접근 제어** 등을 반드시 구현해야 함.

#### 2.2.2 데이터 관리

- **메타데이터 관리, 데이터 카탈로그, 데이터 계보(lineage)** 등은 파이프라인의 복잡성이 커질수록 중요해짐.
- 데이터 엔지니어는 단순히 데이터를 이동시키는 것이 아니라, **데이터가 어디서 왔고, 어떻게 변환되었는지 추적**할 수 있게 만들어야 함.
- 관리 없이는 데이터 품질·신뢰성·규제 준수가 무너질 위험이 큼.

#### 2.2.3 데이터옵스

- DevOps에서 발전된 개념으로, **데이터 파이프라인과 워크플로우의 지속적 통합/배포(CI/CD)**를 지향.
- 목적: **변경 자동화, 품질 보장, 빠른 반복**.
- 파이프라인 테스트, 모니터링, 알림 시스템이 포함되며, **데이터 엔지니어링 팀의 운영 효율성**을 크게 높여줌.

#### 2.2.4 데이터 아키텍처

**시스템 간 결합도**가 핵심 주제.

- **강결합**: 단일 티어 아키텍처(앱+DB가 하나) → 장애에 취약.
- **약결합**: 멀티 티어 아키텍처(데이터·애플리케이션·프레젠테이션 계층 분리) → 유연하고 확장성 높음.

데이터 아키텍처 설계는 **유연성과 신뢰성**의 균형을 맞추는 것이 핵심.

#### 2.2.5 오케스트레이션

- 파이프라인은 점점 더 복잡해지기 때문에, **작업 간 의존성 관리와 실행 순서 제어**가 필요.
- 대표적으로 **Airflow** 같은 툴이 사용됨.
- 오케스트레이션은 단순한 스케줄링을 넘어, **데이터 흐름의 가시성, 에러 대응, 재시도, 모니터링**까지 포함.

#### 2.2.6 소프트웨어 엔지니어링

- 데이터 엔지니어링은 본질적으로 **소프트웨어 개발의 연장**.
- 따라서 버전 관리, 코드 리뷰, 테스트, 모듈화, 자동화 같은 **소프트웨어 엔지니어링 원칙**을 반드시 적용해야 함.
- 데이터 품질 문제 상당수는 **코드 품질 관리 부족**에서 기인하기 때문에, 데이터 엔지니어도 개발자와 같은 수준의 SW 역량이 요구됨.

### 2.3 결론

- 데이터 엔지니어링 수명 주기는 단순히 "데이터 이동 단계"만으로 설명할 수 없음.
- **보안, 데이터 관리, DataOps, 아키텍처, 오케스트레이션, 소프트웨어 엔지니어링**은 "언더커런트"로서 모든 단계에 영향을 주며, **없으면 전체 파이프라인이 불완전**해짐.
- 따라서 성공적인 데이터 엔지니어링은 **기술적 구현 + 운영적 거버넌스**를 동시에 달성하는 데 달려 있음.
