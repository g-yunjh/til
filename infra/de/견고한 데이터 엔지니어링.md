## CHAPTER 1 데이터 엔지니어링 상세

### 1.1 데이터 엔지니어링이란?

데이터 엔지니어링은 단순히 특정 기술을 다루는 것이 아니라, **데이터를 생성 → 저장 → 수집 → 변환 → 제공**하는 전체적인 과정과 이를 뒷받침하는 원칙을 다루는 분야다. 데이터 과학, 분석, 머신러닝이 성과를 내기 위해 필요한 **기초 인프라와 프로세스**를 구축하는 역할을 담당한다.

#### 1.1.1 데이터 엔지니어링 정의

- **정의**: 원시 데이터를 받아 **고품질·일관된 정보**로 가공해 분석과 머신러닝 같은 다운스트림 사용 사례를 지원하는 시스템과 프로세스를 설계·구현·운영하는 것.
- **핵심 교차 영역**: 보안, 데이터 관리, DataOps, 데이터 아키텍처, 오케스트레이션, 소프트웨어 엔지니어링.
- **데이터 엔지니어 역할**: 수명 주기 전반을 관리(소스에서 데이터 가져오기 → 가공 → 활용 가능하게 제공).

#### 1.1.2 데이터 엔지니어링 수명 주기

**5단계**:

1. **Generation (생성)** – 소스 시스템에서 데이터가 만들어짐.
2. **Storage (저장)** – 데이터가 보존되는 곳 (DB, 파일 시스템, 클라우드 등).
3. **Ingestion (수집)** – 저장된 데이터를 가져와 파이프라인에 넣음.
4. **Transformation (변환)** – 데이터를 정제·모델링·가공하여 목적에 맞게 준비.
5. **Serving (제공)** – 분석·머신러닝·비즈니스 시스템에 데이터 전달.

**언더커런트(공통 주제)**: 보안, 데이터 관리, DataOps, 데이터 아키텍처, 오케스트레이션, 소프트웨어 엔지니어링이 전 단계에 걸쳐 중요하다.

#### 1.1.3 데이터 엔지니어링의 진화

- **1980–2000년대 초반**: 데이터 웨어하우스, BI, ETL 개발자 등에서 출발.
- **2000년대 중반–2010년대**: 구글의 GFS·MapReduce 논문과 하둡(Hadoop) 등 오픈소스 빅데이터 기술의 등장 → "빅데이터 엔지니어" 시대.
- **2010년대 후반**: 스트리밍, 클라우드, 다양한 오픈소스·상용 도구 확산. 빅데이터라는 용어는 희석되고, 단순히 "데이터 엔지니어링"으로 통합.
- **2020년대**: 클라우드 기반, 모듈화, 관리형 서비스 중심으로 변화. "데이터 수명 주기 엔지니어"로서 **데이터 관리·보안·데이터 거버넌스**까지 담당하는 방향으로 발전.

#### 1.1.4 데이터 엔지니어링과 데이터 과학

- **관계**: 데이터 엔지니어링은 **업스트림**, 데이터 과학은 **다운스트림**.
- **데이터 과학의 현실**: 실제로는 70–80%의 시간을 데이터 수집·정제·처리에 사용.
- **핵심 메시지**: 데이터 엔지니어링이 잘 구축되어야 데이터 과학자들이 **분석·실험·ML 모델링**에 집중할 수 있다.
- **비유**: 데이터 과학을 위한 "토대(인프라)"를 다지는 것이 데이터 엔지니어링.

### 1.2 데이터 엔지니어링 기술과 활동

데이터 엔지니어는 단순히 파이프라인만 만드는 것이 아니라, **데이터 라이프사이클 전반**을 관리하며 보안, 데이터 관리, DataOps, 아키텍처, 소프트웨어 엔지니어링 등 다양한 영역을 아우르는 활동을 수행한다. 핵심은 **비즈니스 요구와 기술적 구현을 연결**하는 역할이다.

#### 1.2.1 데이터 성숙도와 데이터 엔지니어

**데이터 성숙도**: 조직이 데이터를 활용하는 능력의 성숙 단계를 의미.

**세 가지 단계**:

1. **시작(Starting with Data)** – 초기 단계, 데이터 활용 목표가 모호, 소규모 팀, 데이터 엔지니어는 **제너럴리스트**로서 다양한 역할(분석/엔지니어링 혼합) 수행.
2. **확장(Scaling with Data)** – 데이터 파이프라인·아키텍처가 정립되며, 역할이 **전문화**됨. DevOps/DataOps 도입, 확장성과 안정성이 핵심.
3. **리딩(Leading with Data)** – 데이터가 완전히 내재화된 조직. 자동화된 파이프라인, 셀프서비스 분석/ML 환경, **데이터 거버넌스·품질 관리** 강화.

**포인트**: 단계가 올라갈수록 엔지니어링의 초점이 **빠른 구현 → 확장성 → 거버넌스와 전략적 경쟁력**으로 이동한다.

#### 1.2.2 데이터 엔지니어의 배경과 기술

데이터 엔지니어의 배경은 다양함: **소프트웨어 엔지니어링, 데이터베이스, BI, 통계/분석** 등.

**요구되는 기술 스택**:

- **프로그래밍** (Python, SQL 등)
- **데이터베이스 지식** (OLTP, OLAP, NoSQL 등)
- **분산 시스템과 클라우드 인프라**
- **ETL/ELT, 데이터 파이프라인, 오케스트레이션 툴**
- **보안, 데이터 거버넌스, 데이터 관리 기법**

**특징**: 단일 기술 전문가가 아니라 **폭넓은 스킬셋을 통합적으로 운영**하는 역할.

#### 1.2.3 비즈니스 책임

데이터 엔지니어는 기술뿐 아니라 비즈니스적으로도 중요한 책임을 진다.

- **이해관계자와의 소통** – 데이터 요구를 기술적 설계로 변환.
- **경영진 설득** – 데이터 인프라 투자 가치 설명 및 ROI 확보.
- **데이터 활용 촉진** – 조직 내 데이터 리터러시 향상, 셀프서비스 환경 지원.
- **비즈니스 경쟁력 강화** – 데이터로 차별화된 제품·서비스 제공을 가능하게 함.

#### 1.2.4 기술 책임

핵심은 **데이터 라이프사이클 구현과 운영**.

- 소스에서 데이터 **획득·저장·이동·변환·제공**.
- 파이프라인과 데이터 아키텍처를 **확장 가능하고 안정적**으로 설계.
- **보안·품질 관리·거버넌스** 적용.
- 최신 기술 도입 시 **비용·효율·비즈니스 가치**를 고려해 판단.
- 운영 중 문제 해결(신뢰성·성능·스케일링 등).

#### 1.2.5 A에서 B로 이어지는 데이터 엔지니어링 역할의 연속성

데이터 엔지니어링 역할은 고정적이지 않고 **스펙트럼**을 이룬다.

- **A쪽**: 데이터 분석에 가까운 역할 (SQL 중심, 리포트·모델링 지원).
- **B쪽**: 소프트웨어 엔지니어링에 가까운 역할 (분산 시스템, 데이터 인프라 구축).

대부분의 데이터 엔지니어는 이 스펙트럼 어딘가에 위치하며, 조직의 규모·성숙도·필요에 따라 역할이 달라진다.

즉, 데이터 엔지니어링은 **"데이터 중심 소프트웨어 엔지니어링"에서 "분석 지원 전문 엔지니어링"까지 이어지는 연속적인 역할군**으로 이해할 수 있다.

### 1.3 조직 내 데이터 엔지니어

#### 1.3.1 내부 vs 외부 대면 데이터 엔지니어

**내부 대면 데이터 엔지니어 (Internal-facing)**

- 주요 "고객"은 **내부 팀** (데이터 과학자, 분석가, 제품팀 등).
- 역할: 데이터 파이프라인과 플랫폼을 구축해 **분석·실험·모델링**을 지원.
- 예: 내부 데이터 플랫폼팀, BI 데이터 엔지니어.

**외부 대면 데이터 엔지니어 (External-facing)**

- **외부 고객**을 직접 지원하는 경우.
- 예: SaaS 회사에서 고객 데이터를 처리하는 파이프라인, 데이터 제품을 직접 제공하는 팀.
- 기술뿐 아니라 **고객 요구를 충족하는 비즈니스 마인드** 필요.

#### 1.3.2 데이터 엔지니어와 기타 기술 역할

**소프트웨어 엔지니어**

- 코드·애플리케이션 개발이 중심.
- 데이터 엔지니어는 시스템 관점보다는 **데이터 흐름** 중심.

**데이터 과학자/분석가**

- 다운스트림 사용자. 데이터 엔지니어링이 없다면 대부분의 시간을 데이터 준비에 소모.
- 데이터 엔지니어는 이들의 **데이터 수요를 충족**시켜 "분석 속도"와 "가치 창출"을 높임.

**DevOps/플랫폼 엔지니어**

- 인프라 자동화, 배포, 운영 신뢰성에 집중.
- 데이터 엔지니어는 데이터 파이프라인을 구축·운영하는 과정에서 이들과 밀접하게 협업.

**요약**: 데이터 엔지니어는 **교차 역할**에 있으며, 소프트웨어·데이터 과학·운영 사이의 **중재자/연결자** 역할.

#### 1.3.3 데이터 엔지니어와 비즈니스 리더십

데이터 엔지니어는 단순히 기술자에 그치지 않고 **비즈니스 전략과 실행을 잇는 가교**.

**비즈니스 리더십과 협력**:

- 데이터 전략이 조직 목표와 일치하도록 설계.
- ROI와 비용 효율성을 고려한 인프라 제안.
- 데이터 거버넌스·품질 관리 체계를 경영진과 함께 수립.

**데이터 기반 문화** 확립에서 중요한 기여:

- 엔지니어링을 통해 데이터를 **신뢰 가능한 자산**으로 전환.
- 비즈니스 의사결정이 데이터 중심적으로 이루어지도록 지원.

### 1.4 결론

- 데이터 엔지니어링은 **분석·데이터 과학·머신러닝 성공을 가능하게 하는 토대**.
- 단순히 "데이터 파이프라인을 만드는 직무"가 아니라, **기술적 전문성** + **비즈니스 이해** + **협업 역량**을 요구하는 복합적인 역할.
- 데이터 엔지니어는 조직 내에서 **데이터 성숙도를 끌어올리고**, **내부/외부 이해관계자** 모두에게 가치를 창출.
- 결국, 데이터 엔지니어링은 "데이터를 전략적 자산으로 만드는 엔진" 역할을 수행한다.

## CHAPTER 2 데이터 엔지니어링 수명 주기

### 2.1 데이터 엔지니어링 수명 주기란?

데이터 엔지니어링은 단일 기술이 아니라, **데이터가 생성 → 저장 → 수집 → 변환 → 제공(서빙)** 되는 **연속적인 프로세스**.

이 수명 주기는 조직의 데이터 활용 수준에 관계없이 **핵심 프레임워크**로 작동.

각 단계는 독립적이면서도 상호 연결되어 있으며, 엔지니어는 전체 파이프라인 관점에서 관리해야 한다.

#### 2.1.1 데이터 수명 주기 vs 데이터 엔지니어링 수명 주기

**데이터 수명 주기(Data Lifecycle)**: 데이터가 태어나고(생성), 사용되고, 저장되다가 결국 폐기되는 **존재의 전체 과정**을 의미.

**데이터 엔지니어링 수명 주기(Data Engineering Lifecycle)**: 데이터가 **활용 가능한 자산**으로 전환되는 과정을 중점적으로 다룸.

- 즉, 단순히 보존·폐기까지 포함하는 것이 아니라 **"가치 창출"을 위한 흐름**에 초점.

두 개념은 겹치지만, 엔지니어링 수명 주기는 보다 **실용적이고 기술 중심적**.

#### 2.1.2 데이터 생성

- 데이터는 **애플리케이션, IoT 센서, 로그, 외부 API, 거래 시스템** 등 다양한 소스에서 생성.
- 중요한 점은 데이터가 **의도적으로 만들어지지 않은 경우**(예: 로그)도 많다는 것.
- 데이터 엔지니어는 **어떤 데이터가 생성되는지, 형식과 품질은 어떠한지** 이해해야 함.
- 생성 단계에서 품질·표준을 고려하지 않으면 이후 과정에서 큰 비용이 발생.

#### 2.1.3 데이터 저장

데이터가 머무는 장소.

**주요 스토리지 유형**:

- **OLTP 데이터베이스** (트랜잭션 처리 중심)
- **데이터 웨어하우스** (분석·리포팅 최적화)
- **데이터 레이크** (원시·비정형 데이터 저장)
- **NoSQL/분산 저장소** (특수 목적: 그래프, 키-값 등)

스토리지는 이후 수집과 변환의 기반이 되므로, **확장성·비용·성능·보안**의 균형을 고려해야 한다.

#### 2.1.4 데이터 수집

저장된 데이터를 **파이프라인으로 가져오는 과정**.

**수집 방식**:

- **Batch ingestion (일괄 수집)** – 정해진 주기로 데이터를 모아 처리.
- **Streaming ingestion (실시간 스트리밍)** – 이벤트 발생 즉시 전달.

**고려할 요소**:

- **지연 시간(latency)** vs **비용/복잡성**
- **데이터 품질** (중복·결측치 처리)

엔지니어링 관점에서 "데이터가 언제, 어떻게 시스템에 들어올지"가 핵심.

#### 2.1.5 데이터 변환

데이터를 **정제·표준화·통합·모델링**하는 과정.

**목표**: **분석·머신러닝·비즈니스 사용**에 적합한 형태로 가공.

**접근 방식**:

- **ETL (Extract → Transform → Load)** – 전통적인 방식, 변환 후 적재.
- **ELT (Extract → Load → Transform)** – 클라우드/분산 시스템 확산으로 인기, 적재 후 변환.

**주요 작업**:

- 스키마 조정
- 데이터 정합성 확보
- 비즈니스 로직 반영

**가장 큰 부가가치가 창출되는 단계**로, 많은 엔지니어링 리소스가 집중됨.

#### 2.1.6 데이터 서빙

최종적으로 데이터를 **소비자(분석가, 데이터 과학자, 애플리케이션, 비즈니스 시스템)**에게 전달하는 단계.

**방법**:

- **BI/대시보드** (예: Tableau, Power BI)
- **머신러닝 피드** (예: 추천 시스템, 모델 입력)
- **API/서비스 레이어** (데이터 제품 제공)

**고려할 사항**:

- **성능** (빠른 쿼리 응답)
- **데이터 품질** (정확하고 신뢰 가능해야 함)
- **보안·권한 관리**

데이터 엔지니어링 수명 주기의 **목적지**로서, 조직이 데이터로 **실질적인 가치를 얻는 순간**.

### 2.2 데이터 엔지니어링 수명 주기의 드러나지 않는 주요 요소

#### 2.2.1 보안

- 데이터가 여러 고객·팀·플랫폼 간에 공유되는 환경에서는 **멀티테넌시 보안**이 핵심.
- 잘못된 권한 관리나 데이터 유출은 단순한 내부 사고가 아니라 **신뢰 상실과 심각한 평판 피해**로 이어짐.
- 따라서 **테넌트 단위 보안, 데이터 레벨 접근 제어** 등을 반드시 구현해야 함.

#### 2.2.2 데이터 관리

- **메타데이터 관리, 데이터 카탈로그, 데이터 계보(lineage)** 등은 파이프라인의 복잡성이 커질수록 중요해짐.
- 데이터 엔지니어는 단순히 데이터를 이동시키는 것이 아니라, **데이터가 어디서 왔고, 어떻게 변환되었는지 추적**할 수 있게 만들어야 함.
- 관리 없이는 데이터 품질·신뢰성·규제 준수가 무너질 위험이 큼.

#### 2.2.3 데이터옵스

- DevOps에서 발전된 개념으로, **데이터 파이프라인과 워크플로우의 지속적 통합/배포(CI/CD)**를 지향.
- 목적: **변경 자동화, 품질 보장, 빠른 반복**.
- 파이프라인 테스트, 모니터링, 알림 시스템이 포함되며, **데이터 엔지니어링 팀의 운영 효율성**을 크게 높여줌.

#### 2.2.4 데이터 아키텍처

**시스템 간 결합도**가 핵심 주제.

- **강결합**: 단일 티어 아키텍처(앱+DB가 하나) → 장애에 취약.
- **약결합**: 멀티 티어 아키텍처(데이터·애플리케이션·프레젠테이션 계층 분리) → 유연하고 확장성 높음.

데이터 아키텍처 설계는 **유연성과 신뢰성**의 균형을 맞추는 것이 핵심.

#### 2.2.5 오케스트레이션

- 파이프라인은 점점 더 복잡해지기 때문에, **작업 간 의존성 관리와 실행 순서 제어**가 필요.
- 대표적으로 **Airflow** 같은 툴이 사용됨.
- 오케스트레이션은 단순한 스케줄링을 넘어, **데이터 흐름의 가시성, 에러 대응, 재시도, 모니터링**까지 포함.

#### 2.2.6 소프트웨어 엔지니어링

- 데이터 엔지니어링은 본질적으로 **소프트웨어 개발의 연장**.
- 따라서 버전 관리, 코드 리뷰, 테스트, 모듈화, 자동화 같은 **소프트웨어 엔지니어링 원칙**을 반드시 적용해야 함.
- 데이터 품질 문제 상당수는 **코드 품질 관리 부족**에서 기인하기 때문에, 데이터 엔지니어도 개발자와 같은 수준의 SW 역량이 요구됨.

### 2.3 결론

- 데이터 엔지니어링 수명 주기는 단순히 "데이터 이동 단계"만으로 설명할 수 없음.
- **보안, 데이터 관리, DataOps, 아키텍처, 오케스트레이션, 소프트웨어 엔지니어링**은 "언더커런트"로서 모든 단계에 영향을 주며, **없으면 전체 파이프라인이 불완전**해짐.
- 따라서 성공적인 데이터 엔지니어링은 **기술적 구현 + 운영적 거버넌스**를 동시에 달성하는 데 달려 있음.

## CHAPTER 3 우수한 아키텍처 설계

### 3.1 데이터 아키텍처란?
- 데이터 아키텍처란 데이터가 생성·저장·처리·전달되는 방식을 정의하는 구조적 설계임.  
- 이는 단순한 기술 스택의 나열이 아니라 **데이터 흐름, 책임, 표준, 정책**을 포함하는 조직적 프레임워크임.  
- 엔터프라이즈 아키텍처가 조직 전체 IT를 포괄한다면, 데이터 아키텍처는 그 중 **데이터 중심 구성요소**에 초점을 맞춘 하위 체계임.  
- 우수한 데이터 아키텍처는 **단순함, 유연함, 확장성, 복원력, 보안**의 균형을 이루는 것이 핵심임.  

### 3.2 우수한 데이터 아키텍처의 원칙

- **원칙 1: 공동 컴포넌트를 현명하게 선택하라**  
  - 공통 인프라(저장소, 오케스트레이션, 모니터링 등)는 신중히 선택해야 함.  
  - **표준화와 일관성**이 장기적 안정성을 담보하는 핵심임.  

- **원칙 2: 장애에 대비하라**  
  - 데이터 시스템은 항상 실패를 가정해야 함.  
  - **Fail gracefully** 원칙을 통해 장애 시에도 전체 중단을 피하도록 설계해야 함.  
  - 복제, 백업, 재시작, 모니터링 체계를 갖추는 것이 중요함.  

- **원칙 3: 확장성을 위한 아키텍처를 설계하라**  
  - 데이터와 트래픽 증가를 예측하고 **Scale-out/Scale-up**이 가능한 구조로 설계해야 함.  

- **원칙 4: 아키텍처는 리더십이다**  
  - 좋은 아키텍처는 단순한 기술 결정이 아니라 **팀이 따를 방향성**을 제시하는 리더십의 표현임.  
  - 아키텍트는 기술적 판단뿐 아니라 **조직적 비전**을 제시해야 함.  

- **원칙 5: 항상 아키텍처에 충실하라**  
  - 단기 편의를 위해 원칙을 위반하면 **기술 부채(technical debt)**가 누적됨.  
  - 초기 설계 철학을 지키는 것이 장기적 성공의 기반임.  

- **원칙 6: 느슨하게 결합된 시스템을 구축하라**  
  - **Loose coupling**은 시스템 독립성과 회복력을 높이는 설계 방식임.  
  - 이벤트 기반 구조를 채택하고 인터페이스를 표준화해야 함.  

- **원칙 7: 되돌릴 수 있는 의사결정을 하라**  
  - 변경 불가능한 결정은 시스템 유연성을 해침.  
  - **Reversible decision** 구조로 설계하여 실험과 롤백이 가능해야 함.  

- **원칙 8: 보안 우선순위를 지정하라**  
  - 보안은 사후 대응이 아니라 설계의 시작점임.  
  - 데이터 접근 제어, 암호화, 멀티테넌시 정책을 아키텍처 단계에서 포함해야 함.  

- **원칙 9: 피드백을 수용하라**  
  - 아키텍처는 고정된 산출물이 아니라 **지속적 개선의 과정**임.  
  - 운영 경험과 피드백을 반영하여 주기적으로 개선해야 함.  

### 3.3 주요 아키텍처 개념

- **도메인과 서비스**  
  - 시스템을 **도메인(domain)** 단위로 나누어 책임과 데이터 소유권을 명확히 하는 것이 중요함.  
  - 이는 **데이터 거버넌스와 자율성**을 확보하기 위한 기반임.  

- **분산 시스템, 확장성, 장애 대비**  
  - 현대 시스템은 본질적으로 **분산(distributed)** 환경에서 동작함.  
  - 네트워크 지연, 일관성, 장애 대응 등 분산 환경의 제약을 반드시 고려해야 함.  

- **강한 결합 vs 느슨한 결합**  
  - **Monolith** 구조는 단순하지만 장애 확산 위험이 큼.  
  - **Multitier** 구조는 계층 분리를 통해 안정성과 확장성을 확보함.  

- **사용자 접근: 싱글 vs 멀티테넌트**  
  - 멀티테넌트 환경에서는 **데이터 격리와 접근 제어**가 핵심임.  
  - 고객별 데이터 분리와 필터링 정책을 적용해야 함.  

- **이벤트 기반 아키텍처**  
  - 데이터 흐름을 이벤트 단위로 처리하는 구조임.  
  - Kafka, Kinesis 같은 메시징 큐를 사용해 **비동기성과 확장성**을 확보함.  

- **브라운필드 vs 그린필드 프로젝트**  
  - **그린필드**는 새 시스템 구축, **브라운필드**는 기존 시스템 확장임.  
  - 현실적으로 브라운필드가 많으며 점진적 전환 전략이 필요함.  

### 3.4 데이터 아키텍처의 사례와 유형

- **데이터 웨어하우스**  
  - 정형 데이터를 중심으로 분석을 수행하는 전통적 저장소임.  
  - BI 및 리포팅 중심의 환경에 적합함.  

- **데이터 레이크**  
  - 비정형 원시 데이터를 저장하는 구조임.  
  - 유연하지만 품질 및 거버넌스 관리가 어려움.  

- **통합형 데이터 플랫폼 (Lakehouse 등)**  
  - 웨어하우스와 레이크의 장점을 결합한 형태임.  
  - 단일 메타데이터 계층과 통합 쿼리 엔진을 제공함.  

- **모던 데이터 스택**  
  - 클라우드 기반 SaaS 조합으로 구성된 현대적 데이터 플랫폼임.  
  - 예: Fivetran(수집) + Snowflake(저장) + dbt(변환) + Looker(시각화) 조합임.  

- **람다 아키텍처**  
  - 배치와 스트리밍 처리를 결합한 구조임.  
  - 실시간성과 이력 데이터의 일관성을 동시에 확보함.  

- **카파 아키텍처**  
  - 모든 처리를 스트림 기반으로 수행하는 단순화된 구조임.  
  - 중복과 복잡성을 줄이고 유지보수를 용이하게 함.  

- **데이터 흐름 모델**  
  - 배치와 스트리밍 간의 균형이 중요함.  
  - 데이터 파이프라인의 실시간성과 안정성을 함께 고려해야 함.  

- **IoT용 아키텍처**  
  - 엣지 → 게이트웨이 → 클라우드로 이어지는 계층 구조임.  
  - 실시간성, 보안, 네트워크 효율성이 중요함.  

- **데이터 메시 (Data Mesh)**  
  - 중앙 집중형 구조의 한계를 보완하는 **분산형 데이터 관리 철학**임.  
  - 각 도메인 팀이 자체 데이터 제품(Data Product)을 소유하고 운영함.  
  - 자율성과 표준화를 동시에 추구하는 접근임.  

- **기타 아키텍처 예시**  
  - 그래프 DB, 하이브리드 클라우드, 지리적 복제 구조 등이 존재함.  

### 3.5 데이터 아키텍처 설계 담당자는 누구인가?
- 데이터 아키텍트, 시니어 데이터 엔지니어, 플랫폼 엔지니어가 주로 담당함.  
- 이들은 단순한 기술 설계자가 아니라 **비즈니스와 기술을 잇는 전략적 리더**임.  

### 3.6 결론
- 좋은 데이터 아키텍처는 **기술적 완성도와 조직적 현실**을 동시에 반영해야 함.  
- 복잡성을 단순화하고 **확장성·복원력·보안·자율성**을 균형 있게 유지하는 것이 핵심임.  
- 궁극적으로 데이터 아키텍처는 **조직의 데이터 철학과 리더십을 시각화한 결과물**임.  

## CHAPTER 4 데이터 엔지니어링 수명 주기 전반에 걸친 기술 선택

### 4.1 팀의 규모와 능력
- 기술 선택 시 팀의 **규모와 전문성**을 고려해야 함.  
- 소규모 팀은 학습 곡선이 낮고 관리 부담이 적은 도구를 선호하는 것이 좋음.  
- 대규모 팀은 더 복잡한 기술 스택을 유지할 수 있지만, **조정 비용**이 커짐.  
- 팀이 이미 익숙한 기술을 활용하면 **생산성과 속도**가 향상됨.  

### 4.2 시장 출시 속도 (Speed to Market)
- 완벽을 추구하다가 실행이 늦어지면 데이터 팀이 실패할 수 있음.  
- “완벽은 선의 적이다”는 교훈처럼, **빠르게 가치를 제공하는 것이 중요함**.  
- 이미 익숙한 도구를 사용하여 빠르게 가시적 성과를 내야 함.  
- **신속하고 안전하며 신뢰성 있는 배포**가 핵심 가치임.  

### 4.3 상호 운용성 (Interoperability)
- 대부분의 조직은 하나의 기술만 쓰지 않기 때문에, **도구 간 호환성**이 중요함.  
- 상호 운용성은 시스템이 **데이터를 교환하고 연동하는 능력**을 의미함.  
- JDBC, ODBC 같은 표준을 활용하면 연결성이 높아짐.  
- REST API의 경우 표준이 완벽하지 않기 때문에 **벤더나 OSS의 품질**이 중요함.  
- 시스템을 설계할 때 **모듈성(modularity)**을 고려하면, 도구 교체가 쉬워짐. 

### 4.4 비용 최적화 및 비즈니스 가치
- 기술 선택 시 **비용, 시간, 가치**의 균형을 고려해야 함.  
- 기술은 주요 비용 요인 중 하나이므로, 선택이 예산에 큰 영향을 미침.  
- 비용은 **총소유비용(TCO)**, **기회비용(TOCO)**, **FinOps**의 세 가지 관점에서 분석함.  

#### 4.4.1 총소유비용 (TCO)
- 프로젝트의 **직접비용과 간접비용**을 모두 포함함.  
- 직접비용: 팀 인건비, 클라우드 사용료 등 명확히 산정 가능한 비용임.  
- 간접비용: 인프라 유지, 관리, 교육 등의 **오버헤드**임.  
- 자본적 지출(CAPEX)과 운영비용(OPEX)의 구분도 중요함. 

#### 4.4.2 총기회비용 (TOCO)
- 새로운 기술 도입으로 인해 **다른 기회를 놓치는 비용**을 의미함.  
- 기술 선택은 단순한 구매 결정이 아니라 **전략적 투자 결정**임.  

#### 4.4.3 팬옵스 (FinOps)
- FinOps는 **클라우드 비용을 관리하고 최적화하는 운영 문화**임.  
- 데이터 팀과 재무팀이 협업하여 클라우드 사용의 **ROI를 극대화**해야 함.  

### 4.5 현재 vs 미래: 불변의 기술과 일시적 기술
- 어떤 기술은 장기적으로 **불변의 가치**를 가지며, 어떤 것은 **일시적 트렌드**임.  
- 예를 들어 SQL, Python, 데이터 모델링 원칙 등은 **불변 기술**에 속함.  
- 반면 특정 SaaS 도구나 프레임워크는 **단기적 유행**일 가능성이 높음.  
- 기술 선택 시 “**시간의 시험을 견딜 것인가?**”를 기준으로 평가해야 함.  

### 4.6 장소: 온프레미스, 클라우드, 하이브리드, 멀티클라우드

#### 4.6.1 온프레미스
- 자체 인프라를 관리하는 방식으로, **보안성과 통제력**이 높음.  
- 초기 구축 비용이 크고, 확장성은 제한적임. 

#### 4.6.2 클라우드
- 유연성과 확장성이 높고, **초기 투자 부담이 적음**.  
- AWS, Azure, GCP 등에서 다양한 데이터 서비스 제공함.

#### 4.6.3 하이브리드 클라우드
- 온프레미스와 클라우드를 **병행**하여 운영함.  
- 보안·성능·비용 간의 균형을 유지할 수 있음.  

#### 4.6.4 멀티클라우드
- 여러 클라우드 벤더를 병행하여 **리스크 분산**을 꾀함.  
- 관리 복잡성이 커지지만, **종속성(lock-in)**을 줄일 수 있음. 

#### 4.6.5 탈중앙화: 블록체인과 엣지
- 블록체인과 엣지 컴퓨팅은 **데이터 분산 처리**의 새로운 패러다임임.  
- 데이터 소유권, 보안성, 지연 시간 감소 측면에서 중요함.  

#### 4.6.6 조언
- 모든 워크로드가 클라우드에 적합한 것은 아님.  
- 워크로드 특성에 따라 **적절한 위치 전략**을 수립해야 함.  

#### 4.6.7 클라우드 순환형 논쟁
- 일부 조직은 비용 절감을 위해 클라우드에서 다시 온프레미스로 이전함.  
- 이를 “**클라우드 리패트리에이션(cloud repatriation)**”이라 부름.  
- 하지만 대부분의 경우, 클라우드는 여전히 **민첩성과 유연성** 면에서 우세함. 

### 4.7 구축과 구매 비교 (Build vs Buy)
- 자체 구축은 맞춤형 통제력을 주지만, 유지보수 부담이 큼.  
- 구매는 빠른 도입이 가능하지만, **비용과 벤더 종속성**이 발생함.  

#### 4.7.1 오픈 소스 소프트웨어
- 비용 효율적이고 커스터마이징 가능함.  
- 다만 유지보수와 커뮤니티 의존도가 높음.  

#### 4.7.2 전용 폐쇄형 네트워크 서비스
- 안정적이지만 **유연성이 낮고**, 벤더 락인 위험이 큼.  

#### 4.7.3 조언
- 핵심 역량(Core competency)에 집중하고, 비핵심 영역은 구매하는 것이 현명함.  

### 4.8 모놀리식과 모듈식 비교
- **모놀리스(monolith)**는 단일 시스템으로 관리가 단순하지만, 확장성에 한계가 있음.  
- **모듈식(modular)** 아키텍처는 각 기능이 분리되어 유연성과 확장성이 높음.  
- 잘못된 분산 설계는 “**분산형 모놀리스(Distributed Monolith)**”라는 문제를 유발할 수 있음.  
- 시스템 복잡도와 운영 효율성 사이의 균형이 중요함.  

### 4.9 서버리스와 서버 비교
- **서버리스(serverless)**는 인프라 관리 없이 코드를 실행할 수 있어 민첩함.  
- **컨테이너(container)**는 서버리스보다 제어력이 높지만, 관리가 필요함.  
- 서버리스는 초기 실험 단계나 이벤트 기반 워크로드에 적합함.  
- 평가 시 **비용, 확장성, 운영 부담**을 기준으로 비교해야 함.  

### 4.10 최적화, 성능, 벤치마크 전쟁
- 단순한 벤치마크 수치 비교는 종종 **무의미함**.  
- 벤더는 자신에게 유리한 환경에서 테스트하기 때문임.  
- 최적화는 항상 **맥락(context)**과 **비즈니스 목표** 안에서 평가해야 함.  
- “**매수자 위험 부담 원칙**”에 따라, 도입 전 직접 검증하는 것이 중요함.  

### 4.11 데이터 엔지니어링 수명 주기의 드러나지 않는 요소
- 데이터 엔지니어링에는 잘 드러나지 않는 기반 요소들이 있음:  
  - **데이터 관리(Data Management)**: 품질, 거버넌스, 메타데이터 관리임.  
  - **데이터옵스(DataOps)**: 개발과 운영의 자동화 및 협업을 의미함.  
  - **데이터 아키텍처**: 설계 원칙과 기술 스택을 정의함.  
  - **오케스트레이션(Airflow 등)**: 파이프라인의 자동화와 스케줄링임.  
  - **소프트웨어 엔지니어링**: 테스트, 배포, 모듈화, CI/CD 문화가 포함됨.  

### 4.12 결론
- 기술 선택은 단순한 **도구 선택이 아니라 전략적 결정**임.  
- 조직의 규모, 기술력, 비용, 미래 방향성을 모두 고려해야 함.  
- 완벽한 해답은 없으며, **조직 맥락에 맞는 균형 잡힌 선택**이 가장 중요함.  

## CHAPTER 5 1단계: 원천 시스템에서의 데이터 생성

### 5.1 데이터 원천: 데이터는 어떻게 생성될까?
- 데이터는 **사람, 기계, 프로세스, 센서** 등 다양한 경로를 통해 생성됨.  
- 데이터 생성의 주체는 **거래 시스템, 로그, IoT, API, 서드파티 서비스** 등임.  
- 데이터 엔지니어는 데이터가 처음 만들어지는 지점을 이해해야 **품질과 계보(lineage)**를 보장할 수 있음.  
- 원천 데이터의 생성 패턴을 파악하면 이후 단계(수집·처리)의 복잡도를 줄일 수 있음.  

### 5.2 원천 시스템: 주요 아이디어
- 원천 시스템(Source System)은 데이터를 처음으로 저장하는 시스템임.  
- 데이터 엔지니어는 **이 시스템의 구조, 갱신 주기, 일관성 모델**을 이해해야 함.  
- 일반적으로 다음과 같은 주요 데이터 소스 유형이 존재함.  

#### 5.2.1 파일과 비정형 데이터
- 텍스트, 이미지, 오디오, 동영상 등 **구조가 명확하지 않은 데이터**를 의미함.  
- 비정형 데이터는 분석을 위해 전처리와 메타데이터 관리가 필수적임.  
- CSV, JSON, Parquet 등은 반정형 데이터로서 데이터 처리 효율성을 높임.  

#### 5.2.2 API
- 외부 서비스나 시스템과 데이터를 교환하기 위한 **표준화된 인터페이스**임.  
- REST, GraphQL, gRPC 등의 형태가 있으며, 요청-응답 패턴을 가짐.  
- API는 **데이터 동기화 및 자동화 파이프라인**의 핵심 역할을 함.  

#### 5.2.3 애플리케이션 데이터베이스(OLTP 시스템)
- 온라인 트랜잭션 처리 시스템으로, **운영 데이터의 핵심 저장소**임.  
- 고객 거래, 주문, 결제 등 비즈니스 이벤트가 발생할 때마다 데이터가 기록됨.  
- 데이터 모델은 **정규화(normalization)**되어 있으며, 쓰기 성능이 중시됨.  

#### 5.2.4 온라인 분석 처리 시스템 (OLAP)
- 분석과 의사결정을 위한 **요약·집계 중심 시스템**임.  
- OLTP와 달리 **복잡한 쿼리와 집계 연산**에 최적화되어 있음.  

#### 5.2.5 변경 데이터 캡처 (CDC)
- 원천 시스템의 데이터 변경 사항을 **실시간 또는 배치로 포착**하는 기술임.  
- 로그 기반 CDC, 트리거 기반 CDC 등 다양한 방식이 존재함.  
- CDC는 **ETL/ELT 파이프라인 자동화**에 핵심적인 역할을 함.  

#### 5.2.6 로그
- 시스템, 애플리케이션, 서버의 동작 이력을 기록하는 데이터임.  
- 로그는 **이벤트 중심(event-driven)** 데이터의 주요 원천임.  
- 예: 웹 서버 로그, 애플리케이션 에러 로그, 사용자 행동 로그 등.  

#### 5.2.7 데이터베이스 로그
- 트랜잭션의 변경 내역을 기록하는 **내부 시스템 로그**임.  
- 복제, 복구, 감사(audit) 등에서 활용됨.  

#### 5.2.8 CRUD
- 데이터 조작의 기본 연산으로 **Create, Read, Update, Delete**를 의미함.  
- 원천 시스템의 대부분 데이터 흐름은 CRUD 이벤트로 구성됨.  

#### 5.2.9 입력 전용 (Append-only)
- 기존 데이터를 수정하지 않고, 새로운 데이터만 추가하는 형태임.  
- 데이터의 **불변성(immutability)**을 보장하여 추적성과 감사 기능을 강화함.  

#### 5.2.10 메시지와 스트림
- Kafka, Kinesis 같은 **메시징·스트리밍 플랫폼**에서 발생하는 데이터임.  
- 데이터는 이벤트 단위로 전달되며, **실시간 처리**에 적합함.  
- 스트리밍 데이터는 **시간 순서**를 유지하는 것이 중요함.  

#### 5.2.11 시간 유형
- 데이터 생성 시점에는 세 가지 주요 시간 개념이 있음.  
  - **이벤트 발생 시간(event time)**  
  - **처리 시간(processing time)**  
  - **수집 시간(ingest time)**  
- 스트리밍 파이프라인에서는 이 시간 차이를 이해하는 것이 핵심임.  

### 5.3 추천 시스템의 실질적인 세부 사항
- 다양한 원천 데이터를 결합하여 **추천 알고리즘에 필요한 입력**을 구성함.  
- 주요 데이터 소스는 다음과 같음.  
  - **데이터베이스:** 사용자 행동, 상품 정보 등 핵심 데이터 저장소임.  
  - **API:** 외부 데이터(예: 소셜 네트워크, 광고 데이터) 수집에 활용됨.  
  - **데이터 공유:** 협력사 또는 외부 기관과의 데이터 교환 구조임.  
  - **서드파티 데이터 원천:** 상업 데이터나 외부 인텔리전스 제공자임.  
  - **메시지 큐/스트리밍 플랫폼:** 실시간 이벤트를 수집·분석함.  
- 추천 시스템은 이러한 다양한 데이터 원천을 통합하여 **피드백 루프를 형성**함.  

### 5.4 함께 작업할 대상
- 원천 시스템 설계 및 연동에는 여러 이해관계자가 참여함.  
- 주요 협업 대상은 다음과 같음.  
  - **소프트웨어 엔지니어:** 데이터 생성 로직 및 트랜잭션 설계 담당임.  
  - **시스템 관리자:** 로그, 인프라, 보안 구성 관리함.  
  - **데이터 분석가 및 데이터 과학자:** 원천 데이터 품질 피드백 제공함.  
  - **비즈니스 팀:** 어떤 데이터가 필요한지 정의함.  

### 5.5 드러나지 않는 요소가 원천 시스템에 미치는 영향
- 원천 시스템은 다음과 같은 비가시적 요소의 영향을 받음.  

#### 5.5.1 보안
- 인증, 권한, 암호화 등 **데이터 보호 메커니즘**이 필수임.  
- 개인식별정보(PII)는 수집 단계부터 보호해야 함.  

#### 5.5.2 데이터 관리
- 메타데이터, 카탈로그, 품질 관리가 **원천 단계부터** 적용되어야 함.  

#### 5.5.3 데이터옵스
- 원천 시스템의 **배포, 모니터링, 테스트 자동화**를 위한 접근 방식임.  

#### 5.5.4 데이터 아키텍처
- 데이터 구조, 포맷, 스키마가 전체 파이프라인 설계에 영향을 줌.  

#### 5.5.5 오케스트레이션
- Airflow, Prefect 등을 통해 **데이터 수집 작업의 실행 순서와 의존성**을 관리함.  

#### 5.5.6 소프트웨어 엔지니어링
- 버전 관리, 코드 리뷰, 테스트 문화가 데이터 수집 품질을 결정함.  

### 5.6 결론
- 데이터 생성 단계는 **데이터 엔지니어링 수명 주기의 시작점**임.  
- 원천 시스템을 올바르게 이해하면 **데이터 품질, 신뢰성, 효율성**이 향상됨.  
- 데이터 파이프라인의 성공은 **입력 데이터의 정확성과 구조화 수준**에 달려 있음.  

## CHAPTER 6 2단계: 데이터 저장

### 6.1 데이터 스토리지의 기본 구성 요소
- 데이터 저장은 단순히 데이터를 “넣는 공간”이 아니라,  
  **속도, 비용, 내구성, 접근성의 균형을 설계하는 과정**임.  
- 이 장에서는 저장소의 물리적 계층부터 분산 저장 시스템의 논리적 계층까지 다룸.  

#### 6.1.1 자기 디스크 드라이브 (HDD)
- 회전 플래터를 사용해 데이터를 저장하는 전통적인 방식임.  
- 장점:
  - **저비용, 대용량** 저장이 가능함.  
  - 장기 보관용(콜드 데이터)에 적합함.  
- 단점:
  - **기계적 지연(latency)**이 크며, 읽기/쓰기 속도가 느림.  
  - 장애율이 SSD보다 높음.  
- 데이터 레이크나 백업 시스템에서는 여전히 많이 사용됨.  

#### 6.1.2 SSD (Solid State Drive)
- 전자식 저장 매체로, 플래시 메모리를 사용함.  
- 장점:
  - HDD 대비 **IOPS(초당 입출력)**가 매우 높음.  
  - 랜덤 액세스가 빠르고, 안정적임.  
- 단점:
  - 단가가 비싸고, **쓰기 수명 제한**이 있음.  
- 트랜잭션 처리 시스템이나 OLTP 데이터베이스에서 주로 사용됨.  

#### 6.1.3 읽기 전용 메모리 (RAM)
- 휘발성 저장 매체로, 프로그램 실행 중 데이터를 **임시 보관**하는 용도임.  
- 캐시, 세션 데이터, 버퍼링 등 고속 접근이 필요한 영역에서 사용됨.  
- 정전이나 재시작 시 데이터가 손실되므로 **지속성 보장용**으로는 부적합함.  

#### 6.1.4 네트워크와 CPU
- 분산 환경에서 저장소 성능은 단순히 디스크 속도뿐 아니라 **네트워크 처리량**과 **CPU 성능**에도 좌우됨.  
- 특히 클라우드 환경에서는 **I/O 병목**이 저장 병목보다 먼저 발생하는 경우가 많음.  
- 따라서 네트워크 토폴로지(예: 리전 간 레이턴시)도 고려 대상임.  

#### 6.1.5 직렬화 (Serialization)
- 데이터를 전송하거나 저장하기 위해 **바이트 스트림 형태로 변환하는 과정**임.  
- JSON, Avro, Protobuf, Parquet 등이 대표적인 포맷임.  
- 좋은 직렬화 형식을 선택하면:
  - 네트워크 전송 효율이 증가하고  
  - 언어 간 상호운용성이 향상됨.  
- 반대로, 비효율적 직렬화는 CPU 부담과 전송량을 증가시킴.  

#### 6.1.6 압축 (Compression)
- 저장 공간 절감과 전송 속도 향상을 위해 데이터를 압축함.  
- 대표 알고리즘:
  - **LZ4**: 빠른 압축/해제 속도  
  - **Snappy**: 구글이 개발한 실시간용 압축  
  - **ZSTD**: 고효율 압축 (데이터 레이크에 자주 사용됨)  
- 압축률과 처리 속도의 균형이 중요함.  

#### 6.1.7 캐싱 (Caching)
- 자주 사용되는 데이터를 **더 빠른 저장소에 임시 보관**하여 성능을 높임.  
- 캐싱 계층 구조 예:
  - CPU 캐시 → RAM → SSD → HDD → 원격 객체 스토리지  
- Redis, Memcached, CloudFront 등은 대표적 캐시 기술임.  
- 캐시는 데이터의 **지역성(locality)** 개념을 활용함.  

### 6.2 데이터 스토리지 시스템
- 데이터 스토리지는 단순히 물리 매체가 아니라,  
  **데이터 분산, 복제, 정합성 관리**를 담당하는 핵심 인프라 계층임.  

#### 6.2.1 단일 머신 vs 분산 스토리지
- **단일 머신:**  
  - 관리가 단순하고 비용이 낮지만, **확장성 한계**가 있음.  
  - 예: 로컬 MySQL, SQLite.  
- **분산 스토리지:**  
  - 데이터를 여러 노드에 분산 저장하여 장애 복구, 병렬 처리 가능함.  
  - 예: HDFS, Ceph, Cassandra, Amazon S3.  
  - 노드 간 **일관성 모델**이 핵심 설계 요소임.  

#### 6.2.2 최종 일관성 vs 강력한 일관성
- **강력한 일관성(Strong Consistency)**: 모든 노드가 즉시 동일한 데이터를 가짐.  
  - 예: RDBMS, Google Spanner.  
- **최종 일관성(Eventual Consistency)**: 시간이 지나면 데이터가 동기화됨.  
  - 예: DynamoDB, Cassandra, S3.  
- CAP 정리:
  - **C(Consistency)**, **A(Availability)**, **P(Partition tolerance)** 중 2가지만 선택 가능함.  
  - 대부분의 분산 스토리지는 **AP 또는 CP** 모델을 채택함.  

#### 6.2.3 파일 스토리지
- 데이터를 파일 단위로 저장하고, 디렉터리 구조로 관리함.  
- NAS(Network Attached Storage)가 대표적임.  
- 파일 시스템은 계층적 구조로, **접근 제어(ACL)**와 **잠금(Locking)** 메커니즘을 제공함.  

#### 6.2.4 블록 스토리지
- 데이터를 고정 크기의 블록으로 관리함.  
- 파일 시스템보다 **저수준의 저장 단위**를 제공함.  
- 고성능 DB, VM, 트랜잭션 시스템에 적합함.  
- AWS EBS, GCP Persistent Disk가 대표적임.  

#### 6.2.5 객체 스토리지
- 데이터를 **객체(Object)** 단위로 관리하고, 각 객체는 고유한 ID를 가짐.  
- 장점:
  - **확장성, 내구성, 비용 효율성**이 뛰어남.  
  - RESTful API를 통해 쉽게 접근 가능함.  
- 단점:
  - 지연(latency)이 크고, 파일 시스템처럼 디렉터리 계층이 없음.  
- 대표 시스템: AWS S3, Azure Blob, GCS.  

#### 6.2.6 캐시 및 메모리 기반 스토리지
- 초저지연 데이터를 위한 스토리지로 Redis, Memcached, Hazelcast 등이 있음.  
- 휘발성이기 때문에 주로 **세션, 임시 계산, 큐**에 사용됨.  

#### 6.2.7 하둡 분산 파일 시스템 (HDFS)
- 오픈소스 분산 스토리지 시스템으로, **대용량 데이터 처리**에 최적화됨.  
- 데이터는 블록 단위로 여러 노드에 복제되어 저장됨.  
- **NameNode**가 메타데이터를 관리하고, **DataNode**가 실제 데이터를 저장함.  

#### 6.2.8 스트리밍 스토리지
- Kafka, Pulsar, Kinesis 등은 **스트림 로그 저장소**로 동작함.  
- 메시지는 주로 “토픽 단위”로 관리되며, 재처리나 리플레이가 가능함.  
- 스트리밍 저장소는 데이터 파이프라인의 **버퍼 역할**을 수행함.  

#### 6.2.9 인덱스, 파티셔닝 및 클러스터링
- **인덱스:** 검색 속도 향상을 위한 데이터 구조(B-tree, Bitmap 등).  
- **파티셔닝:** 대량 데이터를 물리적으로 분리하여 병렬 처리 향상.  
- **클러스터링:** 관련 데이터를 물리적으로 인접하게 배치함.  
- 예: PostgreSQL의 파티션 테이블, Snowflake의 마이크로파티션 구조.  

### 6.3 데이터 엔지니어링 스토리지 개요
- 저장소 선택은 데이터 파이프라인의 **성능, 비용, 복잡도**를 좌우함.  
- 데이터의 특성과 접근 패턴에 따라 스토리지를 구분해야 함.  

#### 6.3.1 데이터 웨어하우스
- 구조화된 데이터 분석을 위한 중앙 저장소임.  
- ETL을 통해 정제된 데이터만 저장됨.  
- 대표 시스템: **Snowflake, BigQuery, Redshift**.  
- 특징:
  - 컬럼 지향 저장(Columnar storage).  
  - 고성능 SQL 분석 지원.  
  - 스케일 아웃이 용이함.  

#### 6.3.2 데이터 레이크
- 원시 데이터(raw data)를 그대로 저장하는 저장소임.  
- 반정형·비정형 데이터를 모두 수용함.  
- S3, Azure Data Lake Storage 등이 대표적임.  
- 장점: 유연성, 확장성.  
- 단점: 데이터 거버넌스와 품질 관리 어려움 (“데이터 늪” 위험).  

#### 6.3.3 데이터 레이크하우스
- 웨어하우스와 레이크의 장점을 결합한 모델임.  
- Delta Lake, Apache Iceberg, Apache Hudi가 대표적임.  
- ACID 보장, 메타데이터 관리, 스키마 진화 등을 지원함.  

#### 6.3.4 데이터 플랫폼
- 조직 내 여러 스토리지를 통합 관리하는 **거버넌스 중심 프레임워크**임.  
- 권한, 메타데이터, 품질, 접근을 일원화함.  

#### 6.3.5 Stream-to-Batch 스토리지 아키텍처
- 실시간 스트림 데이터를 배치 분석 시스템으로 전송하는 구조임.  
- Kafka → S3 → Snowflake와 같은 **다단계 저장 경로**가 대표적임.  

### 6.4 스토리지의 주요 아이디어와 통합

#### 6.4.1 데이터 카탈로그
- 저장된 데이터의 **메타데이터, 출처, 품질 상태**를 관리하는 시스템임.  
- 대표 도구: AWS Glue, DataHub, Amundsen.  

#### 6.4.2 데이터 공유
- 조직 간 혹은 팀 간 데이터 교환을 위한 **통합 접근 구조**임.  
- 예: Snowflake Data Sharing, Delta Sharing.  

#### 6.4.3 스키마
- 스키마는 데이터의 구조를 정의하며, 스키마 진화(schema evolution)는 필수 과제임.  
- 스키마 관리 실패는 파이프라인 장애로 이어짐.  

#### 6.4.4 컴퓨팅과 스토리지의 분리
- 현대적 클라우드 아키텍처는 **Compute(쿼리)**와 **Storage(저장)**를 분리함.  
- 예: BigQuery, Snowflake.  
- 이를 통해 비용 절감 및 확장성 확보 가능함.  

#### 6.4.5 데이터 수명 주기 및 보존 정책
- 데이터는 생성 → 사용 → 보관 → 삭제의 수명 주기를 가짐.  
- 보존 정책(retention policy)은 규제(GDPR, HIPAA)에 따라 결정됨.  

#### 6.4.6 싱글테넌트 vs 멀티테넌트
- 싱글테넌트:
  - 독립된 데이터베이스 사용. 보안성 높음.  
- 멀티테넌트:
  - 공유 데이터베이스 사용. 효율적이지만 격리 관리 필요함.  

### 6.5 함께 작업할 대상
- 스토리지 설계와 운영은 여러 팀의 협업이 필수임.  
  - **DevOps 팀:** 인프라 배포 및 모니터링 관리.  
  - **보안 팀:** 접근 통제, 암호화 정책 설정.  
  - **데이터 아키텍트:** 시스템 간 일관성 설계 및 성능 최적화.  
  - **플랫폼 엔지니어:** 클라우드 비용 및 자동화 관리.  

### 6.6 드러나지 않는 요소

#### 6.6.1 보안
- 데이터 암호화, 접근 제어, 감사 로그가 필수임.  
- 보안은 데이터 공유의 **전제 조건**임.  

#### 6.6.2 데이터 관리
- 메타데이터, 카탈로그, 품질 관리가 스토리지 계층에 통합되어야 함.  

#### 6.6.3 데이터옵스
- 데이터 스토리지의 자동화, 테스트, 배포, 모니터링 문화를 포함함.  

#### 6.6.4 데이터 아키텍처
- 저장 구조 설계는 아키텍처 결정(분산/중앙화)과 직결됨.  

#### 6.6.5 오케스트레이션
- Airflow, Dagster 등으로 스토리지 간 데이터 이동 및 파이프라인을 조정함.  

#### 6.6.6 소프트웨어 엔지니어링
- IaC(Terraform, Pulumi 등)을 통해 스토리지 환경을 코드로 정의하고 관리함.  

### 6.7 결론
- 데이터 저장은 **데이터 엔지니어링의 토대**임.  
- 스토리지 선택은 데이터의 **비용, 속도, 안정성, 접근성**을 결정함.  
- 궁극적으로 좋은 스토리지 설계란 **올바른 데이터를 올바른 곳에, 올바른 방식으로 저장하는 것**임.

## CHAPTER 7 3단계: 데이터 수집

### 7.1 데이터 수집이란?
- 데이터 수집(Data Ingestion)은 원천 시스템으로부터 데이터를 가져와 **저장 또는 처리 시스템으로 전달하는 단계**임.  
- 이는 데이터 엔지니어링 수명 주기의 “입구” 역할을 함.  
- 수집 단계에서 중요한 것은 **지연(latency), 신뢰성(reliability), 처리량(throughput)**의 균형임.  
- 수집 방식은 데이터의 생성 형태(배치 또는 스트림), 크기, 주기, 인프라 구조에 따라 달라짐.  
- 효율적인 수집은 이후의 변환·저장·분석 과정의 품질을 결정짓는 핵심임.  

### 7.2 수집 단계의 주요 엔지니어링 고려 사항
- 데이터 수집 단계는 **속도와 정확성의 균형**을 설계하는 과정임.  
- 데이터의 특성과 시스템의 제약 조건에 따라 다양한 패턴과 트레이드오프가 존재함.  

#### 7.2.1 유한 데이터 vs 무한 데이터
- **유한 데이터(finite data):** 고정된 크기 또는 기간을 가지는 데이터셋임. 예: 매일 생성되는 매출 리포트.  
- **무한 데이터(infinite data):** 지속적으로 생성되는 스트리밍 데이터임. 예: 센서 로그, 클릭 이벤트.  
- 무한 데이터는 끝이 없기 때문에 **시간 창(windowing)** 기반 처리나 **오프셋 추적**이 필요함.  

#### 7.2.2 빈도
- 데이터 수집의 빈도는 시스템 부하, 비용, 신선도를 결정함.  
- 일반적으로 다음 세 가지로 구분됨:  
  - 실시간(real-time): 즉시 수집 (Kafka, Kinesis 등)  
  - 미니배치(micro-batch): 짧은 주기(분 단위)로 수집  
  - 배치(batch): 하루 혹은 주 단위 수집  

#### 7.2.3 동기 수집 vs 비동기 수집
- **동기 수집(synchronous):** 요청 후 응답을 기다리는 형태로, 단순하지만 지연이 큼.  
- **비동기 수집(asynchronous):** 이벤트 기반으로 데이터를 비동기적으로 전송함.  
- 실시간 파이프라인에서는 주로 비동기 방식을 사용함.  

#### 7.2.4 직렬화와 역직렬화
- 데이터 전송 시 직렬화(Serialization), 수신 시 역직렬화(Deserialization)가 수행됨.  
- 형식이 다르면 호환성 문제가 발생하므로, **스키마 버전 관리**가 중요함.  
- Avro, Protobuf, JSON, Parquet 등은 일반적인 직렬화 포맷임.  

#### 7.2.5 처리량과 확장
- 수집 파이프라인은 트래픽 증가에 따라 **수평 확장성**을 가져야 함.  
- 메시지 큐를 활용하거나 **파티셔닝(partitioning)**을 통해 부하를 분산함.  

#### 7.2.6 신뢰성과 내구성
- 데이터 손실을 막기 위해 **acknowledgment 메커니즘**과 **재시도 로직**을 설계함.  
- 저장 시에는 **내구성(durability)** 확보를 위해 복제 또는 로그 기반 저장을 사용함.  

#### 7.2.7 페이로드
- 페이로드는 한 번의 전송에서 포함되는 데이터 크기를 의미함.  
- 너무 크면 지연이 커지고, 너무 작으면 오버헤드가 증가함.  

#### 7.2.8 푸시 vs 풀 vs 폴링 패턴
- **푸시(push):** 원천 시스템이 수집 시스템에 데이터를 전달함. (예: 웹훅)  
- **풀(pull):** 수집 시스템이 주기적으로 데이터를 요청함. (예: API 호출)  
- **폴링(polling):** 특정 이벤트 발생 여부를 주기적으로 확인함.  
- 각 방식은 **제어권, 실시간성, 비용**의 균형에 따라 선택됨.  

### 7.3 배치 수집 고려 사항
- 배치 수집은 가장 전통적이며 안정적인 데이터 수집 방식임.  
- 주로 ETL 파이프라인, 백업, 로그 집계 등에 활용됨.  

#### 7.3.1 스냅샷 또는 차등 추출
- **스냅샷(snapshot):** 전체 데이터를 주기적으로 복제함.  
- **차등 추출(delta extract):** 변경된 부분만 추출함.  
- 후자는 네트워크 비용과 처리 시간을 줄일 수 있음.  

#### 7.3.2 파일 기반 익스포트 및 수집
- CSV, JSON, Parquet 등의 파일로 데이터를 내보내고, 스토리지(S3, GCS)에 적재함.  
- 단순하고 안정적이지만, 실시간성은 떨어짐.  

#### 7.3.3 ETL
- Extract → Transform → Load 순으로 데이터를 가공하여 웨어하우스에 저장함.  
- 데이터 품질과 일관성 확보에 강점이 있음.  
- 최근에는 ELT(Load 후 Transform) 방식이 대체 추세임.  

#### 7.3.4 입력, 갱신 및 배치 크기
- 배치 크기를 잘못 설정하면 처리 지연 또는 리소스 낭비가 발생함.  
- 데이터 특성(예: 로그 vs 트랜잭션)에 따라 최적 크기를 조정해야 함.  

#### 7.3.5 데이터 마이그레이션
- 기존 시스템에서 새로운 저장소로 데이터를 이동하는 과정임.  
- 대규모 마이그레이션 시에는 **병렬 전송, 무중단 전략, 무결성 검증**이 필요함.  

### 7.4 메시지 및 스트림 수집에 관한 고려 사항
- 스트리밍 수집은 실시간으로 들어오는 데이터를 지속적으로 처리하는 과정임.  
- 이 단계에서는 **순서, 중복, 시간 관리**가 매우 중요함.  

#### 7.4.1 스키마의 진화
- 스트림 데이터는 스키마가 자주 변경됨.  
- Schema Registry(예: Confluent Schema Registry)를 사용해 버전 관리함.  

#### 7.4.2 늦게 도착하는 데이터
- 이벤트 발생 시간(event time)보다 늦게 도착하는 데이터를 고려해야 함.  
- 윈도우 기반 처리에서는 늦은 데이터 허용 시간(lateness)을 설정함.  

#### 7.4.3 주문 및 복수 전달
- 네트워크 지연으로 이벤트 순서가 뒤바뀌거나 중복될 수 있음.  
- “Exactly-once”, “At-least-once” 전달 보장을 위한 설계가 필요함.  

#### 7.4.4 재처리
- 데이터 오류나 코드 수정 시 스트림 데이터를 다시 처리해야 함.  
- 재처리 가능한 로그 기반 저장 구조(Kafka, Pulsar)가 유용함.  

#### 7.4.5 유효 시간
- 데이터의 유효 시간(Time-to-Live, TTL)을 설정해 불필요한 데이터 누적을 방지함.  

#### 7.4.6 메시지 크기
- 메시지가 너무 크면 소비자가 병목 현상을 겪을 수 있음.  
- 큰 데이터는 메시지 큐에 메타데이터만 보내고, 본문은 객체 스토리지에 저장하는 패턴을 사용함.  

#### 7.4.7 에러 처리와 데드레터 큐
- 처리 실패 시 데이터를 **데드레터 큐(Dead Letter Queue, DLQ)**에 보내 재처리함.  
- DLQ는 장애 복구 및 디버깅에 필수임.  

#### 7.4.8 소비자를 볼 앤 무시
- 소비자가 데이터를 처리하지 않고 무시할 수도 있으므로 **소비자 그룹 관리**가 중요함.  
- 메시지 오프셋(offset)을 잘못 관리하면 중복 또는 누락이 발생함.  

#### 7.4.9 위치
- 메시지의 “위치(offset)”는 데이터 재처리와 장애 복구의 기준임.  
- Kafka 등은 커밋(commit) 단위로 오프셋을 추적함.  

### 7.5 데이터 수집 방법
- 수집 기술은 다양하며, 데이터 유형과 인프라 상황에 따라 달라짐.  

#### 7.5.1 직접 데이터베이스 연결
- JDBC, ODBC를 통해 DB에 직접 접근함.  
- 빠르지만 보안 및 부하 문제가 발생할 수 있음.  

#### 7.5.2 변경 데이터 캡처 (CDC)
- DB의 변경 로그를 읽어 실시간으로 변화 데이터를 반영함.  
- Debezium, Maxwell 등 오픈소스 도구가 대표적임.  

#### 7.5.3 API
- REST/GraphQL API를 주기적으로 호출하여 데이터를 수집함.  
- 서드파티 연동, SaaS 통합에 자주 사용됨.  

#### 7.5.4 메시지 큐와 이벤트 스트리밍 플랫폼
- Kafka, Pulsar, Kinesis 등을 사용하여 **실시간 이벤트 스트림**을 수집함.  

#### 7.5.5 관리형 데이터 커넥터
- Fivetran, Airbyte, Stitch 등은 관리형 ETL/ELT 커넥터를 제공함.  
- 개발 없이도 수백 개의 데이터 소스를 연결할 수 있음.  

#### 7.5.6 객체 스토리지로 데이터 이동
- S3, GCS 등으로 데이터를 덤프(dump)하여 저장하는 패턴임.  
- 데이터 파이프라인의 중간 버퍼로 활용 가능함.  

#### 7.5.7 EDI (Electronic Data Interchange)
- 기업 간 거래 데이터를 표준 형식으로 주고받는 시스템임.  
- 금융, 물류 등에서 여전히 사용됨.  

#### 7.5.8 데이터베이스와 파일 익스포트
- RDB의 데이터를 CSV 등으로 내보내고, 수동 또는 자동으로 업로드함.  
- 레거시 시스템과의 통합에서 자주 사용됨.  

#### 7.5.9 공통 파일 형식의 실질적 문제
- CSV는 단순하지만 스키마 불일치, 구분자 문제로 오류가 많음.  
- Parquet, Avro 등은 메타데이터를 포함해 안정적임.  

#### 7.5.10~7.5.15 기타 방식
- **셸, SSH, SFTP/SCP:** 내부 네트워크 환경에서 파일 전송에 사용됨.  
- **웹훅(Webhook):** 특정 이벤트 발생 시 실시간 푸시.  
- **웹 인터페이스/스크레이핑:** 웹사이트 데이터를 자동 추출함.  
- **데이터 마이그레이션 전용 어플라이언스:** 대용량 이전에 사용됨 (예: AWS Snowball).  
- **데이터 공유:** 외부 플랫폼 간의 데이터 통합 공유를 의미함.  

### 7.6 함께 일할 담당자
- 데이터 수집은 여러 부서의 협업이 필요함.  

#### 7.6.1 업스트림 이해관계자
- 데이터 생성자(개발자, 서비스팀, API 소유자)임.  
- 데이터 구조 변경 시 조기 알림 체계가 중요함.  

#### 7.6.2 다운스트림 이해관계자
- 분석가, 데이터 과학자, 머신러닝 엔지니어 등이 포함됨.  
- 데이터 포맷 및 지연 시간 요구사항을 정의함.  

### 7.7 드러나지 않는 요소

#### 7.7.1 보안
- 인증, 암호화, 접근 제어를 모든 수집 경로에 적용해야 함.  
- 민감 데이터는 전송 중에도 암호화(TLS/SSL)되어야 함.  

#### 7.7.2 데이터 관리
- 수집 단계에서 메타데이터와 품질 검사를 수행함으로써 오류를 조기에 차단함.  

#### 7.7.3 데이터옵스
- 데이터 수집 파이프라인의 **자동화, 모니터링, 테스트 문화**를 포함함.  

#### 7.7.4 오케스트레이션
- Airflow, Prefect 등을 통해 **수집 작업의 순서와 의존성**을 제어함.  

#### 7.7.5 소프트웨어 엔지니어링
- 코드 버전 관리, 로깅, 에러 핸들링을 수집 코드에도 동일하게 적용해야 함.  

### 7.8 결론
- 데이터 수집은 데이터 엔지니어링 파이프라인의 **혈관 역할**임.  
- 수집의 안정성과 일관성이 전체 시스템의 품질을 좌우함.  
- “잘 설계된 수집 시스템은 조용히 동작하지만, 나쁜 수집 시스템은 모든 문제의 근원이 됨.”

## CHAPTER 8 4단계: 쿼리 모델링 및 데이터 변환

### 8.1 쿼리
- 쿼리는 데이터에 **질문을 던지고 응답을 받는 과정**임.  
- 데이터 변환과 분석의 핵심 수단으로, 사용자의 요구를 컴퓨터가 이해할 수 있는 형태로 표현함.  
- 쿼리의 품질은 데이터 파이프라인의 성능과 효율성에 직접적인 영향을 미침.  

#### 8.1.1 쿼리란 무엇인가?
- 쿼리(Query)는 저장된 데이터에 대해 **검색, 집계, 조작, 변환을 수행하는 명령**임.  
- SQL은 가장 보편적인 쿼리 언어로, 구조화된 데이터를 대상으로 함.  
- 최근에는 **NoSQL, GraphQL, DSL(Domain-Specific Language)** 등 다양한 형태로 확장되고 있음.  
- 쿼리는 단순한 SELECT 명령뿐 아니라 **데이터 모델 설계 철학의 반영**임.  

#### 8.1.2 쿼리 수명
- 쿼리의 수명(Query lifecycle)은 다음과 같은 단계를 거침:  
  1. **작성(Authoring):** 사용자가 명령을 정의함.  
  2. **파싱(Parsing):** 시스템이 쿼리를 해석하고 계획을 생성함.  
  3. **최적화(Optimization):** 쿼리 실행 계획을 효율적으로 조정함.  
  4. **실행(Execution):** 실제 데이터 엔진이 쿼리를 처리함.  
  5. **결과 반환(Return):** 사용자가 결과를 수신함.  
- 각 단계에서 성능 병목이 발생할 수 있음 → **쿼리 튜닝의 대상**임.  

#### 8.1.3 쿼리 옵티마이저
- 옵티마이저는 쿼리 실행 계획을 자동으로 선택하는 **DB 엔진의 두뇌**임.  
- 비용 기반(CBO, Cost-Based Optimizer)이 일반적이며,  
  테이블 통계, 인덱스, 조인 순서 등을 고려함.  
- Snowflake, BigQuery 같은 현대적 엔진은 **자동 병렬화, 쿼리 재작성(query rewriting)** 등을 수행함.  

#### 8.1.4 쿼리 성능 향상
- 쿼리 성능 향상 기법에는 다음이 포함됨:  
  - **인덱싱:** 검색 속도 개선.  
  - **파티셔닝:** 데이터 분할로 I/O 감소.  
  - **프루닝(pruning):** 불필요한 데이터 블록 무시.  
  - **캐싱:** 반복 쿼리 응답 속도 향상.  
  - **물리적 설계:** 저장 포맷(Parquet, ORC)과 정렬 기준이 중요함.  
- 쿼리 성능은 “엔진의 기능”보다 “데이터 모델링 품질”에 더 크게 의존함.  

#### 8.1.5 스트리밍 데이터에 대한 쿼리
- 스트리밍 쿼리는 **끊임없이 흐르는 데이터**를 대상으로 수행됨.  
- 고정된 스냅샷이 아니라, 시간 축에서 **창(window)**을 기준으로 처리함.  
- Apache Flink, Kafka Streams, Beam 등이 대표적인 엔진임.  
- 주요 개념:
  - **이벤트 시간(Event time)** vs **처리 시간(Processing time)**  
  - **Watermark:** 늦게 도착한 이벤트의 경계 시점 정의  
  - **상태 관리(Stateful processing):** 스트리밍 중간 결과를 저장함.  

### 8.2 데이터 모델링
- 데이터 모델링은 데이터를 **비즈니스 관점에서 구조화하여 표현하는 과정**임.  
- 잘 설계된 모델은 쿼리 성능, 확장성, 유지보수성을 높임.  
- 데이터 모델링은 데이터의 형태(정형, 반정형, 비정형)와 사용 목적에 따라 다르게 접근함.  

#### 8.2.1 데이터 모델이란?
- 데이터 모델은 데이터가 어떻게 연결되고, 어떤 의미를 가지는지를 설명하는 **개념적 청사진**임.  
- 데이터의 저장 구조, 관계, 제약 조건 등을 포함함.  
- 예: ER(Entity-Relationship) 모델, 스타 스키마, 스노우플레이크 스키마 등.  

#### 8.2.2 개념적, 논리적, 물리적 데이터 모델
- **개념적 모델(Conceptual):** 비즈니스 개념과 관계를 정의함. (비기술적 관점)  
- **논리적 모델(Logical):** 엔티티, 속성, 관계를 구체화함. (데이터베이스 중립적 관점)  
- **물리적 모델(Physical):** 실제 DB 구조(테이블, 인덱스, 키 등)를 정의함.  
- 데이터 엔지니어는 논리적과 물리적 모델의 연결 고리를 설계함.  

#### 8.2.3 정규화
- 데이터 중복을 제거하고 일관성을 유지하기 위한 설계 기법임.  
- 1NF~5NF 단계로 구성되며, 이상(anomaly)을 방지함.  
- 하지만 분석 시스템에서는 과도한 정규화가 비효율적일 수 있어 **비정규화(denormalization)**가 자주 사용됨.  

#### 8.2.4 배치 분석 데이터 모델링 기술
- OLAP 분석 환경에서는 다음과 같은 모델이 일반적임:  
  - **스타 스키마(Star Schema):** 중앙 팩트 테이블과 주변 차원 테이블 구조.  
  - **스노우플레이크 스키마:** 차원 테이블을 추가로 정규화한 구조.  
  - **데이터 볼트(Data Vault):** 확장성과 변경 추적에 유리한 현대적 모델.  
- 쿼리 성능, 데이터 통합, 거버넌스 요구사항에 따라 모델을 선택함.  

#### 8.2.5 스트리밍 데이터 모델링
- 스트리밍 데이터는 정적 스키마 대신 **동적, 시간 기반 모델링**을 필요로 함.  
- 주요 고려 사항:
  - **이벤트 시계열 저장 구조** (append-only 구조 선호)  
  - **윈도우별 집계 및 상태 관리**  
  - **메시지 재처리 대비 설계**  
- Flink Table API나 ksqlDB는 SQL 기반 스트리밍 모델링을 지원함.  

### 8.3 변환
- 데이터 변환(Transformation)은 원천 데이터(raw)를 **분석 또는 서비스용 형태로 가공하는 과정**임.  
- 변환의 품질은 결과 데이터의 신뢰도와 직접적으로 연결됨.  

#### 8.3.1 배치 변환
- ETL(Extract-Transform-Load) 또는 ELT(Extract-Load-Transform) 프로세스의 핵심 단계임.  
- Spark, dbt, Airflow, Dataflow 등이 사용됨.  
- 주요 패턴:
  - **집계(aggregation)**, **조인(join)**, **정규화/비정규화**, **필터링**  
  - **데이터 품질 검사 및 정제**  
- 배치 변환은 처리량이 크지만, 지연(latency)이 큼 → 정기 보고용에 적합함.  

#### 8.3.2 구체화된 뷰, 페더레이션, 쿼리 가상화
- **구체화된 뷰(Materialized View):** 자주 사용하는 쿼리 결과를 미리 저장함. 성능 향상 효과가 큼.  
- **페더레이션(Federation):** 서로 다른 데이터 소스에 분산된 데이터를 단일 쿼리로 조회함.  
- **쿼리 가상화(Query Virtualization):** 실제 데이터를 복제하지 않고, 논리적으로 연결해 통합 조회함.  
- 이러한 기술들은 **데이터 이동을 최소화**하며, 실시간 통합 분석을 가능하게 함.  

#### 8.3.3 스트리밍 변환과 처리
- 스트림 기반 변환은 지속적으로 흐르는 데이터를 실시간으로 가공함.  
- 대표적 연산:
  - **윈도우 집계(Window aggregation)**  
  - **상태 기반 조인(Stateful join)**  
  - **지연 데이터 처리(Late data handling)**  
- Apache Beam, Flink, Kafka Streams가 주로 사용됨.  
- 스트리밍 변환은 “끊임없는 ETL”에 가깝고, 배치보다 복잡한 장애 복구 설계가 필요함.  

### 8.4 함께 일할 담당자

#### 8.4.1 업스트림 이해관계자
- 데이터 원천 시스템 관리자, 애플리케이션 개발자 등이 포함됨.  
- 스키마 변경이나 데이터 품질 문제 발생 시 커뮤니케이션이 필수임.  

#### 8.4.2 다운스트림 이해관계자
- 데이터 분석가, BI 팀, 데이터 과학자 등이 포함됨.  
- 변환된 데이터의 구조와 의미를 명확히 문서화해야 함.  
- dbt 문서화나 데이터 카탈로그 연동이 일반적인 방식임.  

### 8.5 드러나지 않는 요소

#### 8.5.1 보안
- 쿼리 및 변환 단계에서 **데이터 마스킹, 권한 분리, 감사 로그**가 필요함.  
- 특히 개인식별정보(PII)는 변환 중에도 암호화 상태를 유지해야 함.  

#### 8.5.2 데이터 관리
- 스키마 관리, 메타데이터 추적, 데이터 품질 검사가 변환 파이프라인에 내장되어야 함.  
- “데이터 혈통(lineage)” 추적은 규제 준수와 디버깅의 필수 요소임.  

#### 8.5.3 데이터옵스
- 변환 코드를 CI/CD 파이프라인으로 자동 배포함.  
- 테스트, 검증, 모니터링 프로세스를 포함함.  

#### 8.5.4 데이터 아키텍처
- 변환 로직은 전체 데이터 아키텍처의 일관성을 유지해야 함.  
- 변환 계층은 **데이터 레이크 → 웨어하우스 → 서빙 계층**으로 이어짐.  

#### 8.5.5 오케스트레이션
- Airflow, Dagster, Prefect 등으로 **변환 작업의 실행 순서와 의존성을 제어**함.  
- 변환 실패 시 재시도 정책 및 알림 시스템을 구성해야 함.  

#### 8.5.6 소프트웨어 엔지니어링
- 변환 코드는 소프트웨어처럼 관리되어야 함 (버전 관리, 테스트, 리뷰 필수).  
- “데이터를 코드로(Data as Code)”라는 개념이 확산되고 있음.  

### 8.6 결론
- 쿼리와 변환은 데이터 엔지니어링의 “두뇌”에 해당함.  
- 효율적인 쿼리 설계와 일관된 모델링은 **성능, 확장성, 유지보수성**을 결정함.  
- 변환 계층은 데이터 품질의 관문으로, 올바른 변환 없이는 정확한 분석도 불가능함.  
- 결국 데이터 엔지니어의 목표는 “데이터를 올바른 형태로, 올바른 사람에게, 올바른 시점에 전달하는 것”임.

## CHAPTER 9 5단계: 분석, 머신러닝 및 역 ETL을 위한 데이터 서빙

### 9.1 데이터 서빙의 일반적인 고려 사항
- 데이터 서빙(Data Serving)은 데이터 엔지니어링 수명 주기의 **최종 단계**로,  
  데이터를 실제 사용자(사람 혹은 시스템)가 활용할 수 있도록 제공하는 과정임.  
- 서빙 계층은 데이터 파이프라인의 “출구”로서,  
  분석, 시각화, 머신러닝, 운영 시스템 피드백(역 ETL)에 데이터를 전달함.  

#### 9.1.1 신뢰
- 서빙된 데이터가 **정확하고 최신이며 일관성 있는가**가 핵심임.  
- 신뢰(Trust)는 데이터 품질, 계보(lineage), SLA, 모니터링에 의해 확보됨.  
- 데이터 품질이 무너지면 분석과 모델 모두 신뢰를 잃게 됨.  

#### 9.1.2 사용 사례는 무엇이며 사용자는 누구인가?
- 데이터 서빙은 **사용자와 목적에 따라 달라짐**.  
  - 경영진: 집계 리포트, KPI 대시보드  
  - 데이터 분석가: BI 쿼리, 탐색적 분석  
  - 데이터 과학자: 모델 학습용 피처 데이터  
  - 백엔드 시스템: 예측값 피드백 (역 ETL)  
- 서빙 방식(쿼리, API, 스트림)은 대상 사용자에 맞춰 설계해야 함.  

#### 9.1.3 데이터 제품
- 데이터 서빙 결과물은 단순한 쿼리 결과가 아니라 **데이터 제품(Data Product)**임.  
- 데이터 제품은 다음과 같은 특징을 가짐:  
  - 명확한 오너십과 SLA  
  - 문서화된 스키마와 사용 지침  
  - 재사용 가능한 인터페이스(API, SQL View 등)  
- 데이터 제품 개념은 “데이터를 서비스처럼 제공”한다는 **데이터 메시(Data Mesh)** 철학과 맞닿아 있음.  

#### 9.1.4 셀프 서비스 여부
- 현대 데이터 플랫폼의 목표는 **셀프 서비스(Self-Service)** 환경 제공임.  
- 사용자가 직접 쿼리하거나 시각화할 수 있어야 하며,  
  이를 위해 카탈로그, 권한 관리, 시맨틱 계층이 필요함.  

#### 9.1.5 데이터 정의 및 논리
- 데이터 서빙에서 **정의의 일관성(semantic consistency)**은 필수임.  
- 예를 들어 “매출”이라는 지표가 팀마다 다르게 계산되면 혼란이 생김.  
- 이를 해결하기 위해 **중앙 시맨틱 계층(semantic layer)**을 도입함.  

#### 9.1.6 데이터 메시
- 데이터 메시(Data Mesh)는 **분산된 데이터 소유권과 제품화된 데이터 도메인**을 강조함.  
- 중앙집중형 팀 대신 각 도메인이 자신의 데이터 제품을 직접 서빙함.  
- 데이터 엔지니어는 **플랫폼과 표준화된 인프라**를 제공하는 역할을 맡음.  

### 9.2 분석
- 분석(Analytics)은 서빙 계층의 가장 전통적인 사용 사례임.  
- 데이터를 활용하여 **과거를 이해하고, 현재를 모니터링하며, 미래를 예측**함.  

#### 9.2.1 비즈니스 분석
- KPI, 리포트, 대시보드 중심의 정형 분석임.  
- 주로 BI 도구(Tableau, Power BI, Looker)를 통해 수행됨.  
- 요구사항: **정확성, 일관성, 신뢰성**이 최우선임.  

#### 9.2.2 운영 분석
- 실시간 운영 데이터를 기반으로 의사결정을 지원함.  
- 예: 실시간 주문량, 서비스 지연 모니터링.  
- 일반적으로 스트리밍 파이프라인과 결합되어 있음.  

#### 9.2.3 임베디드 분석
- 분석 결과가 **다른 애플리케이션에 내장(embedded)**되어 사용자에게 직접 제공됨.  
- 예: SaaS 대시보드에 통계 그래프를 삽입하거나, CRM 내에서 고객 지표 제공.  
- API 기반 서빙 또는 쿼리 연합 방식으로 구현됨.  

### 9.3 머신러닝
- 머신러닝(ML)은 데이터 서빙의 주요 소비자 중 하나임.  
- 서빙 계층은 모델 학습용 피처 데이터를 제공하고,  
  예측 결과를 저장하거나 운영 시스템으로 다시 피드백함.  
- ML 서빙의 특징은 **정확도와 신선도 간의 균형**임.  
- 피처 저장소(Feature Store), 모델 레지스트리, 배치/온라인 예측 시스템이 핵심 구성 요소임.  

### 9.4 데이터 엔지니어가 ML에 관해 알아야 할 사항
- 데이터 엔지니어는 모델링 자체보다 **데이터 파이프라인과 인프라 설계**에 집중해야 함.  
- 주요 고려 사항:  
  - **학습용/서빙용 데이터의 일관성 유지** (train-serving skew 방지)  
  - **데이터 버전 관리 및 재현성 보장**  
  - **피처 엔지니어링 자동화 및 피처 저장소 관리**  
- 데이터 엔지니어와 ML 엔지니어 간의 협업이 필수적임.  

### 9.5 분석 및 ML을 위한 데이터 서빙 방법
- 서빙 방법은 **데이터 형태, 사용 목적, 지연 요구사항**에 따라 달라짐.  

#### 9.5.1 파일 교환
- CSV, JSON, Parquet 파일을 이메일, S3, GCS 등으로 전달함.  
- 단순하지만 버전 관리와 동기화가 어렵고, 자동화에 한계가 있음.  

#### 9.5.2 데이터베이스
- RDBMS, NoSQL, OLAP 시스템을 통해 쿼리 접근을 제공함.  
- BI, 대시보드, 리포팅에 적합함.  
- 권한 관리, 커넥션 풀링, 캐싱 구조를 함께 설계해야 함.  

#### 9.5.3 스트리밍 시스템
- Kafka, Pulsar, Kinesis를 통한 **실시간 서빙**임.  
- 이벤트 기반 분석, 실시간 피드백 루프에 사용됨.  
- 메시지 키와 오프셋 관리가 중요함.  

#### 9.5.4 쿼리 페더레이션
- 여러 저장소의 데이터를 **단일 쿼리로 조회**하는 기술임.  
- Presto, Trino, BigQuery Federation 등이 대표적임.  
- 데이터 이동을 줄이고, 다양한 소스를 통합 분석함.  

#### 9.5.5 데이터 공유
- 데이터셋을 외부 조직 또는 다른 플랫폼과 **안전하게 공유**함.  
- Snowflake Data Sharing, Delta Sharing, BigQuery Omni 등은 클라우드 간 공유를 지원함.  
- 공유 시 권한 제어, 감사 로그, 비용 관리가 중요함.  

#### 9.5.6 시맨틱과 메트릭 계층
- 시맨틱 계층은 데이터 의미를 표준화하여 **“단일 진실의 원천(single source of truth)”**을 제공함.  
- 메트릭 계층은 KPI 계산식을 중앙에서 관리함.  
- dbt Metrics Layer, LookML, Transform 등이 대표적임.  

#### 9.5.7 노트북에서의 데이터 서빙
- 데이터 과학자는 주로 Jupyter, Databricks, Zeppelin 등의 노트북 환경에서 데이터를 조회함.  
- 이때 SQL 엔진 또는 API를 통한 셀프 서비스 접근이 필요함.  

### 9.6 역 ETL
- 역 ETL(Reverse ETL)은 데이터 웨어하우스나 레이크에 저장된 가공 데이터를  
  **운영 시스템(CRM, 마케팅 툴, SaaS 등)**으로 되돌려주는 과정임.  
- 과거에는 수동 업로드나 Excel 기반으로 처리했으나,  
  현재는 **자동화된 역 ETL 플랫폼(Hightouch, Census)**이 등장함.  
- 주요 목적:
  - 분석 결과(고객 세그먼트, 추천 점수 등)를 운영 환경에 반영함.  
  - 데이터 웨어하우스를 **업무 중심 허브**로 전환함.  
- Reverse ETL은 데이터 사이클을 “분석 → 실행 → 피드백”으로 완성시킴.  

### 9.7 함께 작업하는 사람
- 데이터 서빙 단계에서는 다음의 역할들이 협력함:  
  - **데이터 분석가:** BI 대시보드와 보고서 정의  
  - **데이터 과학자:** 모델 입력 및 결과 관리  
  - **데이터 엔지니어:** 서빙 인프라와 접근 경로 구축  
  - **비즈니스 팀:** 데이터 제품 소비자  

### 9.8 드러나지 않는 요소

#### 9.8.1 보안
- 데이터 접근 제어, 권한 분리, 마스킹이 필수임.  
- 서빙 환경에서는 **데이터 노출 범위**를 최소화해야 함.  

#### 9.8.2 데이터 관리
- 서빙된 데이터셋의 버전, 문서화, lineage를 지속적으로 관리해야 함.  
- 품질 지표(accuracy, freshness, completeness)를 모니터링함.  

#### 9.8.3 데이터옵스
- 서빙 단계의 **자동화, 모니터링, SLA 관리**를 담당함.  
- 데이터 파이프라인의 “운영 안정성”을 확보함.  

#### 9.8.4 데이터 아키텍처
- 서빙 계층은 데이터 웨어하우스, API 게이트웨이, 캐시 계층 등과 결합됨.  
- 설계 시 확장성과 비용 효율성을 함께 고려해야 함.  

#### 9.8.5 오케스트레이션
- Airflow, Dagster 등으로 **서빙 배포 스케줄링**을 자동화함.  
- 데이터 업데이트 주기와 의존성을 관리함.  

#### 9.8.6 소프트웨어 엔지니어링
- 서빙 코드(API, 쿼리, 파이프라인)는 버전 관리와 테스트가 필수임.  
- IaC(Terraform, Pulumi)로 인프라를 코드 기반으로 관리함.  

### 9.9 결론
- 데이터 서빙은 데이터 엔지니어링의 “마지막 1마일(last mile)”임.  
- 좋은 서빙 시스템은 데이터를 **적절한 형태로, 적시에, 올바른 사용자에게 제공**함.  
- 분석, 머신러닝, 운영 시스템 간의 경계가 점점 모호해지면서,  
  데이터 서빙은 단순한 조회 단계를 넘어 **비즈니스 실행의 중심**이 되고 있음.  
- 결국 데이터 엔지니어의 목표는 “데이터가 활용되는 순간까지 책임지는 것”임.

## CHAPTER 10 보안과 개인정보보호

### 10.1 사람
- 보안의 첫 번째 축은 기술이 아니라 **사람**임.  
- 사람의 실수가 보안 사고의 대부분을 차지하며,  
  조직 내 보안 문화는 기술 정책보다 더 강력한 방어선임.  

#### 10.1.1 부정적인 사고의 힘
- “무엇이 잘못될 수 있을까?”를 상시적으로 생각하는 습관이 중요함.  
- 이런 부정적 사고(negative thinking)는 보안에서 매우 생산적임.  
- 예를 들어, 데이터 접근 요청을 받을 때 “이 접근이 악용될 수 있는가?”를 먼저 질문해야 함.  
- 해커의 관점에서 시스템을 상상해보는 것이 가장 현실적인 방어 전략임.  

#### 10.1.2 항상 편집증적인 자세 유지하기
- 보안 담당자에게는 어느 정도의 “건강한 편집증(healthy paranoia)”이 필요함.  
- 보안 위협은 언제든 존재하므로, 항상 의심하고 검증하는 태도가 필수임.  
- 특히 공용 리소스 접근, 공개 API 사용, 이메일 링크 클릭 등은 항상 위험을 내포함.  
- 편집증적인 태도는 팀 전체의 보안 민감도를 높이는 훈련임.  

### 10.2 프로세스
- 보안은 단발적 조치가 아니라 **지속적인 프로세스**임.  
- 조직 차원에서의 정책, 프로시저, 점검 루프가 시스템보다 더 큰 역할을 함.  

#### 10.2.1 보여주기식 vs 숙련된 보안
- “보여주기식 보안”은 문서상 정책만 존재하고 실제로는 적용되지 않는 상태를 의미함.  
- “숙련된 보안”은 위험 모델링, 지속 점검, 개선 루프를 갖춘 상태임.  
- 진정한 보안은 인증서가 아니라 **습관화된 실천**에서 비롯됨.  

#### 10.2.2 능동 보안
- 수동적 감시가 아닌, **위협을 예측하고 선제적으로 차단하는 보안 태도**임.  
- 침입 테스트, 모의 해킹, 위협 인텔리전스 수집이 여기에 해당함.  
- 공격 발생 후 대응하는 것보다 사전 시뮬레이션이 훨씬 효과적임.  

#### 10.2.3 최소 권한 원칙
- 사용자는 업무 수행에 필요한 최소한의 권한만 가져야 함.  
- “모두에게 읽기 권한”은 편리하지만, 가장 큰 위험 요소임.  
- 접근 제어를 역할 기반(Role-Based Access Control, RBAC)으로 설계하면 관리가 용이함.  
- 데이터 접근 로그를 주기적으로 검토하는 것도 최소 권한 원칙의 일부임.  

#### 10.2.4 클라우드에서의 책임 공유
- 클라우드 보안은 “공급자와 사용자 간의 **공유 책임 모델(shared responsibility model)**”을 따름.  
- 클라우드 공급자는 인프라 보안을 담당하지만,  
  데이터 암호화, 접근 통제, 애플리케이션 보안은 사용자 책임임.  
- 예를 들어 AWS에서는 S3 퍼블릭 버킷 설정 오류가 여전히 가장 흔한 보안 사고임.  
- 따라서 클라우드 사용자는 **구성 보안(configuration security)**에 특히 주의해야 함.  

#### 10.2.5 항상 데이터를 백업하라
- 백업은 단순 복구 수단이 아니라 보안의 핵심임.  
- 랜섬웨어 공격 시 유일한 복구 수단이 되기도 함.  
- 백업 데이터는 주 저장소와 물리적으로 분리해야 하며, 주기적 복원 테스트가 필요함.  
- “백업이 없다면 데이터는 이미 위험에 노출되어 있는 것”임.  

#### 10.2.6 보안 정책 예시
- 실무적으로 다음과 같은 정책이 필요함:  
  - 비밀번호 및 키 주기적 교체  
  - MFA(Multi-Factor Authentication) 적용  
  - 접근 로그 보존 및 감사 체계 구축  
  - 퇴사자 접근 권한 즉시 회수  
  - 데이터 전송 시 TLS, 저장 시 암호화  
  - 정기 보안 교육 및 피싱 대응 훈련  
- 정책의 핵심은 “자동화된 점검과 위반 시 즉시 경고”임.  

### 10.3 기술
- 기술은 보안의 기반이며, **사람과 프로세스**를 보완하는 수단임.  
- 최신 기술 스택은 보안 자동화를 가능하게 하지만, 여전히 올바른 설정이 필수임.  

#### 10.3.1 패치와 시스템 갱신
- 대부분의 보안 사고는 이미 알려진 취약점 미패치로 발생함.  
- 운영체제, 데이터베이스, 라이브러리를 주기적으로 업데이트해야 함.  
- 자동 패치 시스템을 도입하되, 프로덕션 환경은 사전 테스트 후 적용해야 함.  
- “패치는 귀찮지만, 공격보다 덜 고통스럽다”는 말이 있음.  

#### 10.3.2 암호화
- 데이터 보안의 근본 원칙은 **암호화(Encryption)**임.  
- 전송 중 암호화(TLS/SSL)와 저장 중 암호화(At-rest Encryption)를 모두 적용해야 함.  
- 키 관리는 별도 서비스(KMS, HSM)를 사용해 안전하게 분리함.  
- 특히 개인정보(PII)와 금융 데이터는 필드 수준 암호화(field-level encryption)가 필요함.  

#### 10.3.3 로깅, 모니터링, 알림
- 보안 이벤트를 탐지하고 대응하기 위해 **로깅과 모니터링 시스템**이 필수임.  
- CloudWatch, Datadog, Splunk, SIEM 시스템 등을 활용함.  
- 단순 수집이 아니라, “이상 행동을 감지하고 즉시 알림”으로 이어져야 함.  
- 로그는 규제 준수(GDPR, SOC2 등)에도 중요함.  

#### 10.3.4 네트워크 접근
- 네트워크는 보안의 최전선임.  
- 방화벽, 보안 그룹, VPN, VPC 격리를 통해 접근을 최소화함.  
- 내부 네트워크라고 해서 신뢰할 수 있는 것은 아님 → 제로 트러스트(Zero Trust) 원칙 적용.  
- 외부 API 호출 시에도 IP 화이트리스트와 요청 서명 검증이 필요함.  

#### 10.3.5 로우 레벨 데이터 엔지니어링을 위한 보안
- 데이터 엔지니어링 특유의 보안 고려 사항은 다음과 같음:  
  - 데이터 파이프라인에 민감 정보가 포함되지 않도록 설계  
  - 로그나 모니터링 도구에 개인정보 노출 금지  
  - 임시 스토리지(temp, cache)도 암호화 적용  
  - 데이터 샘플링 시 익명화(Anonymization) 또는 마스킹(Masking) 필수  
  - 클러스터 및 컨테이너 환경(Docker, Kubernetes)의 보안 패치 유지  
- 즉, 데이터 엔지니어는 단순한 처리자가 아니라 **보안 의식이 있는 관리자**여야 함.  

### 10.4 결론
- 보안과 개인정보보호는 기술이 아니라 **문화이자 태도**임.  
- 완벽한 보안은 존재하지 않지만, 체계적 대비는 피해를 최소화함.  
- 사람 → 프로세스 → 기술의 순서로 보안을 강화해야 함.  
- 결국 데이터 엔지니어는 “데이터를 안전하게 다루는 엔지니어”여야 함.  
- **신뢰받는 데이터 시스템은 보안에서 시작된다**는 점을 잊지 말아야 함.

## CHAPTER 11 데이터 엔지니어링의 미래

### 11.1 사라지지 않는 데이터 엔지니어링 수명 주기
- 데이터 엔지니어링의 **핵심 수명 주기(생성 → 저장 → 수집 → 변환 → 서빙)**는 사라지지 않음.  
- 도구와 접근 방식은 변화하더라도, 데이터가 생성되어 활용되기까지의 본질적 흐름은 동일함.  
- 따라서 “새로운 기술”보다 **기본 원리와 구조적 사고력**이 더 중요함.  
- 미래의 데이터 엔지니어는 기술보다 **데이터 품질, 신뢰, 통합성 관리 능력**이 핵심 역량이 될 것임.  

### 11.2 복잡성의 감소와 사용하기 쉬운 데이터 도구의 부상
- 과거 데이터 엔지니어링은 **복잡한 인프라 설정, 수동 코드 관리, 파편화된 도구**들로 인해 어려웠음.  
- 최근에는 SaaS 기반, 관리형 플랫폼, 노코드/로우코드 툴이 등장하여 **복잡성을 줄이는 방향**으로 진화 중임.  
- 예: Fivetran, dbt Cloud, Snowflake, BigQuery, Databricks 등은 **데이터 파이프라인의 추상화 수준**을 높임.  
- 그러나 단순화된 도구의 사용이 “엔지니어링의 소멸”을 의미하지는 않음 →  
  여전히 **데이터 아키텍처, 설계 원칙, 거버넌스 이해**가 필수임.  

### 11.3 클라우드 규모의 데이터 OS와 향상된 상호 운용성
- 클라우드는 단순 저장소가 아니라 **데이터 운영체제(Data Operating System)**로 발전 중임.  
- 다양한 데이터 서비스들이 API 기반으로 상호 연동되며, 데이터는 물리적 경계를 넘어 이동함.  
- Snowflake, BigQuery, Databricks 같은 플랫폼은 이미 **데이터 공유와 협업 생태계**를 중심으로 진화 중임.  
- 미래에는 “어느 클라우드를 쓰느냐”보다, **어떻게 데이터를 연결하고 표준화하느냐**가 중요해질 것임.  
- 멀티클라우드 및 크로스플랫폼 데이터 이동은 기본 전제가 됨.  

### 11.4 ‘엔터프라이즈’ 데이터 엔지니어링
- 대기업(엔터프라이즈) 환경에서는 여전히 **규모, 규제, 복잡성**이 큰 과제임.  
- 이 환경에서의 데이터 엔지니어링은 단순 기술 구현이 아닌 **프로세스, 보안, 거버넌스 중심의 엔지니어링**임.  
- 중앙 데이터 플랫폼 팀, 데이터 거버넌스 팀, 프라이버시 오피서 등 조직적 구조가 확립되고 있음.  
- 엔터프라이즈 데이터 엔지니어는 기술적 유연성보다 **정책적 준수와 안정성 확보**에 더 초점을 둠.  

### 11.5 직책과 책임의 변화
- 데이터 엔지니어링 분야는 세분화되고 있음.  
- 과거 하나의 “데이터 엔지니어” 역할이 현재는 여러 역할로 분화됨:  
  - **데이터 플랫폼 엔지니어:** 인프라, 오케스트레이션, 클라우드 관리  
  - **데이터 파이프라인 엔지니어:** ETL/ELT, 스트리밍, 배치 설계  
  - **데이터 분석 엔지니어:** dbt, SQL, BI 계층 설계  
  - **ML 엔지니어:** 피처 스토어, 모델 서빙, MLOps  
- 이러한 역할 분화는 기술의 복잡성과 데이터 가치 사슬의 확장에 따라 필연적임.  
- 또한 “데이터 제품 관리자(Data Product Manager)”와 같은 **데이터 비즈니스 직군**도 부상 중임.  

### 11.6 모던 데이터 스택을 넘어 라이브 데이터 스택으로
- 기존의 **모던 데이터 스택(Modern Data Stack)**은 배치 중심 구조였음.  
- 그러나 실시간 의사결정과 개인화 서비스가 확대되면서,  
  **라이브 데이터 스택(Live Data Stack)**이라는 새로운 개념이 등장함.  
- 이는 데이터를 실시간으로 처리, 분석, 피드백하는 **끊임없이 흐르는 데이터 생태계**를 의미함.  

#### 11.6.1 라이브 데이터 스택
- 라이브 데이터 스택은 **데이터 수집부터 서빙까지 실시간으로 연결된 구조**임.  
- 이벤트 기반 설계, 스트리밍 처리, 실시간 피드백 루프가 기본 구성 요소임.  
- 주요 기술 스택: Kafka, Flink, Materialize, Rockset, Snowflake Streaming, dbt Cloud 등임.  

#### 11.6.2 스트리밍 파이프라인과 실시간 분석 데이터베이스
- 데이터는 “나중에 모아서 분석”하는 것이 아니라 **즉시 처리 후 분석되는 흐름**으로 전환 중임.  
- 스트리밍 파이프라인은 ETL의 실시간 버전이며, 이벤트 단위로 변환과 집계를 수행함.  
- 이를 저장하고 쿼리하는 실시간 분석 DB가 발전함 (예: ClickHouse, Pinot, Druid).  
- 결과적으로 “데이터 수집과 분석의 경계”가 점점 사라지고 있음.  

#### 11.6.3 데이터와 애플리케이션의 융합
- 과거에는 애플리케이션이 데이터를 생성하고, 데이터 엔지니어링이 이를 후처리했음.  
- 그러나 현재는 **데이터 처리 로직이 애플리케이션 내부로 들어오고 있음.**  
- 예: Netflix의 실시간 추천, Uber의 가격 책정 알고리즘 등은 **데이터 파이프라인이 비즈니스 로직과 결합된 형태**임.  
- 즉, “데이터 시스템 = 애플리케이션 시스템”으로 융합되는 추세임.  

#### 11.6.4 애플리케이션과 ML 간의 긴밀한 피드백
- 머신러닝 모델은 더 이상 오프라인 훈련 후 끝나지 않음.  
- 운영 데이터가 실시간으로 모델에 입력되고, 결과는 즉시 시스템에 반영됨.  
- 이를 통해 “학습 → 예측 → 피드백”의 **지속적 루프(closed loop)**가 형성됨.  
- ML 파이프라인과 데이터 엔지니어링 파이프라인의 경계가 점점 희미해지고 있음.  

#### 11.6.5 얇게 압축된 데이터와 스프레드시트의 부상
- 데이터 분석 도구가 점점 사용자 친화적으로 변하면서,  
  “데이터의 압축(Abstraction)”이 얇아지고 있음.  
- 스프레드시트, 노트북, 인터랙티브 쿼리 툴이 실시간 데이터와 직접 연결되는 시대임.  
- Google Sheets, Notion, Hex, Observable 같은 도구가 실시간 데이터 플랫폼의 일부로 사용됨.  
- 이는 데이터 민주화(Democratization)의 상징이자, “라이브 데이터 소비”의 확대를 의미함.  

### 11.7 결론
- 데이터 엔지니어링은 도구 중심에서 **플랫폼 중심, 그리고 제품 중심 사고**로 전환되고 있음.  
- 자동화, 스트리밍, 상호운용성이 발전해도 **기본 원리(수명 주기, 품질, 아키텍처)**는 여전히 핵심임.  
- 미래의 데이터 엔지니어는 단순한 배관공(pipeline builder)이 아니라,  
  **데이터 제품 설계자이자 실시간 데이터 흐름의 운영자**로 진화할 것임.  
- 데이터 엔지니어링의 미래는 “정적 데이터”가 아니라,  
  **실시간으로 살아 숨 쉬는 데이터 생태계(Live Data Ecosystem)**를 다루는 것임.
