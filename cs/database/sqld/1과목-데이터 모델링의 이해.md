## 데이터베이스란?

### 정의 (WHAT)
- 여러 데이터들을 모아 통합적으로 관리하는 기술
- 여러 사람들이 함께 사용하고 공유할 수 있는 시스템
- **데이터(DATA)들의 모임(BASE)**

### 데이터베이스 이전 vs 이후

**이전: 파일 시스템의 문제점**
- 각 사용자가 개별 파일을 보유
- 한 사람이 파일을 수정하면 다른 모든 파일도 수정 필요
- 데이터 중복과 불일치 문제 발생

**이후: 데이터베이스의 장점**
- 데이터를 한 곳에 모아 저장
- 실시간 공유 가능
- 중복 작업 불필요

### 활용 예시
- 로그인 시스템: 회원정보 데이터베이스와 입력값 비교
- 직원 관리 프로그램: 직원 정보 저장 및 관리

---

## 데이터 모델이란?

### 정의
현실세계의 대상을 **추상화, 단순화, 명확화**하여 데이터베이스로 표현하는 것

### 데이터 모델링 단계

```
요구사항 접수 → 개념적 모델링 → 논리적 모델링 → 물리적 모델링 → 데이터베이스 구축
```

| 단계 | 개념적 모델링 | 논리적 모델링 | 물리적 모델링 |
|------|--------------|--------------|--------------|
| 특징 | 추상적, 업무중심적 | KEY, 속성, 관계 정의 | DBMS 종속적 |
| 산출물 | ERD 생성 | 정규화 수행 | 성능, 저장 구조 고려 |
| 범위 | 포괄적, 전사적(EA) | 재사용성 높음 | 구체적 |
| DBMS | 독립적 | 독립적 | 종속적 |

## 1. 엔터티(ENTITY) 이해하기

### 정의
**업무에 필요한 정보를 저장/관리하기 위한 집합적인 명사 개념**

예시:
- 직원 엔터티: A회사의 모든 직원들
- 부서 엔터티: A회사의 모든 부서들

### 인스턴스(INSTANCE)
엔터티 집합 내에 존재하는 **개별적인 대상**

```
[엔터티: 직원]
├─ 인스턴스: 직원A씨
├─ 인스턴스: 직원B씨
├─ 인스턴스: 직원C씨
├─ 인스턴스: 직원D씨
└─ 인스턴스: 직원E씨
```

### 엔터티의 특징 (5가지 필수 조건)

1. **업무 필요성**: 반드시 업무에서 필요한 대상이고 업무에 사용될 것
2. **식별 가능성**: 유일한 식별자로 식별이 가능할 것
3. **복수 인스턴스**: 인스턴스가 2개 이상일 것
4. **복수 속성**: 속성이 반드시 2개 이상 존재할 것
5. **관계 존재**: 관계가 하나 이상 존재할 것 (단, 코드성·통계성은 생략 가능)

### 엔터티 분류

#### (1) 유무형에 따른 분류

| 구분 | 정의 | 예시 |
|------|------|------|
| **유형** | 물리적 형태가 있는 엔터티 | 직원, 주류, 강사, 고객 |
| **개념** | 물리적 형태가 없는 엔터티 | 부서, 과목, 계급 |
| **사건** | 업무 수행 중 발생하는 엔터티 | 강의, 매출, 주문, 상담 |

#### (2) 발생시점에 따른 분류

| 구분 | 특징 | 예시 |
|------|------|------|
| **기본/키 엔터티** | 본래 업무에 존재하는 정보<br>독립 생성 가능, 주식별자 보유 | 직원, 고객, 상품 |
| **중심 엔터티** | 기본 엔터티로부터 발생<br>업무의 중심 역할 | 주문, 매출, 계약 |
| **행위 엔터티** | 2개 이상 엔터티로부터 발생 | 주문이력 |

### 엔터티 명명(Naming) 규칙

1. 가능한 **현업 용어** 사용 (예: 사람 → 고객, 전봇대 → 전주)
2. **약어 사용 지양** (예: 일별매출정보 → 일매목 ✗)
3. **단수 명사** 사용 (예: 직원들 → 직원 ✓)
4. 엔터티 이름은 **유일**해야 함
5. 생성의미에 맞게 명명 (예: 연락처목록 → 직원연락처목록? 고객연락처목록?)

## 2. 속성(ATTRIBUTE) 이해하기

### 정의
**업무상 관리하기 위해 의미적으로 더는 분리되지 않는 최소의 데이터 단위**

예시: 직원 엔터티의 속성
- 이름, 직원ID, 패스워드, 연봉, 부서, 입사일시, 생년월일

### 엔터티, 인스턴스, 속성의 관계

```
[엔터티: 직원]
┌─────────┬────────┬──────┬────────┐
│ 직원ID  │  이름  │ 나이 │  연봉  │ ← 속성 집합
├─────────┼────────┼──────┼────────┤
│ Emp001  │ 강태우 │  35  │  5000  │ ← 인스턴스
│ Emp002  │ 김형준 │  32  │  4800  │ ← 인스턴스
│ Emp003  │ 송송이 │  27  │  3400  │ ← 인스턴스
│ Emp004  │ 강태우 │  29  │  3700  │ ← 인스턴스
└─────────┴────────┴──────┴────────┘
```

**4가지 원칙:**
1. 하나의 엔터티는 2개 이상의 인스턴스를 가진다
2. 하나의 엔터티는 2개 이상의 속성을 가진다
3. 속성은 각 인스턴스를 설명해줄 수 있다
4. 하나의 속성에는 하나의 속성값만 들어간다

### 식별자(Identifier)
**엔터티 내 유일한 인스턴스를 식별할 수 있는 속성의 집합**

위 예시에서 '직원ID'는 각 인스턴스를 유일하게 구분할 수 있으므로 식별자가 됨

### 속성의 분류

#### (1) 특성에 따른 분류

| 구분 | 정의 | 예시 |
|------|------|------|
| **기본 속성** | 업무로부터 추출한 속성 | 이름, 나이, 연봉 |
| **설계 속성** | 설계 시 규칙화 등이 필요해 만든 속성 | 부서코드, 일련번호 |
| **파생 속성** | 다른 속성들로부터 계산/변형되어 만들어진 속성 | 부서별연봉합 |

#### (2) 구성방식에 따른 분류

- **PK (Primary Key)**: 주식별자
- **FK (Foreign Key)**: 외래키 (다른 엔터티의 PK를 참조)
- **일반속성**: 일반적인 속성
- **복합속성**: 여러 값으로 구성된 속성 (예: 주소)

### 속성 명명(Naming) 규칙

1. 가능한 **현업 용어** 사용
2. **약어 사용 지양**
3. **명사형** 사용, 서술식이나 수식어 제한 (예: 오늘배송된상품 → 일배송상품)
4. 가능한 속성 이름은 전체 데이터 모델에서 **유일**해야 함

### 도메인(DOMAIN)
**각 속성이 입력받을 수 있는 값의 정의 및 범위**

예시:
- 나이: 숫자형, 0~999
- 이름: 문자형, 최대 5자리

## 3. 관계(Relationship) 이해하기

### 정의
**엔터티 내의 인스턴스들 간에 서로 논리적인 연관성이 있는 상태**

예시:
```
직원 ─소속되다→ 부서
부서 ─보유하다→ 직원
```

### 관계의 분류

#### 존재 vs 행위

| 구분 | 설명 | 예시 |
|------|------|------|
| **존재 관계** | 존재 자체에 의한 관계 | 직원-부서 (소속) |
| **행위 관계** | 행위에 의한 관계 | 고객-상품 (주문) |

> **참고:** ERD는 둘 다 동일하게 표시, UML 클래스다이어그램은 존재(실선), 행위(점선)로 구분

### 관계 표기 방법 (3가지 요소)

#### 1. 관계명(Membership)
- 관계의 이름을 표시
- 애매한 동사나 과거형은 피함

#### 2. 관계차수(Cardinality/Degree)
엔터티 내 각 인스턴스들이 얼마나 참여하는지 표시

**1:1 관계**
```
직원 ─── 직원세부정보
(한 명의 직원은 하나의 세부정보를 가짐)
```

**1:M 관계**
```
부서 ───< 직원
(하나의 부서는 여러 직원을 가질 수 있음)
```

**M:N 관계**
```
학생 ───><─── 과목
(여러 학생이 여러 과목을 수강)

※ M:N은 1:M, M:1로 분해해야 함
학생 ───< 수강 >─── 과목
```

#### 3. 관계선택사양(Optionality)
엔터티 내 인스턴스들이 필수/선택 참여하는지 표시

- **필수 참여**: `|` (최소 1개)
- **선택 참여**: `O` (0개 이상)

### 표기법 비교

**IE 표기법**
```
부서 |─────O<─────| 직원
     소속        보유
```

**Barker 표기법**
```
부서 ─────#─────* 직원
```

### 관계 체크 사항

설정한 관계가 적합한지 확인하는 체크리스트:

1. 두 엔터티 사이에 관심 있는 연관규칙이 있는가?
2. 두 엔터티 사이에 정보의 조합이 발생하는가?
3. 업무기술서, 장표에 관계연결에 대한 규칙이 서술되었는가?
4. 업무기술서, 장표에 관계연결을 가능케 하는 동사(Verb)가 있는가?

## 4. 식별자(Identifiers)

### 정의
**엔터티 내 유일하게 인스턴스를 식별할 수 있는 속성의 집합**

### 식별자 분류 (4가지 기준)

#### (1) 대표성 여부
- **주식별자(Primary Identifier)**: 대표로 선택된 식별자
- **보조식별자(Alternate Identifier)**: 유일성은 만족하지만 대표로 선택되지 않은 식별자

#### (2) 스스로 생성 여부 (자생 여부)
- **내부식별자**: 엔터티 내부에서 스스로 생성
- **외부식별자**: 다른 엔터티로부터 받아온 식별자 (FK)

#### (3) 단일 속성 여부
- **단일식별자**: 하나의 속성으로 구성
- **복합식별자**: 둘 이상의 속성으로 구성

#### (4) 대체 여부
- **본질식별자**: 업무에 의해 만들어진 식별자 (주민번호, 사번 등)
- **인조식별자**: 인위적으로 만든 식별자 (일련번호 등)

### 주식별자 도출 기준

**선정 기준:**
1. 업무에서 자주 쓰는 속성일 것
2. 명칭, 이름 등은 피할 것
3. 속성의 수가 많지 않을 것

**특징 (4가지):**
1. **유일성**: 인스턴스를 유일하게 식별
2. **최소성**: 속성의 수가 최소
3. **불변성**: 가급적 변하지 않음
4. **존재성**: 값이 꼭 입력됨 (NOT NULL)

## 5. 데이터 모델의 이해

### ERD (Entity Relationship Diagram)
엔터티와 엔터티 간의 관계를 발견하고 이를 그림으로 표현하는 행위
→ **개념적 데이터 모델링의 결과물**

### 개념적 모델링 단계

**1단계: 엔터티 그리기**
- 중요한 엔터티를 왼쪽 상단에 배치
- 속성은 제외하고 엔터티만 표시

**2단계: 엔터티 배치**
- 적절한 위치에 배치

**3단계: 관계 설정**
- 서로 관계가 있는 엔터티끼리 선으로 연결

**4단계: 관계명 기술**
- 관계선에 관계명 표시

**5단계: 참여도(Cardinality) 기술**
- 1:1, 1:N, N:N 표시
- N 쪽에는 까치발(>) 표시

**6단계: 필수여부(Optionality) 기술**
- 필수 참여: `|`
- 선택 참여: `O`

### 논리적 모델링 단계

**1단계: 속성 입력**
- 각 엔터티 아래에 모든 속성 나열

**2단계: 식별자 선택**
- 각 엔터티에서 Primary Key 선택

**3단계: 정규화**
- 중복 데이터 제거
- 필요시 엔터티 분할

**4단계: 관계 설정 (FK)**
- Foreign Key로 엔터티 간 관계 연결

### 논리적 모델링 표기법

**IE 표기법**
```
직원
─────────────
직원ID (PK)
이름
나이
연봉
부서코드 (FK)
```

**Barker 표기법**
```
직원
─────────────
# 직원ID
O 이름
O 나이
O 연봉
O 부서코드 (FK)
```

- `#`: PK (식별자)
- `O`: 선택사항
- `*`: 필수사항
- FK가 `O`이면 비식별자관계, `#`이면 식별자관계

### 데이터베이스 3단계 구조

```
┌─────────────────────────────┐
│  외부 스키마 (External)      │ ← 여러 사용자 각각의 관점
├─────────────────────────────┤
│  개념 스키마 (Conceptual)    │ ← 통합적, 조직 전체의 DB 관점
├─────────────────────────────┤
│  내부 스키마 (Internal)      │ ← 데이터 물리 저장 구조
└─────────────────────────────┘
```

**독립성:**
- 외부-개념 스키마 독립성: 개념 스키마 변경 시 외부 스키마 영향 없음
- 개념-내부 스키마 독립성: 저장공간 추가 등 내부 변경 시 개념 스키마 영향 없음

## 데이터 모델링의 중요성

### 1. 파급효과
초반에 잘못 설계하면 나중에 전체를 엎어야 하는 상황 발생

### 2. 간결한 표현
ERD 등 설계도로 쉽게 의사소통 가능

### 3. 데이터 품질
제대로 설계해야 다음 문제들을 방지:

**문제 예시:**
- **데이터 중복**: 같은 정보가 여러 곳에 저장
- **비유연성**: 작은 프로세스 변화에도 구조 변경 필요
- **비일관성**: 데이터 불일치 발생

**해결 방법:**
```
변경 전 (중복 발생):
직원 테이블에 연락처, 주소를 여러 개 저장하려면?
→ 데이터 중복 발생

변경 후 (정규화):
직원 테이블
직원연락처 테이블 (직원ID, 구분코드, 연락처)
직원주소 테이블 (직원ID, 구분코드, 주소)
```

---

## 정리

### 핵심 개념
1. **엔터티**: 관리 대상이 되는 집합
2. **속성**: 엔터티의 특성을 나타내는 최소 단위
3. **관계**: 엔터티 간의 논리적 연관성
4. **식별자**: 인스턴스를 유일하게 구분하는 속성

### 모델링 흐름
```
요구사항 분석
    ↓
개념적 모델링 (ERD 작성)
    ↓
논리적 모델링 (속성, 식별자, 정규화)
    ↓
물리적 모델링 (DBMS 종속적 설계)
    ↓
데이터베이스 구축
```

## 1. 정규화

### 정규화란?

**데이터에 대한 중복을 제거하고 데이터가 관심사별로 처리되도록 엔터티를 쪼개 성능을 향상시키는 활동**

#### 성능 영향
- **입력/삭제/수정**: 성능 향상 ✓
- **조회**: 성능 향상 또는 저하 (상황에 따라 다름)

> **참고**: 정규화가 대체적으로 좋지만, 경우에 따라서는 반정규화가 더 이득일 수 있음

---

### 함수적 종속 (Functional Dependency)

**정의**: 어떤 기준 값(컬럼)에 의해 데이터가 종속되는 현상 → F(X) = Y

#### 예시

```
직원 테이블
┌──────────┬────────┬──────┬────────┬──────────┬──────────┐
│  아이디  │  이름  │ 나이 │  연봉  │  부서ID  │  부서명  │
├──────────┼────────┼──────┼────────┼──────────┼──────────┤
│ Emp001   │ 강태우 │  35  │  5000  │  D001    │  인사부  │
│ Emp002   │ 김형준 │  32  │  4800  │  D001    │  인사부  │
│ Emp003   │ 송송이 │  27  │  3400  │  D002    │  급여부  │
│ Emp004   │ 강태우 │  34  │  3700  │  D002    │  급여부  │
└──────────┴────────┴──────┴────────┴──────────┴──────────┘
```

**함수 종속 관계:**
- 결정자(아이디) → 종속자(이름, 나이, 연봉, 부서ID, 부서명)
- 결정자(부서ID) → 종속자(부서명)

---

### 정규화 과정

```
비정규형
    ↓ 도메인 원자성
1NF (1차 정규화)
    ↓ 부분 종속성 제거
2NF (2차 정규화)
    ↓ 이행 종속성 제거
3NF (3차 정규화)
    ↓ 결정자 제거
BCNF
    ↓ 다치 종속
4NF
    ↓ 조인 속성
5NF
```

> **실무에서는 주로 3NF까지 수행**

---

### 1차 정규화 (1NF) - 도메인 원자성

**규칙**: 엔터티에서 다중 속성이 있거나 하나의 속성에 여러 속성값이 있으면 원자값으로 쪼개기

#### 예시 1: 다중 값 분리

**변경 전:**
```
┌──────────┬────────┬────────┬─────────────────────────┬──────────┬──────────┐
│  직원ID  │  이름  │  연봉  │        연락처           │  부서ID  │  부서명  │
├──────────┼────────┼────────┼─────────────────────────┼──────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234,          │  D001    │  인사부  │
│          │        │        │ 062-123-1231            │          │          │
│ A0002    │ 정치호 │  6000  │ 062-222-2222            │  D002    │  급여부  │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333           │  D001    │  인사부  │
└──────────┴────────┴────────┴─────────────────────────┴──────────┴──────────┘
```

**변경 후:**
```
┌──────────┬────────┬────────┬───────────────┬──────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │  부서ID  │  부서명  │
├──────────┼────────┼────────┼───────────────┼──────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234 │  D001    │  인사부  │
│ A0001    │ 강홍정 │  5000  │ 062-123-1231  │  D001    │  인사부  │
│ A0002    │ 정치호 │  6000  │ 062-222-2222  │  D002    │  급여부  │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333 │  D001    │  인사부  │
└──────────┴────────┴────────┴───────────────┴──────────┴──────────┘
```

#### 예시 2: 복합 속성 분리

**변경 전:**
```
주소1: 중구 택지로 1번지
주소2: 서울 중앙 보훈기관 123호
```

**변경 후:**
```
주소: 중구 택지로 1번지
주소: 서울 중앙 보훈기관 123호
```

### 2차 정규화 (2NF) - 부분 종속성 제거

**규칙**: 식별자에 부분 종속하는 대상을 쪼개기 (완전 함수 종속이 되도록)

#### 예시

**변경 전:**
```
수강 테이블
┌────────┬────────┬────────┬──────────┬──────────┐
│  학번  │  과목  │  성적  │ 담임교수 │ 소속학과 │
├────────┼────────┼────────┼──────────┼──────────┤
│ C0001  │  국어  │   A    │  김철민  │교육융합과│
│ C0001  │  수학  │   A    │  김철민  │교육융합과│
│ C0001  │  영어  │   B    │  김철민  │교육융합과│
│ C0002  │  국어  │   B    │  신두희  │독일언어  │
│ C0002  │  수학  │   C    │  신두희  │독일언어  │
└────────┴────────┴────────┴──────────┴──────────┘
```

**함수 종속 분석:**
- 결정자(학번, 과목) → 종속자(성적, 담임교수, 소속학과)
- 결정자(학번) → 종속자(담임교수, 소속학과) ← **부분 종속 발생!**

**변경 후:**

```
학생 테이블
┌────────┬──────────┬──────────┐
│  학번  │ 담임교수 │ 소속학과 │
├────────┼──────────┼──────────┤
│ C0001  │  김철민  │교육융합과│
│ C0002  │  신두희  │독일언어  │
└────────┴──────────┴──────────┘

수강 테이블
┌────────┬────────┬────────┐
│  학번  │  과목  │  성적  │
├────────┼────────┼────────┤
│ C0001  │  국어  │   A    │
│ C0001  │  수학  │   A    │
│ C0001  │  영어  │   B    │
│ C0002  │  국어  │   B    │
│ C0002  │  수학  │   C    │
└────────┴────────┴────────┘
```

#### 2차 정규화 푸는 팁

**1단계**: 부분 종속하는 항목을 따로 분리
```
결정자(학번) → 종속자(담임교수, 소속학과)
```

**2단계**: 기존 엔터티에서 분리된 속성 제외
```
결정자(학번, 과목) → 종속자(성적)
```

**3단계**: 관계 설정

---

### 3차 정규화 (3NF) - 이행 종속성 제거

**규칙**: 엔터티에서 일반속성끼리 함수 종속이 발생하면 쪼개기

#### 예시

**변경 전:**
```
직원 테이블
┌──────────┬────────┬────────┬───────────────┬─────────────┬──────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │    주소     │  부서ID  │  부서명  │
├──────────┼────────┼────────┼───────────────┼─────────────┼──────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234 │ 중구 택지로 │  D001    │  인사부  │
│ A0002    │ 정치호 │  6000  │ 062-222-2222  │ 광주 광산구 │  D002    │  급여부  │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333 │ 서울 강남   │  D001    │  인사부  │
└──────────┴────────┴────────┴───────────────┴─────────────┴──────────┴──────────┘
```

**함수 종속 분석:**
- 결정자(직원ID) → 종속자(이름, 연봉, 연락처, 주소, 부서ID, 부서명) ← 2NF 만족
- 결정자(부서ID) → 종속자(부서명) ← **이행 종속 발생!**

**변경 후:**

```
직원 테이블
┌──────────┬────────┬────────┬───────────────┬─────────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │    주소     │  부서ID  │
├──────────┼────────┼────────┼───────────────┼─────────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234 │ 중구 택지로 │  D001    │
│ A0002    │ 정치호 │  6000  │ 062-222-2222  │ 광주 광산구 │  D002    │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333 │ 서울 강남   │  D001    │
└──────────┴────────┴────────┴───────────────┴─────────────┴──────────┘

부서 테이블
┌──────────┬──────────┐
│  부서ID  │  부서명  │
├──────────┼──────────┤
│  D001    │  인사부  │
│  D002    │  급여부  │
└──────────┴──────────┘
```

---

### 반정규화 (역정규화)

**정의**: 정규화한 데이터를 다시 합쳐서 중복되게 하거나 통합, 분리 등을 수행하는 모델링 방식

#### 반정규화 종류

1. **테이블 반정규화**: 테이블 병합, 테이블 분할, 테이블 추가 등
2. **컬럼 반정규화**: 중복 컬럼, 파생 컬럼, 이력 테이블 컬럼 추가 등
3. **관계 반정규화**: 중복 관계 추가

---

### 정규화 VS 반정규화

#### 조회 성능 비교

**예제**: hello1234 직원의 이름, 연락처, 주소를 가져오기

**정규화 상태 (3개 테이블):**
```sql
SELECT A.이름
     , B.연락처
     , C.주소
FROM 직원 A
   , 직원연락처 B
   , 직원주소 C
WHERE A.직원ID = B.직원ID
  AND B.직원ID = C.직원ID
  AND A.직원ID = 'hello1234';
```

**반정규화 상태 (1개 테이블):**
```sql
SELECT 이름
     , 연락처
     , 주소
FROM 직원
WHERE 직원ID = 'hello1234';
```

> **조회 성능**: 반정규화 > 정규화 (조인이 없으므로)

#### 입력 성능 비교

**예제**: hello1234 직원의 휴대폰 '010-5555-5555'를 추가

**정규화 상태:**
- 직원연락처 테이블에만 입력 ✓

**반정규화 상태:**
- 직원 테이블 전체에 기존 내용 중복하여 입력 (데이터 중복 발생)

> **입력 성능**: 정규화 > 반정규화

---

### 반정규화 대상 조사 방법

**절차:**

1. 반정규화가 필요한 대상을 찾기
2. 다른 방법이 없는지 검토하기
3. 달리 방법이 없다면 반정규화 적용

> **주의**: 반정규화는 데이터의 무결성을 깨뜨릴 위험이 있으므로 가급적 다른 방법을 먼저 고려

---

### 테이블 반정규화 예시

#### (1) 수직 분할

**목적**: 자주 사용하는 컬럼만 분리

**변경 전:**
```
직원 테이블 (전체)
┌──────────┬────────┬────────┬───────────────┬─────────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │    주소     │  부서ID  │
└──────────┴────────┴────────┴───────────────┴─────────────┴──────────┘
```

**변경 후:**
```
직원기본 테이블 (자주 조회)
┌──────────┬────────┬────────┐
│  직원ID  │  이름  │  연봉  │
└──────────┴────────┴────────┘

직원상세 테이블 (가끔 조회)
┌──────────┬───────────────┬─────────────┬──────────┐
│  직원ID  │    연락처     │    주소     │  부서ID  │
└──────────┴───────────────┴─────────────┴──────────┘
```

#### (2) 수평 분할

**목적**: 데이터를 특정 기준으로 나누어 저장 (예: 기간별, 지역별)

---

### 컬럼 반정규화 예시

#### 중복 컬럼 추가

**목적**: 조인을 감소시키기 위해 중복 컬럼 추가

**변경 전:**
```
직원 테이블
┌──────────┬────────┬────────┐
│  직원ID  │  이름  │  연봉  │
└──────────┴────────┴────────┘

직원연락처 테이블
┌──────────┬───────────────┐
│  직원ID  │    연락처     │
└──────────┴───────────────┘
```

**변경 후:**
```
직원 테이블 (연락처 컬럼 추가)
┌──────────┬────────┬────────┬───────────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │
└──────────┴────────┴────────┴───────────────┘

직원연락처 테이블 (원본 유지)
┌──────────┬───────────────┐
│  직원ID  │    연락처     │
└──────────┴───────────────┘
```

> **주의**: 직원연락처가 변경되면 직원 테이블도 함께 업데이트 필요

## 2. 관계와 조인의 이해

### 조인(Join)이란?

**정의**: 식별자를 상속해 이를 이용하여 데이터를 결합해 여러 엔터티에서 필요한 데이터를 한 번에 가져오는 것

#### 예시

**데이터:**
```
회원 테이블
┌──────────┬────────┐
│  회원ID  │  이름  │
├──────────┼────────┤
│  A0001   │ 동동일 │
│  A0002   │ 동동이 │
│  A0003   │ 동동삼 │
└──────────┴────────┘

회원연락처 테이블
┌──────────┬──────────┬───────────────┐
│  회원ID  │ 구분코드 │    연락처     │
├──────────┼──────────┼───────────────┤
│  A0001   │  휴대폰  │ 010-111-1111  │
│  A0001   │  집전화  │ 062-111-1111  │
│  A0002   │  집전화  │ 062-222-2222  │
│  A0004   │  휴대폰  │ 010-4444-4444 │
└──────────┴──────────┴───────────────┘
```

**질문**: 회원ID가 'A0001'인 회원의 이름과 휴대폰 번호는?

**답변**: 조인을 통해 두 테이블의 데이터를 결합하여 조회

```
ERD 표현:
회원 ────< 회원연락처
```

---

### 계층형 데이터 모델

**정의**: 계층구조를 가진 데이터를 저장한 모델로, 자기 자신의 엔터티와 관계가 발생하는 경우

#### 예시 1: 직원과 사수 정보

**ERD:**
```
직원
├─ 직원ID (PK)
├─ 이름
├─ 직급
└─ 상사ID (FK) ← 자기 참조
```

**데이터 구조:**
```
        김사장
          │
    ┌─────┴─────┐
  박부장      최부장
    │           │
  이과장      강과장
    │
  정대리
```

**테이블 예시:**
```
┌──────────┬────────┬────────┬──────────┐
│  직원ID  │  이름  │  직급  │  상사ID  │
├──────────┼────────┼────────┼──────────┤
│  E0001   │ 김사장 │  사장  │   NULL   │
│  E0002   │ 박부장 │  부장  │  E0001   │
│  E0003   │ 최부장 │  부장  │  E0001   │
│  E0004   │ 이과장 │  과장  │  E0002   │
│  E0005   │ 강과장 │  과장  │  E0003   │
│  E0006   │ 정대리 │  대리  │  E0004   │
└──────────┴────────┴────────┴──────────┘
```

#### 예시 2: 메뉴 정보

**계층 구조:**
```
메뉴1
├─ 메뉴1-1
│  ├─ 메뉴1-1-1
│  └─ 메뉴1-1-2
└─ 메뉴1-2
메뉴2
└─ 메뉴2-1
```

**계층 쿼리 예시**: Oracle의 `START WITH ... CONNECT BY` 또는 재귀 쿼리 사용

---

### 상호배타적 관계

**정의**: A와 B가 C집단에 소속되었지만, 서로 공통적인 부분이 없는 관계

#### 예시

**시나리오**: 고객은 개인고객 또는 법인고객 중 하나

```
ERD 표현:

        고객
         │
    ┌────┴────┐
    │         │
 개인고객  법인고객
```

**특징:**
- 한 고객은 개인고객이거나 법인고객이지, 둘 다일 수 없음
- 배타적 OR 관계

**테이블 구조:**
```
고객 테이블
┌──────────┬────────┬──────────┐
│  고객ID  │  이름  │ 고객유형 │
└──────────┴────────┴──────────┘

개인고객 테이블
┌──────────┬──────────────┬────────┐
│  고객ID  │  주민등록번호│ 성별   │
└──────────┴──────────────┴────────┘

법인고객 테이블
┌──────────┬──────────────┬────────┐
│  고객ID  │  사업자번호  │ 대표자 │
└──────────┴──────────────┴────────┘
```

## 3. 모델이 표현하는 트랜잭션의 이해

### 트랜잭션(Transaction)이란?

**정의**: 데이터베이스의 논리적인 연산 단위 혹은 논리적인 업무 단위

#### 트랜잭션의 특성 (ACID)

1. **원자성(Atomicity)**: 전부 실행되거나 전부 실행되지 않거나
2. **일관성(Consistency)**: 트랜잭션 전후 데이터 무결성 유지
3. **격리성(Isolation)**: 동시 실행되는 트랜잭션은 서로 영향 없음
4. **지속성(Durability)**: 완료된 트랜잭션은 영구적으로 반영

---

### 식별자 관계 VS 비식별자 관계

#### 식별자 관계 (강한 연결 관계)

**정의**: 외래키(빌려온 키)가 PK(식별자)의 일부분인 경우

**특징:**
- 부모 엔터티의 PK를 자식 엔터티의 PK로 사용
- 부모 없이 자식 존재 불가
- 강한 종속 관계

#### 비식별자 관계 (약한 연결 관계)

**정의**: 외래키(빌려온 키)가 PK(식별자)의 일부분이 아닌 경우

**특징:**
- 부모 엔터티의 PK를 자식 엔터티의 일반 속성(FK)으로 사용
- 부모 없이 자식 독립적 존재 가능
- 약한 종속 관계

---

### ERD 표기법 비교

#### IE 표기법

```
직원
├─────────────
│ 직원ID (PK)
│ 이름
│ 부서ID (FK)
└─────────────
      │ (실선)
      │ 비식별자 관계
      ↓
부서
├─────────────
│ 부서ID (PK)
│ 부서명
└─────────────

직원
├─────────────
│ 직원ID (PK)
│ 이름
└─────────────
      │
      │ (점선)
      │ 식별자 관계
      ↓
직원연락처
├─────────────
│ 직원ID (PK, FK)
│ 구분코드 (PK)
│ 연락처
└─────────────
```

#### Barker 표기법

```
직원
├─────────────
│ # 직원ID
│ * 이름
│ * 부서ID (FK)
└─────────────
      │
      │ (실선, FK가 *)
      │ 비식별자 관계
      ↓
부서
├─────────────
│ # 부서ID
│ * 부서명
└─────────────

직원
├─────────────
│ # 직원ID
│ * 이름
└─────────────
      │
      │ (실선, FK가 #)
      │ 식별자 관계
      ↓
직원연락처
├─────────────
│ # 직원ID (FK)
│ # 구분코드
│ * 연락처
└─────────────
```

**기호 설명:**
- `#`: PK (Primary Key)
- `*`: 필수 속성 (NOT NULL)
- `O`: 선택 속성 (NULL 허용)

---

### 실무 예제: 쇼핑몰 주문 시스템

**요구사항:**
- 고객이 주문을 하면 주문정보 저장
- 하나의 주문에 여러 상품이 포함됨 → 주문상세정보 저장

**ERD:**
```
고객 ────< 주문 >────< 주문상세 ────< 상품
```

**테이블 구조:**

```
주문 테이블
┌──────────┬──────────┬────────────┐
│  주문ID  │  고객ID  │  주문일시  │
│   (PK)   │   (FK)   │            │
└──────────┴──────────┴────────────┘

주문상세 테이블
┌──────────┬──────────┬──────────┬────────┐
│  주문ID  │ 상세번호 │  상품ID  │  수량  │
│(PK, FK)  │   (PK)   │   (FK)   │        │
└──────────┴──────────┴──────────┴────────┘
```

**관계:**
- 주문 ↔ 주문상세: **식별자 관계** (주문 없이 주문상세 존재 불가)
- 고객 ↔ 주문: **비식별자 관계** (주문은 독립적으로 존재 가능)

## 4. NULL 속성의 이해

### NULL이란?

**정의**: 아직 정해지지 않은 값을 의미

> **주의**: NULL은 0이나 공백('')과 다름!

---

### NULL이 필요한 이유

#### (1) 미확정 값 표현

**시나리오**: 새로운 회원 가입 시 주소 정보 미입력

```
입력받은 값:
- 고객ID: TEST
- 고객명: TEST
- 휴대폰번호: 01011112222
- 주소: (입력 안 함)
```

**테이블:**
```
┌──────────┬────────┬───────────────┬────────┐
│  고객ID  │  이름  │   휴대폰번호  │  주소  │
├──────────┼────────┼───────────────┼────────┤
│  TEST    │  TEST  │ 01011112222   │  NULL  │
└──────────┴────────┴───────────────┴────────┘
```

> **NULL 사용**: 주소 정보가 없음을 명시적으로 표현

#### (2) 테이블 구조 유지

**특징**: 테이블은 행 × 열 형태를 유지해야 함

```
┌──────────┬────────┬───────────────┬────────┐
│  고객ID  │  이름  │   휴대폰번호  │  주소  │
├──────────┼────────┼───────────────┼────────┤
│  C0001   │ 홍길동 │ 010-1111-1111 │ 서울시 │
│  C0002   │ 김철수 │ 010-2222-2222 │ 부산시 │
│  TEST    │  TEST  │ 01011112222   │  NULL  │ ← 주소 없어도 행 유지
└──────────┴────────┴───────────────┴────────┘
```

> **중요**: NULL 값을 넣어서 테이블의 행×열 형태를 유지!

---

### NULL과 관계 표기

#### IE 표기법

```
직원
├─────────────
│ 직원ID (PK)
│ 이름
│ 부서ID (FK)
└─────────────
      │O
      │ (선택 참여 - NULL 허용)
      ↓
부서
├─────────────
│ 부서ID (PK)
│ 부서명
└─────────────
```

- `O`: 선택 참여 (NULL 가능)
- `|`: 필수 참여 (NOT NULL)

#### Barker 표기법

```
직원
├─────────────
│ # 직원ID
│ * 이름
│ O 부서ID (FK) ← O는 NULL 허용
└─────────────

부서
├─────────────
│ # 부서ID
│ * 부서명
└─────────────
```

- `*`: 필수 속성 (NOT NULL)
- `O`: 선택 속성 (NULL 허용)

---

### NULL 처리 시 주의사항

1. **NULL과 연산**: NULL과 어떤 값을 연산하면 결과는 NULL
   ```sql
   SELECT 100 + NULL;  -- 결과: NULL
   SELECT NULL = NULL; -- 결과: NULL (TRUE 아님!)
   ```

2. **NULL 비교**: `IS NULL` 또는 `IS NOT NULL` 사용
   ```sql
   SELECT * FROM 고객 WHERE 주소 IS NULL;     -- 올바름
   SELECT * FROM 고객 WHERE 주소 = NULL;      -- 잘못됨
   ```

3. **NULL 처리 함수**: `NVL`, `ISNULL`, `COALESCE` 등
   ```sql
   SELECT COALESCE(주소, '주소없음') FROM 고객;
   ```

## 5. 본질식별자 VS 인조식별자

### 식별자 분류 (재정리)

| 분류 기준 | 종류 1 | 종류 2 |
|-----------|--------|--------|
| **(1) 대표성 여부** | 주식별자 | 보조식별자 |
| **(2) 스스로 생성 여부** | 내부식별자 | 외부식별자 |
| **(3) 단일 속성 여부** | 단일식별자 | 복합식별자 |
| **(4) 대체 여부** | **본질식별자** | **인조식별자** |

---

### 본질식별자 (Natural Identifier)

**정의**: 업무에 의해 생성된 식별자

**특징:**
- 비즈니스 로직에서 자연스럽게 도출
- 의미 있는 값
- 업무적으로 유일성 보장

**예시:**
```
직원 테이블
├─────────────────────
│ 주민등록번호 (PK) ← 본질식별자
│ 이름
│ 연봉
└─────────────────────

상품 테이블
├─────────────────────
│ 상품코드 (PK) ← 본질식별자
│ 상품명
│ 가격
└─────────────────────
```

**장점:**
- 업무적으로 의미가 명확
- 별도의 값 생성 불필요

**단점:**
- 업무 규칙 변경 시 식별자 변경 필요
- 복합키가 될 가능성 높음
- 자식 테이블로 전파 시 컬럼 수 증가

---

### 인조식별자 (Surrogate Identifier)

**정의**: 편의를 위해 인위적으로 만든 식별자

**특징:**
- 시스템에서 자동 생성 (일련번호, SEQUENCE 등)
- 업무적 의미 없음
- 단순한 구조

**예시:**
```
직원 테이블 (인조식별자 사용)
├─────────────────────
│ 직원ID (PK) ← 인조식별자 (일련번호)
│ 주민등록번호 (UK)
│ 이름
│ 연봉
└─────────────────────

직원연락처 테이블
├─────────────────────
│ 직원ID (PK, FK)
│ 구분코드 (PK)
│ 연락처
└─────────────────────
```

**다른 예시:**
```
직원연락처이력 테이블 (방법 1 - 본질식별자)
├─────────────────────
│ 직원ID (PK, FK)
│ 구분코드 (PK, FK)
│ 순번 (PK)
│ 연락처
└─────────────────────

직원연락처이력 테이블 (방법 2 - 인조식별자)
├─────────────────────
│ 이력일련번호 (PK) ← 인조식별자
│ 직원ID (FK)
│ 구분코드 (FK)
│ 순번
│ 연락처
└─────────────────────
```

**장점:**
- 단순한 구조 (단일 컬럼 PK)
- 업무 변경에 영향 없음
- 자식 테이블로 전파 시 컬럼 수 최소화
- 성능상 유리 (단일 컬럼 인덱스)

**단점:**
- 업무적 의미 없음
- 별도의 인덱스 관리 필요
- 중복 데이터 입력 가능성

---

### 본질식별자 VS 인조식별자 비교

| 구분 | 본질식별자 | 인조식별자 |
|------|-----------|-----------|
| **생성 방식** | 업무에서 자연 발생 | 시스템이 인위 생성 |
| **의미** | 업무적 의미 있음 | 업무적 의미 없음 |
| **구조** | 복합키 가능성 높음 | 주로 단일 컬럼 |
| **변경 가능성** | 업무 변경 시 영향 받음 | 업무 변경에 독립적 |
| **성능** | 복합키 시 성능 저하 | 단일키로 성능 우수 |
| **관리** | 업무 규칙 준수 필요 | 시스템 자동 관리 |
| **자식 전파** | 컬럼 수 증가 | 컬럼 수 최소 |

---

### 실무 선택 가이드

#### 본질식별자를 사용하는 경우

1. 업무적으로 유일성이 명확한 경우
   - 주민등록번호, 사업자번호, 차량번호 등

2. 외부 시스템과 연동되는 경우
   - 표준 코드, 공통 코드 등

3. 마스터 테이블
   - 코드 테이블, 참조 테이블 등

#### 인조식별자를 사용하는 경우

1. 복합키가 필요한 경우
   - 주문상세, 이력 테이블 등

2. 자주 변경될 가능성이 있는 경우
   - 회원 ID, 이메일 등

3. 성능이 중요한 경우
   - 대용량 트랜잭션 테이블

4. 자식 테이블이 많은 경우
   - PK 전파 시 구조 단순화 필요

---

### 복합 사용 예시

**권장 패턴**: 인조식별자를 PK로, 본질식별자를 UK(Unique Key)로 설정

```
회원 테이블
├─────────────────────
│ 회원번호 (PK) ← 인조식별자 (시스템 생성)
│ 이메일 (UK) ← 본질식별자 (업무적 유일)
│ 이름
│ 가입일
└─────────────────────
```

**장점:**
- 시스템 성능 확보 (단일 PK)
- 업무 유일성 보장 (UK)
- 유연한 데이터 관리

## 정리 및 핵심 요약

### 1. 정규화

**핵심 개념:**
- 데이터 중복 제거 및 관심사 분리
- 1NF(원자성) → 2NF(부분종속제거) → 3NF(이행종속제거)
- 실무에서는 주로 3NF까지 수행

**성능 영향:**
- 입력/수정/삭제: 성능 향상 ✓
- 조회: 상황에 따라 다름

### 2. 반정규화

**핵심 개념:**
- 조회 성능 향상을 위해 의도적으로 중복 허용
- 데이터 무결성 위험 존재
- 다른 방법 검토 후 최후 수단으로 사용

**적용 방법:**
- 테이블 병합/분할
- 중복 컬럼 추가
- 파생 컬럼 추가

### 3. 조인

**핵심 개념:**
- 여러 테이블의 데이터를 결합
- FK를 통한 테이블 간 연결
- 계층형 데이터: 자기 참조 관계

### 4. 식별자 관계

**식별자 관계 (강한 종속):**
- FK가 PK의 일부
- 부모 없이 자식 존재 불가

**비식별자 관계 (약한 종속):**
- FK가 일반 속성
- 부모와 독립적 존재 가능

### 5. NULL

**핵심 개념:**
- 미확정 값 표현
- 테이블 구조 유지
- `IS NULL` 또는 `IS NOT NULL`로 비교

### 6. 본질식별자 VS 인조식별자

**본질식별자:**
- 업무에서 자연 발생
- 의미 있지만 복잡할 수 있음

**인조식별자:**
- 시스템이 생성
- 단순하고 성능 우수

**권장 패턴:**
- 인조식별자(PK) + 본질식별자(UK)

## 실무 적용 팁

1. **정규화 우선, 반정규화는 신중히**
   - 먼저 완전히 정규화
   - 성능 문제 발생 시에만 반정규화 검토

2. **식별자 관계는 비즈니스 의존성 고려**
   - 강한 의존: 식별자 관계
   - 약한 의존: 비식별자 관계

3. **NULL 허용은 최소화**
   - 가급적 NOT NULL 제약조건 사용
   - 필요한 경우에만 NULL 허용

4. **인조식별자 활용 권장**
   - 대부분의 경우 인조식별자가 유리
   - 마스터/코드 테이블은 본질식별자 고려

5. **ERD 표기법 일관성 유지**
   - 프로젝트 내에서 IE 또는 Barker 중 하나로 통일
   - 관계선, 식별자 표기 규칙 준수
