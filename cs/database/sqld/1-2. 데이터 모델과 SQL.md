## 1. 정규화

### 정규화란?

**데이터에 대한 중복을 제거하고 데이터가 관심사별로 처리되도록 엔터티를 쪼개 성능을 향상시키는 활동**

#### 성능 영향
- **입력/삭제/수정**: 성능 향상 ✓
- **조회**: 성능 향상 또는 저하 (상황에 따라 다름)

> **참고**: 정규화가 대체적으로 좋지만, 경우에 따라서는 반정규화가 더 이득일 수 있음

---

### 함수적 종속 (Functional Dependency)

**정의**: 어떤 기준 값(컬럼)에 의해 데이터가 종속되는 현상 → F(X) = Y

#### 예시

```
직원 테이블
┌──────────┬────────┬──────┬────────┬──────────┬──────────┐
│  아이디  │  이름  │ 나이 │  연봉  │  부서ID  │  부서명  │
├──────────┼────────┼──────┼────────┼──────────┼──────────┤
│ Emp001   │ 강태우 │  35  │  5000  │  D001    │  인사부  │
│ Emp002   │ 김형준 │  32  │  4800  │  D001    │  인사부  │
│ Emp003   │ 송송이 │  27  │  3400  │  D002    │  급여부  │
│ Emp004   │ 강태우 │  34  │  3700  │  D002    │  급여부  │
└──────────┴────────┴──────┴────────┴──────────┴──────────┘
```

**함수 종속 관계:**
- 결정자(아이디) → 종속자(이름, 나이, 연봉, 부서ID, 부서명)
- 결정자(부서ID) → 종속자(부서명)

---

### 정규화 과정

```
비정규형
    ↓ 도메인 원자성
1NF (1차 정규화)
    ↓ 부분 종속성 제거
2NF (2차 정규화)
    ↓ 이행 종속성 제거
3NF (3차 정규화)
    ↓ 결정자 제거
BCNF
    ↓ 다치 종속
4NF
    ↓ 조인 속성
5NF
```

> **실무에서는 주로 3NF까지 수행**

---

### 1차 정규화 (1NF) - 도메인 원자성

**규칙**: 엔터티에서 다중 속성이 있거나 하나의 속성에 여러 속성값이 있으면 원자값으로 쪼개기

#### 예시 1: 다중 값 분리

**변경 전:**
```
┌──────────┬────────┬────────┬─────────────────────────┬──────────┬──────────┐
│  직원ID  │  이름  │  연봉  │        연락처           │  부서ID  │  부서명  │
├──────────┼────────┼────────┼─────────────────────────┼──────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234,          │  D001    │  인사부  │
│          │        │        │ 062-123-1231            │          │          │
│ A0002    │ 정치호 │  6000  │ 062-222-2222            │  D002    │  급여부  │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333           │  D001    │  인사부  │
└──────────┴────────┴────────┴─────────────────────────┴──────────┴──────────┘
```

**변경 후:**
```
┌──────────┬────────┬────────┬───────────────┬──────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │  부서ID  │  부서명  │
├──────────┼────────┼────────┼───────────────┼──────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234 │  D001    │  인사부  │
│ A0001    │ 강홍정 │  5000  │ 062-123-1231  │  D001    │  인사부  │
│ A0002    │ 정치호 │  6000  │ 062-222-2222  │  D002    │  급여부  │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333 │  D001    │  인사부  │
└──────────┴────────┴────────┴───────────────┴──────────┴──────────┘
```

#### 예시 2: 복합 속성 분리

**변경 전:**
```
주소1: 중구 택지로 1번지
주소2: 서울 중앙 보훈기관 123호
```

**변경 후:**
```
주소: 중구 택지로 1번지
주소: 서울 중앙 보훈기관 123호
```

### 2차 정규화 (2NF) - 부분 종속성 제거

**규칙**: 식별자에 부분 종속하는 대상을 쪼개기 (완전 함수 종속이 되도록)

#### 예시

**변경 전:**
```
수강 테이블
┌────────┬────────┬────────┬──────────┬──────────┐
│  학번  │  과목  │  성적  │ 담임교수 │ 소속학과 │
├────────┼────────┼────────┼──────────┼──────────┤
│ C0001  │  국어  │   A    │  김철민  │교육융합과│
│ C0001  │  수학  │   A    │  김철민  │교육융합과│
│ C0001  │  영어  │   B    │  김철민  │교육융합과│
│ C0002  │  국어  │   B    │  신두희  │독일언어  │
│ C0002  │  수학  │   C    │  신두희  │독일언어  │
└────────┴────────┴────────┴──────────┴──────────┘
```

**함수 종속 분석:**
- 결정자(학번, 과목) → 종속자(성적, 담임교수, 소속학과)
- 결정자(학번) → 종속자(담임교수, 소속학과) ← **부분 종속 발생!**

**변경 후:**

```
학생 테이블
┌────────┬──────────┬──────────┐
│  학번  │ 담임교수 │ 소속학과 │
├────────┼──────────┼──────────┤
│ C0001  │  김철민  │교육융합과│
│ C0002  │  신두희  │독일언어  │
└────────┴──────────┴──────────┘

수강 테이블
┌────────┬────────┬────────┐
│  학번  │  과목  │  성적  │
├────────┼────────┼────────┤
│ C0001  │  국어  │   A    │
│ C0001  │  수학  │   A    │
│ C0001  │  영어  │   B    │
│ C0002  │  국어  │   B    │
│ C0002  │  수학  │   C    │
└────────┴────────┴────────┘
```

#### 2차 정규화 푸는 팁

**1단계**: 부분 종속하는 항목을 따로 분리
```
결정자(학번) → 종속자(담임교수, 소속학과)
```

**2단계**: 기존 엔터티에서 분리된 속성 제외
```
결정자(학번, 과목) → 종속자(성적)
```

**3단계**: 관계 설정

---

### 3차 정규화 (3NF) - 이행 종속성 제거

**규칙**: 엔터티에서 일반속성끼리 함수 종속이 발생하면 쪼개기

#### 예시

**변경 전:**
```
직원 테이블
┌──────────┬────────┬────────┬───────────────┬─────────────┬──────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │    주소     │  부서ID  │  부서명  │
├──────────┼────────┼────────┼───────────────┼─────────────┼──────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234 │ 중구 택지로 │  D001    │  인사부  │
│ A0002    │ 정치호 │  6000  │ 062-222-2222  │ 광주 광산구 │  D002    │  급여부  │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333 │ 서울 강남   │  D001    │  인사부  │
└──────────┴────────┴────────┴───────────────┴─────────────┴──────────┴──────────┘
```

**함수 종속 분석:**
- 결정자(직원ID) → 종속자(이름, 연봉, 연락처, 주소, 부서ID, 부서명) ← 2NF 만족
- 결정자(부서ID) → 종속자(부서명) ← **이행 종속 발생!**

**변경 후:**

```
직원 테이블
┌──────────┬────────┬────────┬───────────────┬─────────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │    주소     │  부서ID  │
├──────────┼────────┼────────┼───────────────┼─────────────┼──────────┤
│ A0001    │ 강홍정 │  5000  │ 010-1231-1234 │ 중구 택지로 │  D001    │
│ A0002    │ 정치호 │  6000  │ 062-222-2222  │ 광주 광산구 │  D002    │
│ A0003    │ 강태우 │  7000  │ 010-3333-3333 │ 서울 강남   │  D001    │
└──────────┴────────┴────────┴───────────────┴─────────────┴──────────┘

부서 테이블
┌──────────┬──────────┐
│  부서ID  │  부서명  │
├──────────┼──────────┤
│  D001    │  인사부  │
│  D002    │  급여부  │
└──────────┴──────────┘
```

### 반정규화 (역정규화)

**정의**: 정규화한 데이터를 다시 합쳐서 중복되게 하거나 통합, 분리 등을 수행하는 모델링 방식

#### 반정규화 종류

1. **테이블 반정규화**: 테이블 병합, 테이블 분할, 테이블 추가 등
2. **컬럼 반정규화**: 중복 컬럼, 파생 컬럼, 이력 테이블 컬럼 추가 등
3. **관계 반정규화**: 중복 관계 추가

---

### 정규화 VS 반정규화

#### 조회 성능 비교

**예제**: hello1234 직원의 이름, 연락처, 주소를 가져오기

**정규화 상태 (3개 테이블):**
```sql
SELECT A.이름
     , B.연락처
     , C.주소
FROM 직원 A
   , 직원연락처 B
   , 직원주소 C
WHERE A.직원ID = B.직원ID
  AND B.직원ID = C.직원ID
  AND A.직원ID = 'hello1234';
```

**반정규화 상태 (1개 테이블):**
```sql
SELECT 이름
     , 연락처
     , 주소
FROM 직원
WHERE 직원ID = 'hello1234';
```

> **조회 성능**: 반정규화 > 정규화 (조인이 없으므로)

#### 입력 성능 비교

**예제**: hello1234 직원의 휴대폰 '010-5555-5555'를 추가

**정규화 상태:**
- 직원연락처 테이블에만 입력 ✓

**반정규화 상태:**
- 직원 테이블 전체에 기존 내용 중복하여 입력 (데이터 중복 발생)

> **입력 성능**: 정규화 > 반정규화

---

### 반정규화 대상 조사 방법

**절차:**

1. 반정규화가 필요한 대상을 찾기
2. 다른 방법이 없는지 검토하기
3. 달리 방법이 없다면 반정규화 적용

> **주의**: 반정규화는 데이터의 무결성을 깨뜨릴 위험이 있으므로 가급적 다른 방법을 먼저 고려

---

### 테이블 반정규화 예시

#### (1) 수직 분할

**목적**: 자주 사용하는 컬럼만 분리

**변경 전:**
```
직원 테이블 (전체)
┌──────────┬────────┬────────┬───────────────┬─────────────┬──────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │    주소     │  부서ID  │
└──────────┴────────┴────────┴───────────────┴─────────────┴──────────┘
```

**변경 후:**
```
직원기본 테이블 (자주 조회)
┌──────────┬────────┬────────┐
│  직원ID  │  이름  │  연봉  │
└──────────┴────────┴────────┘

직원상세 테이블 (가끔 조회)
┌──────────┬───────────────┬─────────────┬──────────┐
│  직원ID  │    연락처     │    주소     │  부서ID  │
└──────────┴───────────────┴─────────────┴──────────┘
```

#### (2) 수평 분할

**목적**: 데이터를 특정 기준으로 나누어 저장 (예: 기간별, 지역별)

---

### 컬럼 반정규화 예시

#### 중복 컬럼 추가

**목적**: 조인을 감소시키기 위해 중복 컬럼 추가

**변경 전:**
```
직원 테이블
┌──────────┬────────┬────────┐
│  직원ID  │  이름  │  연봉  │
└──────────┴────────┴────────┘

직원연락처 테이블
┌──────────┬───────────────┐
│  직원ID  │    연락처     │
└──────────┴───────────────┘
```

**변경 후:**
```
직원 테이블 (연락처 컬럼 추가)
┌──────────┬────────┬────────┬───────────────┐
│  직원ID  │  이름  │  연봉  │    연락처     │
└──────────┴────────┴────────┴───────────────┘

직원연락처 테이블 (원본 유지)
┌──────────┬───────────────┐
│  직원ID  │    연락처     │
└──────────┴───────────────┘
```

> **주의**: 직원연락처가 변경되면 직원 테이블도 함께 업데이트 필요

## 2. 관계와 조인의 이해

### 조인(Join)이란?

**정의**: 식별자를 상속해 이를 이용하여 데이터를 결합해 여러 엔터티에서 필요한 데이터를 한 번에 가져오는 것

#### 예시

**데이터:**
```
회원 테이블
┌──────────┬────────┐
│  회원ID  │  이름  │
├──────────┼────────┤
│  A0001   │ 동동일 │
│  A0002   │ 동동이 │
│  A0003   │ 동동삼 │
└──────────┴────────┘

회원연락처 테이블
┌──────────┬──────────┬───────────────┐
│  회원ID  │ 구분코드 │    연락처     │
├──────────┼──────────┼───────────────┤
│  A0001   │  휴대폰  │ 010-111-1111  │
│  A0001   │  집전화  │ 062-111-1111  │
│  A0002   │  집전화  │ 062-222-2222  │
│  A0004   │  휴대폰  │ 010-4444-4444 │
└──────────┴──────────┴───────────────┘
```

**질문**: 회원ID가 'A0001'인 회원의 이름과 휴대폰 번호는?

**답변**: 조인을 통해 두 테이블의 데이터를 결합하여 조회

```
ERD 표현:
회원 ────< 회원연락처
```

---

### 계층형 데이터 모델

**정의**: 계층구조를 가진 데이터를 저장한 모델로, 자기 자신의 엔터티와 관계가 발생하는 경우

#### 예시 1: 직원과 사수 정보

**ERD:**
```
직원
├─ 직원ID (PK)
├─ 이름
├─ 직급
└─ 상사ID (FK) ← 자기 참조
```

**데이터 구조:**
```
        김사장
          │
    ┌─────┴─────┐
  박부장      최부장
    │           │
  이과장      강과장
    │
  정대리
```

**테이블 예시:**
```
┌──────────┬────────┬────────┬──────────┐
│  직원ID  │  이름  │  직급  │  상사ID  │
├──────────┼────────┼────────┼──────────┤
│  E0001   │ 김사장 │  사장  │   NULL   │
│  E0002   │ 박부장 │  부장  │  E0001   │
│  E0003   │ 최부장 │  부장  │  E0001   │
│  E0004   │ 이과장 │  과장  │  E0002   │
│  E0005   │ 강과장 │  과장  │  E0003   │
│  E0006   │ 정대리 │  대리  │  E0004   │
└──────────┴────────┴────────┴──────────┘
```

#### 예시 2: 메뉴 정보

**계층 구조:**
```
메뉴1
├─ 메뉴1-1
│  ├─ 메뉴1-1-1
│  └─ 메뉴1-1-2
└─ 메뉴1-2
메뉴2
└─ 메뉴2-1
```

**계층 쿼리 예시**: Oracle의 `START WITH ... CONNECT BY` 또는 재귀 쿼리 사용

---

### 상호배타적 관계

**정의**: A와 B가 C집단에 소속되었지만, 서로 공통적인 부분이 없는 관계

#### 예시

**시나리오**: 고객은 개인고객 또는 법인고객 중 하나

```
ERD 표현:

        고객
         │
    ┌────┴────┐
    │         │
 개인고객  법인고객
```

**특징:**
- 한 고객은 개인고객이거나 법인고객이지, 둘 다일 수 없음
- 배타적 OR 관계

**테이블 구조:**
```
고객 테이블
┌──────────┬────────┬──────────┐
│  고객ID  │  이름  │ 고객유형 │
└──────────┴────────┴──────────┘

개인고객 테이블
┌──────────┬──────────────┬────────┐
│  고객ID  │  주민등록번호│ 성별   │
└──────────┴──────────────┴────────┘

법인고객 테이블
┌──────────┬──────────────┬────────┐
│  고객ID  │  사업자번호  │ 대표자 │
└──────────┴──────────────┴────────┘
```

## 3. 모델이 표현하는 트랜잭션의 이해

### 트랜잭션(Transaction)이란?

**정의**: 데이터베이스의 논리적인 연산 단위 혹은 논리적인 업무 단위

#### 트랜잭션의 특성 (ACID)

1. **원자성(Atomicity)**: 전부 실행되거나 전부 실행되지 않거나
2. **일관성(Consistency)**: 트랜잭션 전후 데이터 무결성 유지
3. **격리성(Isolation)**: 동시 실행되는 트랜잭션은 서로 영향 없음
4. **지속성(Durability)**: 완료된 트랜잭션은 영구적으로 반영

---

### 식별자 관계 VS 비식별자 관계

#### 식별자 관계 (강한 연결 관계)

**정의**: 외래키(빌려온 키)가 PK(식별자)의 일부분인 경우

**특징:**
- 부모 엔터티의 PK를 자식 엔터티의 PK로 사용
- 부모 없이 자식 존재 불가
- 강한 종속 관계

#### 비식별자 관계 (약한 연결 관계)

**정의**: 외래키(빌려온 키)가 PK(식별자)의 일부분이 아닌 경우

**특징:**
- 부모 엔터티의 PK를 자식 엔터티의 일반 속성(FK)으로 사용
- 부모 없이 자식 독립적 존재 가능
- 약한 종속 관계

---

### ERD 표기법 비교

#### IE 표기법

```
직원
├─────────────
│ 직원ID (PK)
│ 이름
│ 부서ID (FK)
└─────────────
      │ (실선)
      │ 비식별자 관계
      ↓
부서
├─────────────
│ 부서ID (PK)
│ 부서명
└─────────────

직원
├─────────────
│ 직원ID (PK)
│ 이름
└─────────────
      │
      │ (점선)
      │ 식별자 관계
      ↓
직원연락처
├─────────────
│ 직원ID (PK, FK)
│ 구분코드 (PK)
│ 연락처
└─────────────
```

#### Barker 표기법

```
직원
├─────────────
│ # 직원ID
│ * 이름
│ * 부서ID (FK)
└─────────────
      │
      │ (실선, FK가 *)
      │ 비식별자 관계
      ↓
부서
├─────────────
│ # 부서ID
│ * 부서명
└─────────────

직원
├─────────────
│ # 직원ID
│ * 이름
└─────────────
      │
      │ (실선, FK가 #)
      │ 식별자 관계
      ↓
직원연락처
├─────────────
│ # 직원ID (FK)
│ # 구분코드
│ * 연락처
└─────────────
```

**기호 설명:**
- `#`: PK (Primary Key)
- `*`: 필수 속성 (NOT NULL)
- `O`: 선택 속성 (NULL 허용)

---

### 실무 예제: 쇼핑몰 주문 시스템

**요구사항:**
- 고객이 주문을 하면 주문정보 저장
- 하나의 주문에 여러 상품이 포함됨 → 주문상세정보 저장

**ERD:**
```
고객 ────< 주문 >────< 주문상세 ────< 상품
```

**테이블 구조:**

```
주문 테이블
┌──────────┬──────────┬────────────┐
│  주문ID  │  고객ID  │  주문일시  │
│   (PK)   │   (FK)   │            │
└──────────┴──────────┴────────────┘

주문상세 테이블
┌──────────┬──────────┬──────────┬────────┐
│  주문ID  │ 상세번호 │  상품ID  │  수량  │
│(PK, FK)  │   (PK)   │   (FK)   │        │
└──────────┴──────────┴──────────┴────────┘
```

**관계:**
- 주문 ↔ 주문상세: **식별자 관계** (주문 없이 주문상세 존재 불가)
- 고객 ↔ 주문: **비식별자 관계** (주문은 독립적으로 존재 가능)

## 4. NULL 속성의 이해

### NULL이란?

**정의**: 아직 정해지지 않은 값을 의미

> **주의**: NULL은 0이나 공백('')과 다름!

---

### NULL이 필요한 이유

#### (1) 미확정 값 표현

**시나리오**: 새로운 회원 가입 시 주소 정보 미입력

```
입력받은 값:
- 고객ID: TEST
- 고객명: TEST
- 휴대폰번호: 01011112222
- 주소: (입력 안 함)
```

**테이블:**
```
┌──────────┬────────┬───────────────┬────────┐
│  고객ID  │  이름  │   휴대폰번호  │  주소  │
├──────────┼────────┼───────────────┼────────┤
│  TEST    │  TEST  │ 01011112222   │  NULL  │
└──────────┴────────┴───────────────┴────────┘
```

> **NULL 사용**: 주소 정보가 없음을 명시적으로 표현

#### (2) 테이블 구조 유지

**특징**: 테이블은 행 × 열 형태를 유지해야 함

```
┌──────────┬────────┬───────────────┬────────┐
│  고객ID  │  이름  │   휴대폰번호  │  주소  │
├──────────┼────────┼───────────────┼────────┤
│  C0001   │ 홍길동 │ 010-1111-1111 │ 서울시 │
│  C0002   │ 김철수 │ 010-2222-2222 │ 부산시 │
│  TEST    │  TEST  │ 01011112222   │  NULL  │ ← 주소 없어도 행 유지
└──────────┴────────┴───────────────┴────────┘
```

> **중요**: NULL 값을 넣어서 테이블의 행×열 형태를 유지!

---

### NULL과 관계 표기

#### IE 표기법

```
직원
├─────────────
│ 직원ID (PK)
│ 이름
│ 부서ID (FK)
└─────────────
      │O
      │ (선택 참여 - NULL 허용)
      ↓
부서
├─────────────
│ 부서ID (PK)
│ 부서명
└─────────────
```

- `O`: 선택 참여 (NULL 가능)
- `|`: 필수 참여 (NOT NULL)

#### Barker 표기법

```
직원
├─────────────
│ # 직원ID
│ * 이름
│ O 부서ID (FK) ← O는 NULL 허용
└─────────────

부서
├─────────────
│ # 부서ID
│ * 부서명
└─────────────
```

- `*`: 필수 속성 (NOT NULL)
- `O`: 선택 속성 (NULL 허용)

---

### NULL 처리 시 주의사항

1. **NULL과 연산**: NULL과 어떤 값을 연산하면 결과는 NULL
   ```sql
   SELECT 100 + NULL;  -- 결과: NULL
   SELECT NULL = NULL; -- 결과: NULL (TRUE 아님!)
   ```

2. **NULL 비교**: `IS NULL` 또는 `IS NOT NULL` 사용
   ```sql
   SELECT * FROM 고객 WHERE 주소 IS NULL;     -- 올바름
   SELECT * FROM 고객 WHERE 주소 = NULL;      -- 잘못됨
   ```

3. **NULL 처리 함수**: `NVL`, `ISNULL`, `COALESCE` 등
   ```sql
   SELECT COALESCE(주소, '주소없음') FROM 고객;
   ```

## 5. 본질식별자 VS 인조식별자

### 식별자 분류 (재정리)

| 분류 기준 | 종류 1 | 종류 2 |
|-----------|--------|--------|
| **(1) 대표성 여부** | 주식별자 | 보조식별자 |
| **(2) 스스로 생성 여부** | 내부식별자 | 외부식별자 |
| **(3) 단일 속성 여부** | 단일식별자 | 복합식별자 |
| **(4) 대체 여부** | **본질식별자** | **인조식별자** |

---

### 본질식별자 (Natural Identifier)

**정의**: 업무에 의해 생성된 식별자

**특징:**
- 비즈니스 로직에서 자연스럽게 도출
- 의미 있는 값
- 업무적으로 유일성 보장

**예시:**
```
직원 테이블
├─────────────────────
│ 주민등록번호 (PK) ← 본질식별자
│ 이름
│ 연봉
└─────────────────────

상품 테이블
├─────────────────────
│ 상품코드 (PK) ← 본질식별자
│ 상품명
│ 가격
└─────────────────────
```

**장점:**
- 업무적으로 의미가 명확
- 별도의 값 생성 불필요

**단점:**
- 업무 규칙 변경 시 식별자 변경 필요
- 복합키가 될 가능성 높음
- 자식 테이블로 전파 시 컬럼 수 증가

---

### 인조식별자 (Surrogate Identifier)

**정의**: 편의를 위해 인위적으로 만든 식별자

**특징:**
- 시스템에서 자동 생성 (일련번호, SEQUENCE 등)
- 업무적 의미 없음
- 단순한 구조

**예시:**
```
직원 테이블 (인조식별자 사용)
├─────────────────────
│ 직원ID (PK) ← 인조식별자 (일련번호)
│ 주민등록번호 (UK)
│ 이름
│ 연봉
└─────────────────────

직원연락처 테이블
├─────────────────────
│ 직원ID (PK, FK)
│ 구분코드 (PK)
│ 연락처
└─────────────────────
```

**다른 예시:**
```
직원연락처이력 테이블 (방법 1 - 본질식별자)
├─────────────────────
│ 직원ID (PK, FK)
│ 구분코드 (PK, FK)
│ 순번 (PK)
│ 연락처
└─────────────────────

직원연락처이력 테이블 (방법 2 - 인조식별자)
├─────────────────────
│ 이력일련번호 (PK) ← 인조식별자
│ 직원ID (FK)
│ 구분코드 (FK)
│ 순번
│ 연락처
└─────────────────────
```

**장점:**
- 단순한 구조 (단일 컬럼 PK)
- 업무 변경에 영향 없음
- 자식 테이블로 전파 시 컬럼 수 최소화
- 성능상 유리 (단일 컬럼 인덱스)

**단점:**
- 업무적 의미 없음
- 별도의 인덱스 관리 필요
- 중복 데이터 입력 가능성

---

### 본질식별자 VS 인조식별자 비교

| 구분 | 본질식별자 | 인조식별자 |
|------|-----------|-----------|
| **생성 방식** | 업무에서 자연 발생 | 시스템이 인위 생성 |
| **의미** | 업무적 의미 있음 | 업무적 의미 없음 |
| **구조** | 복합키 가능성 높음 | 주로 단일 컬럼 |
| **변경 가능성** | 업무 변경 시 영향 받음 | 업무 변경에 독립적 |
| **성능** | 복합키 시 성능 저하 | 단일키로 성능 우수 |
| **관리** | 업무 규칙 준수 필요 | 시스템 자동 관리 |
| **자식 전파** | 컬럼 수 증가 | 컬럼 수 최소 |

---

### 실무 선택 가이드

#### 본질식별자를 사용하는 경우

1. 업무적으로 유일성이 명확한 경우
   - 주민등록번호, 사업자번호, 차량번호 등

2. 외부 시스템과 연동되는 경우
   - 표준 코드, 공통 코드 등

3. 마스터 테이블
   - 코드 테이블, 참조 테이블 등

#### 인조식별자를 사용하는 경우

1. 복합키가 필요한 경우
   - 주문상세, 이력 테이블 등

2. 자주 변경될 가능성이 있는 경우
   - 회원 ID, 이메일 등

3. 성능이 중요한 경우
   - 대용량 트랜잭션 테이블

4. 자식 테이블이 많은 경우
   - PK 전파 시 구조 단순화 필요

---

### 복합 사용 예시

**권장 패턴**: 인조식별자를 PK로, 본질식별자를 UK(Unique Key)로 설정

```
회원 테이블
├─────────────────────
│ 회원번호 (PK) ← 인조식별자 (시스템 생성)
│ 이메일 (UK) ← 본질식별자 (업무적 유일)
│ 이름
│ 가입일
└─────────────────────
```

**장점:**
- 시스템 성능 확보 (단일 PK)
- 업무 유일성 보장 (UK)
- 유연한 데이터 관리

---

## 정리 및 핵심 요약

### 1. 정규화

**핵심 개념:**
- 데이터 중복 제거 및 관심사 분리
- 1NF(원자성) → 2NF(부분종속제거) → 3NF(이행종속제거)
- 실무에서는 주로 3NF까지 수행

**성능 영향:**
- 입력/수정/삭제: 성능 향상 ✓
- 조회: 상황에 따라 다름

### 2. 반정규화

**핵심 개념:**
- 조회 성능 향상을 위해 의도적으로 중복 허용
- 데이터 무결성 위험 존재
- 다른 방법 검토 후 최후 수단으로 사용

**적용 방법:**
- 테이블 병합/분할
- 중복 컬럼 추가
- 파생 컬럼 추가

### 3. 조인

**핵심 개념:**
- 여러 테이블의 데이터를 결합
- FK를 통한 테이블 간 연결
- 계층형 데이터: 자기 참조 관계

### 4. 식별자 관계

**식별자 관계 (강한 종속):**
- FK가 PK의 일부
- 부모 없이 자식 존재 불가

**비식별자 관계 (약한 종속):**
- FK가 일반 속성
- 부모와 독립적 존재 가능

### 5. NULL

**핵심 개념:**
- 미확정 값 표현
- 테이블 구조 유지
- `IS NULL` 또는 `IS NOT NULL`로 비교

### 6. 본질식별자 VS 인조식별자

**본질식별자:**
- 업무에서 자연 발생
- 의미 있지만 복잡할 수 있음

**인조식별자:**
- 시스템이 생성
- 단순하고 성능 우수

**권장 패턴:**
- 인조식별자(PK) + 본질식별자(UK)

---

## 실무 적용 팁

1. **정규화 우선, 반정규화는 신중히**
   - 먼저 완전히 정규화
   - 성능 문제 발생 시에만 반정규화 검토

2. **식별자 관계는 비즈니스 의존성 고려**
   - 강한 의존: 식별자 관계
   - 약한 의존: 비식별자 관계

3. **NULL 허용은 최소화**
   - 가급적 NOT NULL 제약조건 사용
   - 필요한 경우에만 NULL 허용

4. **인조식별자 활용 권장**
   - 대부분의 경우 인조식별자가 유리
   - 마스터/코드 테이블은 본질식별자 고려

5. **ERD 표기법 일관성 유지**
   - 프로젝트 내에서 IE 또는 Barker 중 하나로 통일
   - 관계선, 식별자 표기 규칙 준수
