## 스프링 웹 스코프

### 스코프 개요
- **싱글톤**: 컨텍스트당 빈 이름별 1개 인스턴스(기본).
- **프로토타입**: `getBean` 호출 때마다 새 인스턴스(수명 관리는 호출자 책임).
- **웹 스코프(웹 앱 한정)**  
  - **요청(Request)**: HTTP 요청마다 새 인스턴스, 요청 종료 시 소멸.  
  - **세션(Session)**: HTTP 세션 동안 유지, 동일 클라이언트의 여러 요청 간 공유.  
  - **애플리케이션(Application)**: 앱 전체에서 1개 인스턴스, 모든 요청이 공유.

### 요청 스코프
**특징**
- 요청마다 인스턴스 생성·사용, 요청 종료 후 가비지 컬렉션 대상.
- 단일 요청/스레드에서만 접근 → **동기화 불필요**(동기화는 오히려 성능 저하).

**권장/주의**
- 생성자/`@PostConstruct`에 **DB·네트워크 등 시간 소모 로직 금지**.
- 자격 증명·폼 데이터처럼 **요청 한정 상태** 보관에 적합.

**예시**
- `@RequestScope`가 붙은 `LoginProcessor`를 컨트롤러에 주입하여 로그인 처리.
- 성공 시 메시지 렌더링 또는 `/main`으로 리다이렉션.

### 세션 스코프
**특징**
- 세션 생성 시 인스턴스 생성, 세션 생존 동안 재사용.
- 동일 클라이언트의 여러 요청이 **상태 공유**.

**권장/주의**
- 동시 요청 가능 → **경쟁 상태** 유의, 필요 시 최소 범위로 동기화.
- 세션에 **민감/대용량 데이터 저장 금지**(메모리·보안 리스크).
- 상태 공유가 불필요하면 **영속 저장소(DB/캐시)**로 대체.

**예시**
- `@SessionScope` `LoggedUserManagementService`에 사용자명 저장.
- 로그인 성공 시 세션에 사용자명 기록 → 보호된 `/main` 접근 허용.
- 로그아웃 시 사용자명 `null`로 초기화.

### 애플리케이션 스코프
**특징**
- 애플리케이션 전역 1개, 모든 요청 공유(사실상 전역 상태).
- 싱글톤과 유사하나 **타입당 1개**라는 점이 핵심.

**권장/주의**
- **동시성 이슈**에 취약 → 가능하면 **불변/무상태**로.
- 전역 카운터 등은 **영속 계층/외부 스토어** 사용 권장.
- 프로덕션에서는 대체로 **비권장**(병목·메모리 상주·상태성 증가).

**예시**
- `@ApplicationScope` `LoginCountService`로 전체 로그인 시도 수 집계(데모 용).
- 컨테이너 재시작 시 유실·확장성 부족 → 실서비스는 DB로 집계.

### 실무 체크리스트
- 요청 한정 데이터 → **`@RequestScope`**
- 최소한의 사용자 세션 상태 → **`@SessionScope`**, 민감/대용량 금지
- 전역 공유 상태 지양 → **`@ApplicationScope` 대신 DB/캐시**
- 상태 공유가 늘수록 **stateful 위험** ↑ → 가능하면 **stateless** 설계
- 웹 스코프 빈은 테스트 난이도·동시성 리스크 ↑ → **필요 최소한만** 사용

### 요약
- 웹 스코프는 HTTP 경계를 기준으로 빈 수명·공유 범위를 정한다.  
- **요청 스코프**: 간단·안전(동기화 불필요), 생성 비용 주의.  
- **세션 스코프**: 편리하지만 동시성·메모리·보안 이슈 → 최소화.  
- **애플리케이션 스코프**: 전역 상태로 병목·유실 위험 → **지양**, 영속 계층으로 대체.



## 스프링 앱에서 데이터 소스 사용

### 데이터 소스 개념
- **DataSource**는 DB 커넥션을 **풀링·재사용**해 성능을 높인다.
- JDBC는 **추상화**만 제공 → 실제 DBMS 연결엔 **JDBC 드라이버** 필요.
- 매번 `DriverManager.getConnection(...)`를 호출하는 방식은 **비효율적** → DataSource가 내부적으로 커넥션을 관리/재사용.
- 스프링 부트 기본 구현: **HikariCP**(경량·고성능 커넥션 풀).

### 실무 포인트
- 대개 **부트 자동 구성**으로 DataSource 주입만 받아 사용.
- 테스트/로컬: **H2 인메모리 DB**로 빠르게 검증 (`spring.sql.init`로 스키마 자동 실행).
- 금전/정밀 데이터는 **`BigDecimal`**로 표현(부동소수점 오차 방지).



### JdbcTemplate으로 영속성 작업

#### 핵심 API
- **CUD**: `jdbcTemplate.update(sql, params...)`
- **조회**: `jdbcTemplate.query(sql, rowMapper)` / `queryForObject(...)`
- **RowMapper**: `ResultSet` → 도메인 객체 매핑 람다로 간단 구현

#### 레이어 구성 예시
- **모델**: `Purchase(id, product, price: BigDecimal)`
- **리포지토리**: `PurchaseRepository`
  - `storePurchase(p)` → `INSERT`
  - `findAllPurchases()` → `SELECT` + `RowMapper`
- **컨트롤러** (`/purchase`)
  - `POST` 바디 → 저장
  - `GET` → 전체 목록 반환



### 데이터 소스 구성 사용자 정의

#### application.properties로 설정 (권장)
- JDBC URL/계정/비밀번호 지정 (`spring.datasource.*`)
- 드라이버 의존성만 교체하면 **H2 → MySQL** 전환 용이
- **시크릿은 외부화**(환경변수/Secret Manager) 권장

#### @Bean으로 수동 등록 (특수 상황)
- 다중 데이터베이스/동적 튜닝/부트 미사용 등
- 예: `@Bean DataSource dataSource() { return new HikariDataSource(...); }`
- 수동 DataSource 빈이 존재하면 부트의 기본 자동 구성 대신 **해당 빈을 사용**
- 다중 데이터 소스 사용 시
  - 각 DataSource에 대응하는 **JdbcTemplate**를 생성
  - 주입 시 **`@Qualifier`**로 구분



### 체크리스트

#### 연결/풀링
- 풀 크기·타임아웃은 **운영 환경에 맞게 튜닝**(Hikari: `maximumPoolSize`, `connectionTimeout` 등)
- 연결 누수 방지: 트랜잭션/예외 경로에서 **커넥션 자동 반환**을 신뢰(JdbcTemplate 사용)

#### 스키마 관리
- `schema.sql`은 간단 PoC에 적합
- 실서비스는 **마이그레이션 툴(Flyway/Liquibase)**로 버전 관리

#### 예외 처리
- JDBC 예외는 스프링이 **DataAccessException** 계층으로 변환 → 호출부에서 일관 처리

#### 정밀도/타입
- 금액/수량 등은 **`BigDecimal`** 사용
- `RowMapper`에서 컬럼 타입과 정확히 매칭(`getBigDecimal`, `getInt`, `getString` 등)



### 요약
- **DataSource(커넥션 풀)**로 DB 연결을 효율화하고, 스프링 부트는 기본적으로 **HikariCP**를 자동 구성한다.
- **JdbcTemplate**은 JDBC 작업의 상용구를 제거하여 **간단하고 안전한 CRUD**를 제공한다.
- 환경 전환은 **드라이버·프로퍼티** 교체로 해결, 특수 요구는 **수동 빈 등록**과 **`@Qualifier`**로 다중 DB를 관리한다.
- 스키마는 **마이그레이션 툴**로 버전 관리, 금액은 **`BigDecimal`**, 예외는 **DataAccessException**으로 일관 처리한다.



## 스프링 앱에서 트랜잭션 사용

### 트랜잭션 개념
- **트랜잭션(transaction)**: 원자성을 갖는 가변 작업들의 집합  
- 모든 단계가 성공해야만 데이터 일관성이 보장됨  
- 두 가지 종료 방식:
  - **커밋(commit)**: 변경 사항을 영구 반영
  - **롤백(rollback)**: 시작 시점 상태로 복원



### 스프링 트랜잭션의 동작 방식
- 스프링 트랜잭션은 **AOP 애스펙트** 기반
- `@Transactional` 애너테이션을 사용하면 메서드가 트랜잭션으로 래핑됨
- 내부 로직:
  ```java
  try {
      // 트랜잭션 시작
      // 비즈니스 로직 실행
      // 커밋
  } catch (RuntimeException | Error e) {
      // 롤백
  } catch (Exception e) {
      // 체크 예외는 기본적으로 커밋
  }
    ```

* **런타임 예외/에러** → 롤백
* **체크 예외** → 커밋 (원하는 경우 `rollbackFor` 속성으로 변경 가능)



### 스프링 앱에서 트랜잭션 사용

* `@Transactional`:

  * **메서드 단위** 적용
  * **클래스 단위** 적용 시 모든 메서드 트랜잭션 처리
* 전자 지갑 예제:

  * 원본 계좌 출금
  * 대상 계좌 입금
  * 두 작업을 트랜잭션으로 묶어 원자성 보장



### 예제 구성

1. **모델**: `Account` (id, name, amount)
2. **리포지토리**: `AccountRepository`

   * `findAccountById(id)`
   * `changeAmount(id, amount)`
   * `findAllAccounts()`
3. **서비스**: `TransferService`

   * `@Transactional transferMoney(senderId, receiverId, amount)`
   * `getAllAccounts()`
4. **컨트롤러**: `AccountController`

   * `POST /transfer`
   * `GET /accounts`
5. **DTO**: `TransferRequest` (송신자, 수신자, 금액)



### 트랜잭션 테스트

* **성공 케이스**

  ```bash
  $ curl http://localhost:8080/accounts
  [{"id":1,"name":"Helen Down","amount":1000.0},{"id":2,"name":"Peter Read","amount":1000.0}]

  $ curl -XPOST -H "Content-Type: application/json" \
    -d '{"senderAccountId":1, "receiverAccountId":2, "amount":100}' \
    http://localhost:8080/transfer

  $ curl http://localhost:8080/accounts
  [{"id":1,"name":"Helen Down","amount":900.0},{"id":2,"name":"Peter Read","amount":1100.0}]
  ```
* **실패 케이스 (런타임 예외 발생)**

  ```bash
  $ curl -XPOST -H "Content-Type: application/json" \
    -d '{"senderAccountId":1, "receiverAccountId":2, "amount":100}' \
    http://localhost:8080/transfer
  {"status":500,"error":"Internal Server Error"}

  $ curl http://localhost:8080/accounts
  [{"id":1,"name":"Helen Down","amount":1000.0},{"id":2,"name":"Peter Read","amount":1000.0}]
  ```
* 런타임 예외 발생 시 롤백이 정상적으로 동작함을 확인



### 요약

* **트랜잭션**은 데이터 변경 작업의 원자성을 보장
* 모든 작업이 성공해야 커밋, 하나라도 실패하면 롤백
* 스프링에서 `@Transactional`을 통해 손쉽게 트랜잭션 관리 가능
* 런타임 예외는 기본적으로 롤백, 체크 예외는 커밋 (옵션으로 제어 가능)
* 서비스 계층에서 트랜잭션을 걸어 비즈니스 로직 단위의 무결성 보장



## 스프링 데이터로 데이터 영속성 구현

### 스프링 데이터란
- 스프링 생태계 프로젝트로, **영속성 계층을 최소 코드로 구현**하도록 돕는다.
- 인터페이스(계약)만 정의하면, 스프링이 **런타임 구현체를 자동 생성**해 빈으로 등록한다.
- 다양한 영속성 기술(JDBC, JPA/Hibernate, MongoDB 등)에 대해 **공통 추상화**를 제공한다.

### 작동 방식 & 핵심 계약
- 모듈별로 의존성을 선택(예: **spring-data-jdbc**, **spring-data-jpa**, **spring-data-mongodb**).
- 대표 인터페이스:
  - `Repository` : 마커 인터페이스(연산 없음).
  - `CrudRepository<T, ID>` : 기본 **CRUD** 제공.
  - `PagingAndSortingRepository<T, ID>` : CRUD + **페이지네이션/정렬**.
- 필요 기능만 확장하는 구조로 **인터페이스 분리 원칙(ISP)** 준수.

### 스프링 데이터 JDBC 실전 흐름
- 의존성: `spring-boot-starter-data-jdbc`(+ DB 드라이버/H2).
- **엔터티**: `@Id` 필드 포함(예: `Account`).
- **리포지토리**: `interface AccountRepository extends CrudRepository<Account, Long>`.
- **서비스**: 리포지토리 주입 후 **사용 사례(계좌 이체)** 구현, 무결성 위해 `@Transactional` 적용.
- **컨트롤러**: REST 엔드포인트(`POST /transfer`, `GET /accounts`)에서 서비스 호출.

### 쿼리 정의 방식: 메서드명 vs @Query vs @Modifying
- **메서드 이름 유도 쿼리**: `List<Account> findAccountsByName(String name)`
  - 장점: 코드 최소화.  
  - 단점: 복잡해지면 **이름이 장황**, 리팩터링 실수 위험, **부팅 시 파싱 비용**.
- **@Query**: SQL을 명시하여 명확·성능 유리.
  - 예) `@Query("SELECT * FROM account WHERE name = :name")`
- **변경 쿼리**는 `@Modifying` 필수.
  - 예) `@Modifying @Query("UPDATE account SET amount = :amount WHERE id = :id")`

### 트랜잭션과 서비스 계층
- 비즈니스 규칙(예: **계좌 이체**)은 서비스에서 **원자성 보장**이 필요 → `@Transactional`.
- 조회는 기본 제공(`findById`, `findAll`), 예외/검증은 서비스에서 처리(예: `orElseThrow`로 `AccountNotFoundException`).

### 엔드포인트 구성 예
- `POST /transfer` : `TransferRequestDTO` 수신 → `transferService.transferMoney(...)`
- `GET /accounts` : 전체/이름 필터 조회 → `transferService.getAllAccounts()` / `findAccountsByName(name)`

### 베스트 프랙티스 / 주의점
- 단순 쿼리는 **메서드명 유도**, 복잡/성능 민감 쿼리는 **@Query** 권장.
- 변경 연산은 **@Modifying** 누락 주의.
- 금액/화폐는 **BigDecimal** 사용(정밀도 보장).
- 트랜잭션 경계는 **서비스 계층**에 두고, 컨트롤러/리포지토리는 단순화.
- 모듈은 **기술에 맞춰 선택**(JDBC vs JPA vs Mongo 등).

### 요약
- 스프링 데이터는 다양한 데이터 기술을 **통일된 인터페이스**로 다루게 해 개발 속도와 유지보수를 향상한다.
- JDBC 사용 시 **CrudRepository** 확장만으로 기본 CRUD 확보, 필요 시 `@Query`/`@Modifying`로 확장.
- 비즈니스 로직은 `@Transactional`로 **무결성/원자성**을 보장하며, REST로 쉽게 노출 가능하다.
