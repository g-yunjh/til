## 스프링 컨텍스트: 빈 정의 & 작성

### 스프링 컨텍스트에 새로운 빈 추가
스프링에서 객체를 관리하려면 스프링 컨텍스트에 빈(bean)으로 등록해야 한다. 등록 방식은 크게 세 가지다:

1. **@Bean 애너테이션 사용**  
   - `@Configuration` 클래스를 만들고, 인스턴스를 반환하는 메서드에 `@Bean`을 붙인다.  
   - 메서드 이름이 빈의 이름이 된다.  
   - 동일 타입의 여러 인스턴스를 등록할 수 있으며, 라이브러리 클래스처럼 소스 코드를 수정할 수 없는 경우에도 활용 가능하다.  
   - 단점: 빈마다 별도의 메서드를 작성해야 하므로 상용구(boilerplate) 코드가 늘어난다.

2. **스테레오타입 애너테이션(@Component 등) 사용**  
   - 클래스 선언부에 `@Component`를 붙이고, `@ComponentScan`을 통해 탐색 경로를 지정하면 자동으로 빈으로 등록된다.  
   - 코드 양이 적어 가독성이 높다.  
   - 단, 애플리케이션 내부 클래스만 등록할 수 있고, 동일 타입은 기본적으로 하나만 관리된다.  

   👉 실무에서는 기본적으로 **스테레오타입 애너테이션을 우선 사용**하고, 불가피할 때만 `@Bean`을 활용한다.

3. **프로그래밍 방식 등록 (`registerBean`)**  
   - `ApplicationContext.registerBean()` 메서드를 호출해 런타임에 동적으로 빈을 추가한다.  
   - 인스턴스 직접 제어, Supplier 제공, BeanDefinitionCustomizer 활용 가능.  
   - 매우 유연하지만 **Spring 5 이상**에서만 사용할 수 있는 방법이다.  



### 구성 파일에서 정의된 빈 간 관계 구현
빈 간에는 종속성(예: `Person`이 `Parrot`을 소유)이 있을 수 있으며, 다음 방식으로 연결한다:

1. **두 @Bean 메서드 간 직접 메서드 호출 (와이어링)**  
   - `person()` 메서드 안에서 `parrot()` 메서드를 직접 호출해 주입.  
   - 스프링은 이미 생성된 빈이 있으면 재생성하지 않고 기존 빈을 사용한다.

2. **@Bean 메서드의 매개변수로 의존성 주입**  
   - `public Person person(Parrot parrot)` 형태로 정의하면, 스프링이 타입에 맞는 빈을 자동으로 주입한다.  
   - 이 방식이 더 깔끔하며, DI(Dependency Injection)의 기본적인 형태이다.  



### @Autowired 애너테이션을 사용한 빈 주입
의존성을 연결하는 또 다른 방법은 `@Autowired`를 이용하는 것이다. 주입 위치에 따라 다음 세 가지 방식이 있다:

1. **필드 주입**  
   - `@Autowired`를 필드에 직접 붙여서 주입.  
   - 간단하지만 `final`을 사용할 수 없고 테스트하기 어려워 실무에선 권장되지 않는다.

2. **생성자 주입** (추천)  
   - `@Autowired`를 생성자에 붙여 주입.  
   - 스프링 4.3 이상에서는 생성자가 하나뿐이면 `@Autowired` 생략 가능.  
   - `final` 필드 사용 가능해 안정성이 높고, 테스트하기도 용이하다.

3. **Setter 주입**  
   - 세터 메서드에 `@Autowired` 적용.  
   - 과거에는 종종 사용했지만, 유지보수성과 불변성을 해치므로 실제 서비스 코드에선 거의 쓰이지 않는다.  



### 순환 의존성 다루기
- **순환 의존성(circular dependency)**: A 빈이 B 빈을 필요로 하고, 동시에 B 빈이 A 빈을 필요로 하는 상황.  
- 스프링은 이를 허용하지 않으며 `BeanCurrentlyInCreationException` 같은 예외를 발생시킨다.  
- 순환 의존성이 보인다면 설계가 잘못된 것이므로 리팩터링이 필요하다.  
- 해결책: 의존 관계 단절, 인터페이스 도입, 지연 주입(`@Lazy`) 등의 기법.



### 스프링 컨텍스트에서 여러 빈 중 선택하기
동일한 타입의 빈이 여러 개 등록되면 모호성이 생기며, 해결 방법은 다음과 같다:

1. **빈 이름 기반 선택**  
   - 매개변수명 또는 `context.getBean("beanName", Type.class)` 방식으로 특정 빈을 가져올 수 있다.

2. **@Primary 사용**  
   - 동일 타입 빈 중 하나를 기본 빈으로 지정해 충돌을 방지한다.

3. **@Qualifier 사용**  
   - 의존성 주입 시 명시적으로 특정 빈 이름을 지정한다.  
   - 실무에서는 매개변수 이름에 의존하기보다 `@Qualifier`를 권장한다.  



✅ **정리**  
- 빈 등록 방법: `@Bean`, `@Component`, `registerBean`  
- 빈 관계 설정: 메서드 호출 / 매개변수 주입  
- 의존성 주입: 생성자 주입을 기본으로, 필요시 `@Autowired` 활용  
- 순환 의존성은 설계 문제 → 반드시 피해야 함  
- 동일 타입 빈이 여러 개일 때: `@Primary` 또는 `@Qualifier` 사용  



## 스프링 컨텍스트: 추상화

### 계약 정의를 위한 인터페이스 사용
- **인터페이스의 역할**: 무엇이 발생해야 하는지(계약)를 정의, 구현체는 어떻게 발생할지를 정의.  
- **구현 분리 장점**  
  - DIP(의존성 역전 원칙): 구현이 아닌 추상화에 의존 → 변경 유연성 확보  
  - OCP(개방-폐쇄 원칙): 새로운 구현을 추가해도 기존 코드 수정 불필요  
- **예시**:  
  - `DeliveryDetailsPrinter`는 정렬 책임을 직접 가지지 않고, `Sorter` 인터페이스에 위임.  
  - `CommentService` 역시 댓글 저장(`CommentRepository`)과 알림 전송(`CommentNotificationProxy`)을 인터페이스로 분리.



### 프레임워크 없이 요구 사항 구현
- **시나리오 요구사항**:  
  1. 사용자가 댓글을 남긴다.  
  2. 댓글은 저장소에 저장되고, 특정 주소로 알림(이메일 등)이 전송된다.  
- **구성 요소**  
  - `Comment`: 모델(POJO)  
  - `CommentRepository`: 저장소 인터페이스  
  - `DBCommentRepository`: 저장소 구현체  
  - `CommentNotificationProxy`: 알림 전송 인터페이스  
  - `EmailCommentNotificationProxy`: 알림 구현체  
  - `CommentService`: 서비스, 위 두 의존성을 받아서 댓글 게시(use case) 실행  

👉 인터페이스를 통해 구현을 교체 가능하게 하여, 변경 요구(저장 방식/알림 방식)가 생겨도 `CommentService` 코드는 그대로 유지된다.



### 추상화와 함께 의존성 주입
- 스프링 컨텍스트에 추가해야 할 객체는 **의존성을 가지거나, 다른 객체의 의존성이 되는 경우**다.  
  - `CommentService` (의존성 2개 필요)  
  - `DBCommentRepository` (의존성 제공자)  
  - `EmailCommentNotificationProxy` (의존성 제공자)  
- `Comment` 같은 단순 데이터 모델은 빈으로 등록하지 않는다. (→ 오버엔지니어링 방지)  
- `@Component`와 `@ComponentScan`을 활용해 자동 등록.  
- 생성자 주입을 통해 의존성을 연결하면, 개발자는 직접 인스턴스를 생성할 필요가 없고 스프링이 관리.



### 추상화의 여러 구현체 선택하기
- 동일 인터페이스 구현체가 여러 개 있으면 스프링은 어떤 빈을 주입할지 결정하지 못해 `NoUniqueBeanDefinitionException` 발생.  
- 해결 방법:
  1. **@Primary**: 기본 구현을 하나 지정.  
     - 간단하게 기본 구현을 바꾸고 싶을 때 유용.  
  2. **@Qualifier**: 특정 이름을 붙여서 주입 시 명시적으로 선택.  
     - 예:  
       - `@Qualifier("EMAIL")` → 이메일 알림  
       - `@Qualifier("PUSH")` → 푸시 알림  
     - 서비스에서 생성자 매개변수에 `@Qualifier("PUSH")` 지정 → 원하는 구현체 주입.  

👉 실무에서는 서비스마다 다른 구현체가 필요할 수 있으므로 `@Qualifier` 활용이 더 명확하다.



### 스테레오타입 애너테이션으로 책임 표현
- 단순 `@Component` 대신 의도를 명확히 드러내는 스테레오타입 사용:  
  - `@Service`: 사용 사례(비즈니스 로직) 구현 책임  
  - `@Repository`: 데이터 접근 및 영속성 관리 책임  
- 책임이 드러나므로 **코드 가독성**과 **설계 이해도**가 향상된다.



### 요약
- **추상화(인터페이스)**는 구현을 분리하여 OCP와 DIP 원칙을 지킨다.  
- **의존성 주입(DI)**과 결합하면 스프링은 추상화된 계약의 구현체를 자동으로 주입한다.  
- **다중 구현체 처리**: `@Primary`(기본값) 또는 `@Qualifier`(명시적 선택).  
- **스테레오타입 애너테이션**: `@Service`, `@Repository`를 사용해 클래스의 책임을 명확히 표현한다.  

## 스프링 컨텍스트: 빈의 스코프 및 수명 주기

### 스코프 개요
- **주요 스코프**: `singleton`(기본), `prototype`
- **웹 컨텍스트 스코프**: `request`, `session`, `application` (웹 환경/서블릿 컨텍스트에서만 의미 있음)
- **핵심**: 스코프는 “언제/얼마나 자주 인스턴스를 만들고 누가 수명 주기를 관리하느냐”를 정한다.



### 싱글톤 스코프
**동작**
- 컨텍스트당 **빈 이름별로 딱 1개 인스턴스**를 유지. (같은 타입이라도 이름이 다르면 여러 개 가능)
- `@Bean`이든 `@Component`든 **기본이 싱글톤**.
- `getBean("name")` 호출 시 **항상 같은 인스턴스**가 반환됨.

**실전 이슈 & 권장 사항**
- 싱글톤은 **여러 스레드가 공유** → 가변 상태(mutable state)면 경쟁 상태(race condition) 위험.
- 가능하면 **불변(immutable) 설계 + 생성자 주입 + `final` 필드**로 구성.
- 빈을 컨텍스트에 올리는 기준: **프레임워크 보강(트랜잭션, AOP, 설정 주입 등)**이 필요한 객체만. (무분별한 등록 = 오버엔지니어링)

**즉시/지연 초기화**
- **즉시(eager, 기본)**: 컨텍스트 초기화 시 생성 → 의존성 유효성/오류를 **앱 시작 시점**에 조기 발견.
- **지연(lazy)**: 최초 사용 시 생성 (`@Lazy`) → 메모리 절약 가능하지만, 설계 신호로 **모듈 분리 고려**.



### 프로토타입 스코프
**동작**
- `getBean("name")` 호출 **매번 새 인스턴스** 생성.
- 스프링은 **생성까지만** 관여, 이후 **수명 주기(특히 소멸)는 호출자 책임**.
- 가변 상태를 안전하게 다루는 데 적합(스레드 간 공유 안 함).

**선언**
- `@Scope(BeanDefinition.SCOPE_PROTOTYPE)`를 `@Bean` 메서드나 스테레오타입 클래스에 부여.

**실전 사용**
- 요청마다 상태가 달라지는 **처리기/빌더/컨텍스트 객체** 등은 프로토타입 후보.
- 하지만 “정말 빈이어야 하는가?”를 먼저 검토. 단순 지역 객체면 **new**로 충분.



### 프로토타입을 싱글톤에 주입할 때의 함정 & 해법
**문제**
- 싱글톤 생성 시점에 프로토타입 빈을 **한 번만** 주입하면, 그 후엔 사실상 **싱글톤처럼** 공유됨 → 프로토타입의 의도가 무너짐.

**안티패턴**
- `@Autowired private CommentProcessor p;` (프로토타입)  
  → 한 번 주입된 `p`가 **계속 재사용**됨.

**권장 해법**
1) **요청 시 조회(lookup)**  
   - `ApplicationContext#getBean(PrototypeType.class)`를 **사용 시점**에 호출.  
   - 또는 `ObjectFactory<T>` / `ObjectProvider<T>`를 주입해 **필요할 때마다 `getObject()`** 호출.
2) **@Lookup 메서드 주입**  
   - 추상 메서드에 `@Lookup`을 붙여 호출 때마다 새 인스턴스 반환(프록시 기반).
3) **스코프 프록시** *(웹 스코프 등)*  
   - `@Scope(value = "request", proxyMode = TARGET_CLASS)`처럼 프록시로 지연 결정을 위임.

> 일반 서비스(싱글톤)에서 가변 작업이 필요하다면: **프로토타입을 직접 들고 있지 말고, 매 호출마다 “조회/생성”**하는 패턴으로 가져오기.



### 싱글톤 vs 프로토타입 비교 요약

| 구분 | 싱글톤 | 프로토타입 |
|---|---|---|
| 인스턴스 수명 | 컨텍스트당 1개(빈 이름별) | `getBean` 호출마다 새로 생성 |
| 기본 스코프 | 예 | 아니오 (`@Scope` 필요) |
| 생성 시점 | eager(기본) 또는 lazy | 호출 시 항상 새로 |
| 상태 관리 | **불변 권장**(가변이면 동기화 부담) | **가변 허용**(공유 안 함) |
| 소멸 관리 | 스프링이 관리 | 호출자(클라이언트) 책임 |



### 한눈에 정리
- **대부분은 싱글톤**으로: 불변/무상태(stateless) 서비스 구성에 적합.
- **가변 상태를 안전하게** 쓰려면 프로토타입을 고려하되, **싱글톤에 직접 고정 주입 금지** → `ObjectProvider`/`@Lookup`/요청 시 조회 패턴 사용.
- **즉시 초기화**는 빠른 오류 발견 & 의존성 보장, **지연 초기화**는 메모리 절감(설계 개선 신호일 수 있음).
- 스프링 빈으로 등록할지 여부는 “**프레임워크 이점이 필요한가?**”를 기준으로 결정.



## 스프링 AOP로 애스펙트 사용

### 스프링에서 애스펙트 작동 방식
- **용어**
  - **Aspect**: 실행할 부가 로직(what)
  - **Advice**: 실행 시점(when: @Around, @Before, @After, @AfterReturning, @AfterThrowing)
  - **Pointcut**: 어떤 메서드를 가로챌지(where/which, 예: `execution(..)`, `@annotation(..)`)
  - **Join point**: 가로챌 수 있는 지점(스프링 AOP에선 “메서드 호출”)
- **프록시 기반 동작**
  - 스프링은 대상 빈 주위에 **프록시**를 둘러 **위빙(weaving)**한다.
  - 컨텍스트에서 빈을 주입/조회하면 실제 객체가 아닌 **프록시**가 반환된다.
  - 포인트컷에 매칭되면 프록시가 **어드바이스**를 실행한 뒤 필요 시 실제 메서드로 위임한다.

### 스프링 AOP를 사용한 애스펙트 구현
- **필수 설정**
  - `@EnableAspectJAutoProxy`로 애스펙트 기능 활성화
  - `@Aspect`로 애스펙트 클래스 선언 후 반드시 빈으로 등록
  - 어드바이스 애너테이션(@Around 등)으로 포인트컷 지정
- **@Around 기본 패턴**
  - 흐름: (전) 로직 → `pjp.proceed(..)`로 실제 메서드 실행 → (후) 로직
  - **매개변수·반환값 조작 가능** → 하지만 남용은 유지보수성 저하
- **애너테이션 기반 포인트컷**
  - `@ToLog` 같은 커스텀 애너테이션 활용
  - `@Around("@annotation(ToLog)")`로 간단히 표현 가능

### 어드바이스 종류와 특징
- **@Around**: 가장 강력, 흐름 제어/예외 처리/데이터 조작 가능
- **@Before**: 실제 메서드 **호출 전**
- **@AfterReturning**: 정상 반환 후 실행, 반환값 접근 가능
- **@AfterThrowing**: 예외 발생 시 실행, 예외 접근 가능
- **@After**: 성공/실패 상관없이 항상 실행

### 애스펙트 실행 체인
- 여러 애스펙트가 같은 포인트컷을 가로챌 수 있음
- 순서가 중요하다면 `@Order`로 실행 순서를 지정 (낮을수록 먼저 실행)
- 지정하지 않으면 컨테이너 등록 순서 등에 의존 → 예측 어려움

### 실무 팁 & 주의사항
- **Self-invocation 문제**: 동일 빈 내부에서 자기 메서드를 호출하면 프록시를 거치지 않아 AOP가 적용되지 않음 → 구조 분리 필요
- **프록시 한계**:
  - JDK 동적 프록시: 인터페이스 기반
  - CGLIB: 클래스 상속 기반 → `final` 클래스/메서드는 불가
- **가시성**: 보통 `public` 메서드에서만 유효
- **안전한 사용**: 파라미터/리턴값 변조는 꼭 필요한 경우에만, 로깅/보안/트랜잭션 같은 **횡단 관심사**에 집중
- **스프링 기능과의 관계**: `@Transactional`, `@PreAuthorize` 등도 AOP 기반 → 체인 순서가 결과에 영향

### 요약
- 스프링 AOP는 **프록시로 메서드 호출을 가로채** 공통 관심사를 주입한다.
- 구현은 `@EnableAspectJAutoProxy` + `@Aspect` + 포인트컷/어드바이스 조합으로 가능하다.
- **@Around**가 가장 강력하지만 남용은 금물.
- 여러 애스펙트가 있을 땐 `@Order`로 실행 순서 제어.
- 프록시의 한계(Self-invocation, final 등)를 이해하고 설계에 반영해야 한다.
